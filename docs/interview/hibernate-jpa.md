# Hibernate / JPA

### 1. Что такое проблема N+1 и как её решить

Проблема N+1 — это ситуация, когда при загрузке N сущностей (например, списка пользователей) Hibernate выполняет 1 запрос для их получения, а затем для каждой из N сущностей выполняет ещё один дополнительный запрос для загрузки связанных с ней данных (например, заказов каждого пользователя). Итого получается N+1 запросов вместо одного или двух, что сильно бьёт по производительности.

Решить проблему можно несколькими способами:
- **`JOIN FETCH`** в JPQL-запросе: заставляет Hibernate загрузить основную сущность и связанные с ней данные одним SQL-запросом с `JOIN`.
- **`@EntityGraph`**: декларативно указывает, какие ассоциации нужно загрузить жадно в конкретном запросе, не меняя глобальную стратегию загрузки.
- **`@BatchSize`** или **batch fetching**: Hibernate загружает связанные сущности не по одной, а пакетами по указанному размеру, сокращая общее количество запросов.
- **DTO-проекции**: для read-only сценариев лучше сразу выбирать только нужные поля в DTO, избегая загрузки полных сущностей и их связей.


### 2. В чём разница между Lazy и Eager загрузкой

- **Eager (жадная) загрузка**: связанные сущности или коллекции загружаются **немедленно**, в тот же момент, когда загружается корневая сущность. Это гарантирует, что данные уже в памяти, но может приводить к загрузке лишних данных и проблеме N+1.
- **Lazy (ленивая) загрузка**: связанные сущности загружаются **отложенно**, только при первом обращении к ним из кода. Hibernate возвращает прокси-объект, который инициализируется реальными данными при вызове метода. Это экономит память и ресурсы, если связанные данные не всегда нужны.


### 3. Когда использовать Lazy, а когда Eager loading

- **Lazy** рекомендуется использовать по умолчанию, особенно для коллекций (`@OneToMany`, `@ManyToMany`). Это позволяет избежать загрузки ненужных данных и снизить нагрузку на БД. Hibernate по умолчанию применяет `LAZY` для коллекций.
- **Eager** стоит выбирать только тогда, когда связанные данные **всегда** нужны вместе с корневой сущностью в подавляющем большинстве сценариев использования. Например, для `@ManyToOne`, где связь обязательна и часто используется. Hibernate по умолчанию использует `EAGER` для `@ManyToOne` и `@OneToOne`. Но даже в этом случае лучше предпочесть явную загрузку через `JOIN FETCH` или `@EntityGraph` в конкретных запросах, а не глобальный `EAGER`.


### 4. Что такое LazyInitializationException и как её избежать

`LazyInitializationException` возникает, когда код пытается обратиться к лениво загруженной ассоциации (прокси) **после того, как сессия Hibernate (Persistence Context) была закрыта**. Hibernate больше не может выполнить запрос к БД, чтобы инициализировать прокси, и выбрасывает исключение.

Способы избежать:
- **Загрузить данные заранее** внутри транзакции с помощью `JOIN FETCH` или `@EntityGraph`, чтобы к моменту закрытия сессии нужные ассоциации уже были инициализированы.
- **Использовать DTO-проекции** и возвращать из сервисного слоя уже готовые объекты передачи данных, а не сущности с ленивыми связями.
- **Инициализировать вручную** с помощью `Hibernate.initialize()` внутри транзакции, если нужно загрузить конкретную ассоциацию.
- **Open Session in View (OSIV)** — паттерн, при котором сессия остаётся открытой на время рендеринга представления (например, в Spring Boot включён по умолчанию). Это решает проблему, но считается спорной практикой, так как держит соединение с БД дольше необходимого.

```java
// ❌ LazyInitializationException: обращение к ленивой ассоциации вне сессии
public class OrderService {

    @Transactional(readOnly = true)
    public OrderDto getOrderDto(Long id) {
        Order order = orderRepo.findById(id).orElseThrow();
        // Сессия ещё открыта (внутри @Transactional)
        // Но если мы выйдем из транзакции и попробуем получить customers:
        // order.getCustomers().forEach(...); // LLE вне транзакции!
        return mapToDto(order);
    }

    // ✅ Решение 1: JOIN FETCH
    @Transactional(readOnly = true)
    public OrderDto getOrderDtoWithCustomers(Long id) {
        Order order = orderRepo.findByIdWithCustomers(id); // JOIN FETCH
        // customers уже загружены
        return mapToDto(order);
    }

    // ✅ Решение 2: DTO-проекция
    @Transactional(readOnly = true)
    public OrderDto getOrderDtoProjection(Long id) {
        // Запрашиваем только нужные поля, без ленивых связей
        return orderRepo.findOrderDtoById(id);
    }
}

// Repository
public interface OrderRepository extends JpaRepository<Order, Long> {

    @Query("SELECT o FROM Order o JOIN FETCH o.customers WHERE o.id = :id")
    Order findByIdWithCustomers(@Param("id") Long id);

    @Query("SELECT new com.example.OrderDto(o.id, o.total, COUNT(o.customers)) FROM Order o WHERE o.id = :id")
    OrderDto findOrderDtoById(@Param("id") Long id);
}
```


### 5. Какие стратегии fetch существуют в Hibernate

В Hibernate есть несколько стратегий извлечения данных (fetch strategies), которые определяют, как и когда загружаются связанные сущности:
- **Join fetching**: Hibernate загружает связанные сущности или коллекции в том же `SELECT` с помощью `OUTER JOIN`.
- **Select fetching**: для загрузки связанной сущности или коллекции выполняется **отдельный `SELECT`**. По умолчанию этот запрос выполняется лениво, при первом обращении к ассоциации.
- **Subselect fetching**: для загрузки коллекций, связанных со всеми сущностями, полученными в предыдущем запросе, выполняется **один дополнительный `SELECT` с подзапросом**, который переиспользует исходный запрос.
- **Batch fetching**: оптимизация для select fetching. Hibernate загружает связанные сущности **пакетами** по заданному размеру (например, `@BatchSize`), используя `IN` условие, вместо N отдельных запросов.


### 6. Что делает аннотация @BatchSize

`@BatchSize` указывает Hibernate, сколько лениво загружаемых сущностей или коллекций следует инициализировать **за один пакетный запрос**. Вместо того чтобы выполнять отдельный SQL-запрос для каждой ленивой ассоциации, Hibernate группирует их и загружает пачками указанного размера. Это значительно сокращает количество обращений к базе данных (например, со 100 запросов до 5 при `@BatchSize(size = 20)`).

Аннотацию можно ставить на класс сущности (для пакетной загрузки прокси этой сущности) или на поле коллекции.


### 7. Опишите жизненный цикл Entity в Hibernate

Жизненный цикл сущности в Hibernate/JPA описывается четырьмя основными состояниями, через которые она проходит от создания до удаления: **transient**, **persistent** (managed), **detached** и **removed**. Переходы между состояниями управляются `EntityManager` (или `Session`) и связаны с `Persistence Context`.


### 8. Что такое состояния: transient, persistent, detached, removed

- **Transient (новое/временное)**: объект только что создан с помощью `new`, у него ещё нет идентификатора (или он не сгенерирован), и он **не связан** с `Persistence Context`. Такой объект не сохраняется в БД автоматически.
- **Persistent / Managed (управляемое)**: объект **связан** с `Persistence Context` и имеет идентификатор. Все изменения в нём отслеживаются (dirty checking), и при flush/commit Hibernate синхронизирует их с БД. Объект становится managed после `persist()`, `merge()` или загрузки из БД через `find()`/JPQL.
- **Detached (отсоединённое)**: объект имеет идентификатор, но **больше не связан** с `Persistence Context` (например, после закрытия сессии или `detach()`). Изменения в нём не отслеживаются, и автоматического обновления в БД не произойдёт.
- **Removed (удалённое)**: объект связан с `Persistence Context` и имеет идентификатор, но **запланирован к удалению**. При flush Hibernate выполнит `DELETE` для этого объекта.


### 9. Что такое кэш первого уровня в Hibernate

Кэш первого уровня — это **кэш сессии** (`Session`/`EntityManager`), который включён всегда и не может быть отключён. Он представляет собой `Persistence Context` — хранилище всех сущностей, загруженных или добавленных в текущей сессии. Когда вы повторно запрашиваете ту же сущность по идентификатору в рамках одной сессии, Hibernate возвращает её из кэша, не обращаясь к БД. Это гарантирует идентичность объектов в рамках одной сессии.


### 10. Что такое кэш второго уровня и когда его использовать

Кэш второго уровня — это **разделяемый кэш**, привязанный к `SessionFactory` (а не к отдельной сессии). Он может быть разделён между несколькими сессиями и даже экземплярами приложения (например, при использовании Redis). По умолчанию **отключён**.

Использовать его имеет смысл для данных, которые:
- **Часто читаются**, но **редко изменяются** (справочники, каталоги, конфигурации).
- Допускают некоторую задержку актуальности (eventual consistency).

Не стоит кэшировать сущности с высокой частотой записи или данными, критичными к свежести (например, баланс счёта).


### 11. Как настроить кэш второго уровня

Настройка включает несколько шагов:
1. **Включить** кэш в конфигурации Hibernate (свойство `hibernate.cache.use_second_level_cache = true`).
2. **Указать провайдера** кэша (например, EhCache, Caffeine, Infinispan, Redisson) через `hibernate.cache.region.factory_class`.
3. **Пометить сущности**, которые должны кэшироваться, аннотацией `@Cache` (из `org.hibernate.annotations`), указав стратегию конкурентного доступа (`CacheConcurrencyStrategy`), например `READ_ONLY`, `READ_WRITE`, `NONSTRICT_READ_WRITE` или `TRANSACTIONAL`.
4. При необходимости настроить **кэш запросов** (`hibernate.cache.use_query_cache = true`) для кэширования результатов конкретных запросов.


### 12. Что такое dirty checking в Hibernate

Dirty checking — это механизм Hibernate, который **автоматически обнаруживает изменения** в управляемых (persistent) сущностях. При загрузке сущности Hibernate сохраняет снимок её состояния. При flush он сравнивает текущее состояние каждого управляемого объекта со снимком. Если обнаружены изменения, Hibernate генерирует и выполняет соответствующие `UPDATE` (или `INSERT`/`DELETE`) запросы, даже если вы явно не вызывали `save()` или `update()`.


### 13. Как работает механизм flush в Hibernate

**Flush** — это процесс синхронизации состояния `Persistence Context` с базой данных. Во время flush Hibernate:
1. Выполняет **dirty checking** для всех управляемых сущностей.
2. Генерирует и выполняет **SQL-запросы** (`INSERT`, `UPDATE`, `DELETE`) для всех новых, изменённых и удалённых сущностей.
3. Синхронизирует состояние сессии с БД, но **не завершает транзакцию** (commit происходит отдельно).

Flush может происходить автоматически (перед выполнением запроса, затрагивающего те же таблицы, или при commit транзакции) или вызываться вручную через `EntityManager.flush()`.


### 14. В чём разница между persist() и merge()

- **`persist()`** переводит **новую (transient)** сущность в состояние **persistent (managed)**. Он добавляет объект в `Persistence Context`, и при flush будет выполнен `INSERT`. Если сущность уже managed, `persist()` ничего не делает. Если сущность detached, поведение не определено (может быть выброшено исключение).
- **`merge()`** используется для **detached** сущности. Он копирует состояние переданного detached-объекта в **managed-копию** (либо загружает существующую из БД, либо создаёт новую). Возвращается именно **managed-экземпляр**, а переданный объект остаётся detached. Если сущности с таким ID нет, будет выполнен `INSERT`; если есть — `UPDATE`.


### 15. Что делает метод refresh()

`refresh()` обновляет состояние **managed-сущности** из базы данных. Он перечитывает данные из БД и перезаписывает ими текущий объект в `Persistence Context`. Это полезно, если вы подозреваете, что данные в БД были изменены другим процессом (например, триггером или другой транзакцией), и хотите синхронизировать объект с актуальным состоянием БД. Все несохранённые изменения в объекте будут потеряны.


### 16. Что такое EntityManager и чем он отличается от Session

- **`EntityManager`** — это интерфейс из спецификации **JPA** (`javax.persistence` / `jakarta.persistence`). Он предоставляет стандартный API для работы с персистентностью: `persist`, `merge`, `remove`, `find`, `createQuery` и т.д. Это часть Java EE / Jakarta EE.
- **`Session`** — это интерфейс из **Hibernate** (`org.hibernate`). Он **расширяет** `EntityManager` и добавляет несколько специфичных для Hibernate операций. В Hibernate каждый `EntityManager` фактически является `Session` (можно получить через `unwrap()`).

Таким образом, `EntityManager` — это стандартный API JPA, а `Session` — это реализация/расширение от Hibernate с дополнительными возможностями.


### 17. Как реализовать оптимистичную блокировку в JPA

Оптимистичная блокировка предполагает, что конфликты происходят редко, и не блокирует данные на время транзакции. Вместо этого она **обнаруживает конфликт при commit**. Реализуется путём добавления в сущность поля-версии, помеченного аннотацией `@Version` (обычно `int`, `long` или `Timestamp`). При каждом обновлении Hibernate увеличивает версию и проверяет, что она не изменилась с момента загрузки. Если версия изменилась (другая транзакция успела обновить запись), выбрасывается `OptimisticLockException`.

```java
@Entity
public class Account {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String owner;

    private BigDecimal balance;

    @Version
    private Long version;  // Оптимистичная блокировка

    // Методы...
}

// При обновлении:
// UPDATE accounts SET balance=?, version=? WHERE id=? AND version=?
// Если версия изменилась — 0 строк обновлено → OptimisticLockException
```


### 18. Как реализовать пессимистичную блокировку в JPA

Пессимистичная блокировка явно **блокирует** запись в базе данных на время транзакции, предотвращая её изменение другими транзакциями. В JPA это делается через `EntityManager.find()` или `Query` с параметром `LockModeType`, например `LockModeType.PESSIMISTIC_WRITE` (обычно транслируется в `SELECT ... FOR UPDATE`). Другие транзакции, пытающиеся изменить или заблокировать эту же запись, будут ждать освобождения блокировки. Это стратегия выбора при высокой конкуренции за одни и те же данные.

```java
// Пессимистичная блокировка через EntityManager
@Transactional
public void transferFunds(Long fromId, Long toId, BigDecimal amount) {
    // Блокируем обе записи на время транзакции
    Account from = em.find(Account.class, fromId, LockModeType.PESSIMISTIC_WRITE);
    Account to = em.find(Account.class, toId, LockModeType.PESSIMISTIC_WRITE);

    if (from.getBalance().compareTo(amount) < 0) {
        throw new InsufficientFundsException();
    }

    from.setBalance(from.getBalance().subtract(amount));
    to.setBalance(to.getBalance().add(amount));

    // При commit блокировки будут освобождены
}
```


### 19. Что такое @Version и зачем она нужна

`@Version` — это аннотация JPA, которая помечает поле сущности как **атрибут версии** для реализации **оптимистичной блокировки**. Hibernate автоматически управляет этим полем: увеличивает его при каждом обновлении и использует в условии `WHERE` при `UPDATE`/`DELETE`. Если количество обновлённых строк равно 0 (версия не совпала), значит, запись была изменена другой транзакцией, и выбрасывается `OptimisticLockException`. Это позволяет обнаруживать конфликты конкурентного доступа без явных блокировок БД.


### 20. Как работают каскадные операции (Cascade)

Каскадные операции позволяют **автоматически распространять** определённое действие (например, `persist`, `merge`, `remove`) с родительской сущности на связанные с ней дочерние сущности. Без каскада вам пришлось бы явно вызывать `persist()` для каждого дочернего объекта. Каскад настраивается атрибутом `cascade` в аннотациях связей (`@OneToMany`, `@ManyToOne` и т.д.).


### 21. Какие типы Cascade существуют

В JPA (`CascadeType`) определены следующие типы:
- **`PERSIST`**: при `persist()` родителя также сохраняются связанные сущности.
- **`MERGE`**: при `merge()` родителя также обновляются связанные сущности.
- **`REMOVE`**: при `remove()` родителя также удаляются связанные сущности.
- **`REFRESH`**: при `refresh()` родителя также обновляются связанные сущности из БД.
- **`DETACH`**: при `detach()` родителя связанные сущности также отсоединяются от `Persistence Context`.
- **`ALL`**: включает все перечисленные операции.


### 22. Что такое orphan removal

**Orphan removal** (`orphanRemoval = true`) — это более агрессивная форма каскадного удаления, введённая в JPA 2.0. Она удаляет дочернюю сущность, когда она **перестаёт быть связанной** с родительской сущностью (становится «сиротой»). Например, если вы удаляете элемент из коллекции `@OneToMany` на родителе, Hibernate автоматически выполнит `DELETE` для этого дочернего объекта в БД. В отличие от `CascadeType.REMOVE`, который срабатывает только при удалении самого родителя, `orphanRemoval` реагирует на разрыв связи.


### 23. Как правильно использовать @OneToMany и @ManyToOne

Правильное использование двунаправленной связи `@OneToMany` / `@ManyToOne`:
- На стороне **«многие»** (`@ManyToOne`) указывается внешний ключ и владелец связи. Именно эта сторона отвечает за обновление колонки внешнего ключа в БД.
- На стороне **«один»** (`@OneToMany`) используется атрибут `mappedBy`, который указывает на поле в классе «многие», владеющее связью. Это делает связь **двунаправленной** и позволяет избежать создания лишней промежуточной таблицы.

Важно поддерживать согласованность обеих сторон в коде (например, при добавлении ребёнка в коллекцию также устанавливать родителя у ребёнка), чтобы избежать проблем при сохранении.


### 24. В чём особенности bidirectional relationships

Двунаправленные связи (`bidirectional`) имеют две стороны: владельца (`owning side`, обычно `@ManyToOne`) и обратную сторону (`inverse side`, обычно `@OneToMany` с `mappedBy`). Особенности:
- Только владелец управляет обновлением внешнего ключа в БД. Изменения на обратной стороне не влияют на БД, если не синхронизировать их вручную.
- При загрузке графа сущностей необходимо следить за тем, чтобы обе стороны ссылались друг на друга, иначе можно получить неполные данные в памяти.
- При сериализации в JSON двунаправленные связи могут вызывать **бесконечную рекурсию**, которую нужно обрывать с помощью аннотаций (`@JsonIgnore`, `@JsonManagedReference`/`@JsonBackReference` и т.п.).


### 25. Как избежать бесконечной рекурсии при сериализации Entity

При сериализации сущностей с двунаправленными связями (например, `User` ↔ `Order`) в JSON может возникнуть бесконечный цикл: `User` сериализует список `orders`, каждый `Order` сериализует своего `user`, который снова сериализует `orders` и т.д.

Способы решения:
- **`@JsonIgnore`**: исключить одну из сторон связи из сериализации (обычно обратную сторону).
- **`@JsonManagedReference` / `@JsonBackReference`**: указать Jackson, какая сторона является «родительской» (сериализуется), а какая — «дочерней» (пропускается).
- **`@JsonIdentityInfo`**: использовать идентификатор объекта для предотвращения повторной сериализации того же объекта в рамках одного графа.
- **DTO-проекции**: возвращать из контроллера не сущности, а специальные DTO, не содержащие циклических ссылок.


### 26. Что такое JPQL и чем он отличается от SQL

**JPQL (Java Persistence Query Language)** — это объектно-ориентированный язык запросов, определённый в спецификации JPA. Он работает не с таблицами и колонками БД, а с **сущностями и их полями**. JPQL-запросы транслируются провайдером (Hibernate) в SQL с учётом маппинга.

Отличия от SQL:
- **Объекты вместо таблиц**: `SELECT u FROM User u` вместо `SELECT * FROM users`.
- **Поля вместо колонок**: `u.name` вместо `user_name`.
- **Полиморфизм**: JPQL может запрашивать сущности в иерархии наследования.
- **Переносимость**: JPQL не зависит от конкретной СУБД, так как провайдер генерирует диалект-специфичный SQL.


### 27. Что такое Criteria API и когда его использовать

**Criteria API** — это программный API для построения запросов к сущностям JPA с использованием Java-кода (вместо строк JPQL). Он позволяет строить запросы **динамически**, с типовой безопасностью на уровне компиляции (при использовании метамодели).

Когда использовать:
- Когда структура запроса (фильтры, сортировка, проекция) **меняется во время выполнения** в зависимости от входных параметров (например, сложный поиск с множеством необязательных фильтров).
- Когда нужна **типовая безопасность** и защита от опечаток в именах полей.

Для простых, статических запросов JPQL обычно предпочтительнее из-за читаемости.


### 28. Как использовать JOIN FETCH для решения проблемы N+1

`JOIN FETCH` — это конструкция в JPQL, которая указывает Hibernate загрузить связанную сущность или коллекцию **в том же SQL-запросе** с помощью `JOIN`, вместо выполнения отдельных запросов для каждой ассоциации.

Пример:
```java
@Query("SELECT u FROM User u JOIN FETCH u.orders WHERE u.id = :id")
User findUserWithOrders(@Param("id") Long id);
```
Этот запрос загрузит пользователя и все его заказы одним SQL-запросом (с `LEFT JOIN`), полностью устраняя проблему N+1 для данной ассоциации. Для нескольких коллекций одновременно `JOIN FETCH` может привести к декартову произведению, поэтому нужно использовать осторожно.


### 29. Что такое projection в JPA

**Projection (проекция)** — это способ выбрать из запроса не целые сущности, а **только определённый набор полей** (или вычисляемые значения). Это позволяет:
- Уменьшить объём передаваемых из БД данных.
- Избежать загрузки ненужных ассоциаций и связанных с ними проблем (N+1, LazyInitializationException).
- Повысить производительность read-only запросов.

Виды проекций:
- **Выбор отдельных полей** в JPQL: `SELECT u.name, u.email FROM User u`.
- **Конструкторные выражения**: `SELECT new com.example.UserDto(u.name, u.email) FROM User u`.
- **Интерфейсные проекции** (в Spring Data JPA): интерфейс с геттерами для нужных полей.


### 30. Какие типы наследования поддерживает JPA

JPA поддерживает три стратегии наследования, которые задаются аннотацией `@Inheritance(strategy = ...)`:

- **`SINGLE_TABLE`**: вся иерархия классов отображается в **одну таблицу** со столбцом-дискриминатором, определяющим тип сущности. Плюс: быстрые запросы без JOIN. Минус: много NULL-колонок для полей подклассов.
- **`JOINED`**: каждый класс иерархии имеет **свою таблицу**; общие поля хранятся в родительской таблице, специфичные — в таблицах подклассов. Для загрузки подкласса выполняется `JOIN`. Плюс: нормализованная схема. Минус: более сложные и медленные запросы.
- **`TABLE_PER_CLASS`**: для каждого **конкретного** класса создаётся отдельная таблица, содержащая все его поля (включая унаследованные). Плюс: нет NULL-колонок. Минус: полиморфные запросы требуют `UNION` всех таблиц, что может быть неэффективно.
