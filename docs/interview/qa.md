# Тестирование и автотестирование (Middle/Middle+ QA)


### 1. Что такое QA и чем он отличается от разработки

QA (Quality Assurance) — процесс обеспечения качества продукта: тестирование, анализ дефектов, предотвращение регрессий.

- **QA-инженер** — проверяет, что продукт работает как ожидалось, находит баги, пишет тест-кейсы.
- **Разработчик** — пишет код, который QA проверяет.
- Middle/Middle+ QA — понимает архитектуру, пишет автотесты, работает с CI/CD, может читать код (Java/Python), знает БД, сети, API.

Ключевые навыки Middle QA:
- Функциональное тестирование (API, UI, интеграционное).
- Автотестирование (Pytest, JUnit, Selenium, Playwright).
- Работа с БД (SQL-запросы, проверка данных).
- Понимание архитектуры (микросервисы, очереди, кэш).
- Нагрузочное тестирование (JMeter, Gatling, k6).
- CI/CD (Git, Jenkins, GitHub Actions).


### 2. Какие виды тестирования существуют

По уровню:
- **Юнит-тесты** — проверка отдельных функций/методов (разработчик).
- **Интеграционные тесты** — проверка взаимодействия компонентов (API + БД, сервис + брокер).
- **E2E-тесты** — проверка полного сценария (UI → API → БД).
- **Нагрузочные тесты** — проверка производительности под нагрузкой.

По типу:
- **Функциональное** — проверка бизнес-логики (что делает).
- **Нефункциональное** — производительность, надёжность, безопасность (как делает).
- **Регрессионное** — проверка, что старые функции не сломались.
- **Smoke-тесты** — быстрая проверка ключевых функций после деплоя.
- **Sanity-тесты** — точечная проверка конкретной функции после фикса.

По уровню абстракции:
- **Black-box** — тестируем без знания кода (требования, API).
- **White-box** — тестируем зная код (покрытие, ветвления).
- **Gray-box** — частичное знание (API + логика).


### 3. Что такое пирамида тестирования и почему она важна

Пирамида тестирования — распределение тестов по уровням:

- **База (юнит-тесты)** — 70%: быстрые, дешёвые, много.
- **Средина (интеграционные)** — 20%: средние по скорости, проверяют взаимодействия.
- **Вершина (E2E)** — 10%: медленные, дорогие, мало.

Почему важна:
- **Экономика** — юнит-тесты дешевле и быстрее.
- **Надёжность** — много юнит-тестов = высокий уровень покрытия.
- **Баланс** — не только юниты, но и интеграционные/E2E для проверки сценариев.

Антипаттерн "айсберг":
- Мало юнит-тестов, много E2E.
- Дорого, медленно, хрупко.
- QA Middle+ должен указывать на это и предлагать баланс.

- **Gatling** — нагрузочное тестирование.

- **Requests** — HTTP-клиент.
- **Selenium** — UI-тесты (браузер).
- **Playwright** — UI-тесты (современный, быстрее Selenium).

Кросс-платформенные:

- **Sentry / Grafana** — мониторинг в production.


### 5. Как написать хороший тест-кейс

Структура тест-кейса:
- **ID** — уникальный идентификатор (TC-1234).
- **Название** — что тестируем (например, "Создание заказа с валидным email").
- **Предусловия** — что должно быть выполнено до теста (пользователь авторизован).
- **Шаги** — последовательность действий (1. Открыть страницу. 2. Заполнить форму. 3. Нажать "Оплатить").
- **Ожидаемый результат** — что должно произойти (заказ создан, email отправлен).
- **Фактический результат** — что произошло (заполняется при тестировании).
- **Статус** — Pass/Fail/Blocked.

Пример:
```
ID: TC-1234
Название: Создание заказа с валидными данными
Предусловия: Пользователь авторизован, в корзине есть товар
Шаги:
  1. Перейти на страницу оформления
  2. Заполнить адрес доставки
  3. Выбрать способ оплаты
  4. Нажать кнопку "Оплатить"
Ожидаемый результат:
  - Заказ создан (статус "Оплачен")
  - Email с подтверждением отправлен
  - Товар списан из корзины
Фактический результат: (заполняется)
Статус: (Pass/Fail)
```

Критерии хорошего тест-кейса:
- **Понятный** — любой QA может выполнить.
- **Детерминированный** — одинаковый результат при повторном выполнении.
- **Покрытые краевые случаи** — не только happy path.
- **Связан с требованиями** — каждый кейс отражает требование.


### 6. Что такое автотестирование и когда оно оправдано

Автотестирование — написание скриптов, которые автоматически проверяют продукт.

Когда оправдано:
- **Регрессия** — после каждого изменения нужно проверять старые функции.
- **Повторяемые сценарии** — если сценарий выполняется часто (например, smoke-тесты перед деплоем).
- **Критичные сценарии** — если ошибка в сценарии = большой ущерб (оплата, авторизация).
- **Нагрузка** — ручное нагрузочное тестирование невозможно.

Когда не оправдано:
- **Одноразовые проверки** — если сценарий выполняется один раз.
- **Сложный UI** — если UI часто меняется, автотесты будут хрупкими.
- **Креативные сценарии** — эвристическое тестирование (исследование) сложно автоматизировать.

Middle+ QA должен уметь:
- Определить, какие сценарии автоматизировать.
- Написать автотесты (Python/Java).
- Поддерживать их (обновлять при изменениях).
- Интегрировать в CI/CD.


### 7. Как тестировать REST API

Ключевые аспекты:
- **Статус коды** — 200, 201, 204, 400, 401, 403, 404, 409, 422, 500.
- **Тело ответа** — структура JSON, обязательные поля.
- **Заголовки** — Content-Type, Authorization, CORS.
- **Идемпотентность** — PUT/DELETE должны быть идемпотентны.
- **Валидация** — невалидные данные → 400/422.
- **Автентификация** — токен, JWT, OAuth2.
- **Авторизация** — роли, права доступа.

Инструменты:
- **Postman / Insomnia** — ручное тестирование.
- **RestAssured (Java)** — автотесты API.
- **Requests (Python)** — автотесты API.
- **WireMock** — мок внешние API.

Пример (Python, Pytest):
```python
import requests

def test_create_order():
    response = requests.post(
        "http://localhost:8080/api/orders",
        json={"product_id": 123, "quantity": 2},
        headers={"Authorization": "Bearer token"}
    )
    assert response.status_code == 201
    data = response.json()
    assert data["status"] == "created"
    assert data["total_price"] == 2 * 100
```


### 8. Как тестировать микросервисную архитектуру

Особенности:
- **Множество сервисов** — нужно тестировать взаимодействия.
- **Асинхронность** — сообщения в очередях (Kafka, RabbitMQ).
- **Распределённые транзакции** — Saga, eventual consistency.
- **Наблюдаемость** — trace-id для отладки.

Подходы:
- **Contract Testing** — проверка контрактов между сервисами (Pact).
- **Чёрный ящик** — тестируем публичный API (не внутренние детали).
- **Интеграционные тесты** — сервис + реальная БД/очередь (Testcontainers).
- **Нагрузочные тесты** — проверка производительности под нагрузкой.

Инструменты:
- **Testcontainers** — реальная БД/брокер в Docker.
- **WireMock** — мок соседние сервисы.
- **Gatling / k6** — нагрузочное тестирование.
- **Jaeger / Zipkin** — трассировка.


### 9. Что такое нагрузочное тестирование и как его проводить

Цели:
- **Производительность** — сколько запросов/сек выдерживает система.
- **Пропускная способность** — максимальная нагрузка.
- **Надёжность** — как система ведёт себя под нагрузкой.
- **Масштабируемость** — как растёт производительность при увеличении ресурсов.

Типы:
- **Load test** — штатная нагрузка (нормальный трафик).
- **Stress test** — превышение штатной нагрузки (поиск предела).
- **Spike test** — резкий всплеск нагрузки.
- **Soak test** — длительная нагрузка (поиск memory leak).

Метрики:
- **Throughput** — запросы/сек.
- **Latency** — p50, p95, p99 (время отклика).
- **Error rate** — доля ошибок.
- **CPU / Memory / Disk I/O** — загрузка ресурсов.

Инструменты:
- **JMeter** — графический UI, Java.
- **Gatling** — код на Scala, высокопроизводительный.
- **k6** — код на JavaScript, современный.
- **Locust** — код на Python.

Пример (k6):
```javascript
import http from 'k6/http';
import { check } from 'k6';

export const options = {
  vus: 100, // 100 виртуальных пользователей
  duration: '5m',
};

export default function () {
  const res = http.get('http://localhost:8080/api/products');
  check(res, {
    'status is 200': (r) => r.status === 200,
    'latency < 500ms': (r) => r.timings.duration < 500,
  });
}
```


### 10. Как тестировать БД и данные

Задачи:
- **Проверка данных** — корректность записей.
- **Связи** — FK, целостность.
- **Транзакции** — ACID (атомарность, консистентность, изоляция, долговечность).
- **Производительность** — время запросов, индексы.

Подходы:
- **SQL-запросы** — проверка данных после операций.
- **Тестирование миграций** — Flyway/Liquibase.
- **Проверка целостности** — FK, constraints.
- **Нагрузочные тесты** — производительность БД.

Пример (Python, Testcontainers):
```python
import pytest
from testcontainers.postgres import PostgresContainer
from sqlalchemy import create_engine, text

@pytest.fixture
def db():
    with PostgresContainer("postgres:15") as postgres:
        engine = create_engine(postgres.get_connection_url())
        yield engine

def test_create_user(db):
    with db.connect() as conn:
        conn.execute(text("INSERT INTO users (email) VALUES ('test@example.com')"))
        result = conn.execute(text("SELECT COUNT(*) FROM users"))
        assert result.fetchone()[0] == 1
```


### 11. Что такое CI/CD и как QA в нём участвует

CI (Continuous Integration) — автоматическая сборка и тестирование при каждом изменении кода.

CD (Continuous Delivery/Deployment) — автоматический деплой в production.

Роль QA:
- **Написать автотесты** — которые будут запускаться в CI.
- **Настроить pipeline** — Jenkins, GitHub Actions, GitLab CI.
- **Smoke-тесты** — быстрые проверки перед деплоем.
- **Регрессионные тесты** — полный прогон перед релизом.
- **Мониторинг** — Sentry, Grafana после деплоя.

Пример (GitHub Actions):
```yaml
name: CI Pipeline
on: [push]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run unit tests
        run: pytest tests/unit/
      - name: Run integration tests
        run: pytest tests/integration/
      - name: Run E2E tests
        run: pytest tests/e2e/
```


### 12. Как написать баг-репорт

Структура:
- **ID** — уникальный (BUG-1234).
- **Название** — краткое описание (например, "Оплата не проходит с картой Visa").
- **Приоритет** — Critical / High / Medium / Low.
- **Сeverity** — Blocker / Major / Minor / Trivial.
- **Окружение** — версия, браузер, ОС, устройство.
- **Шаги воспроизведения** — 1. 2. 3.
- **Ожидаемый результат** — что должно произойти.
- **Фактический результат** — что происходит.
- **Вложения** — скриншоты, логи, видео.

Пример:
```
ID: BUG-1234
Название: Оплата не проходит с картой Visa
Приоритет: Critical
Severity: Blocker
Окружение: v2.1.0, Chrome 120, Windows 11
Шаги воспроизведения:
  1. Добавить товар в корзину
  2. Перейти к оплате
  3. Выбрать карту Visa
  4. Нажать "Оплатить"
Ожидаемый результат: Оплата прошла, заказ создан
Фактический результат: Ошибка "Технические работы", заказ не создан
Вложения: screenshot.png, logs.txt
```


### 13. Что такое регрессионное тестирование и как его оптимизировать

Регрессионное тестирование — проверка, что старые функции не сломались после изменений.

Оптимизация:
- **Автотесты** — автоматизация регрессии (Pytest, JUnit).
- **Smoke-тесты** — быстрая проверка ключевых функций.
- **Тест-отбор** — выборка тестов на основе рисков (risk-based testing).
- **Параллельное выполнение** — запуск тестов параллельно (pytest-xdist).
- **CI/CD** — автоматический запуск при каждом изменении.

Middle+ QA должен уметь:
- Определить, какие сценарии критичны для регрессии.
- Автоматизировать их.
- Интегрировать в CI/CD.
- Анализировать результаты и отчёты.


### 14. Как тестировать безопасность (Security Testing)

Аспекты:
- **Инъекции** — SQL, XSS, CSRF.
- **Аутентификация** — weak passwords, brute force.
- **Авторизация** — IDOR (Insecure Direct Object Reference).
- **Данные** — шифрование, хранение.
- **API** — rate limiting, validation.

Инструменты:
- **OWASP ZAP** — сканер уязвимостей.
- **Burp Suite** — ручное тестирование.
- **Nmap** — сканирование портов.
- **SQLMap** — SQL-инъекции.

Middle+ QA должен знать:
- OWASP Top 10.
- Базовые уязвимости.
- Как проводить пентест (или приглашать специалиста).


### 15. Какие метрики качества ты используешь

- **Покрытие тестами** — процент кода, покрытого тестами (JaCoCo, Coverage.py).
- **Количество багов** — открытые/закрытые, по приоритету.
- **Время на регрессию** — сколько времени занимает прогон регрессии.
- **Детектируемость** — сколько багов найдено до production.
- **MTTR (Mean Time To Recovery)** — среднее время восстановления после сбоя.
- **Error rate** — доля ошибок в production.

Middle+ QA должен уметь:
- Собирать эти метрики.
- Анализировать тренды.
- Предлагать улучшения (например, больше автотестов).


### 16. Как подготовиться к собеседованию на Middle QA

Ключевые темы:
- **Функциональное тестирование** — виды, уровни, подходы.
- **Автотестирование** — Python/Java, фреймворки.
- **API-тестирование** — REST, GraphQL, гRPC.
- **Базы данных** — SQL, Testcontainers.
- **Архитектура** — микросервисы, очереди, кэш.
- **CI/CD** — pipeline, автотесты.
- **Нагрузочное тестирование** — JMeter, Gatling, k6.
- **Безопасность** — OWASP, базовые уязвимости.

Что проверить:
- Понимание архитектуры (как работает система).
- Умение читать код (Java/Python).
- Опыт с инструментами (Pytest, JUnit, Testcontainers).
- Понимание CI/CD.
- Умение писать баг-репорты.

**Итог:**
- Middle QA — не только находит баги, но и предотвращает их.
- Умеет писать автотесты, работает с CI/CD.
- Понимает архитектуру, БД, сети.
- Готовится к собеседованию по всем аспектам (функциональное, автотестирование, API, БД, архитектура, CI/CD, нагрузочное, безопасность).
