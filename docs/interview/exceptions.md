# Исключения

### 1. В чём разница между checked и unchecked exceptions

- **Checked (проверяемые)** исключения — это наследники `Exception`, но **не** `RuntimeException`. Компилятор **требует** их обработки: метод должен либо объявить их в `throws`, либо обработать в `try-catch`. Они представляют **ожидаемые** проблемы внешней среды (файл не найден, сеть недоступна).
- **Unchecked (непроверяемые)** исключения — это наследники `RuntimeException` (и `Error`). Компилятор **не требует** их обработки. Они представляют **программные ошибки** (NPE, `IndexOutOfBounds`, `IllegalArgument`) или непредвиденные сбои.


### 2. Что такое checked exception и когда его использовать

Checked exception — исключение, которое компилятор обязывает обработать или пробросить. Используется, когда **вызывающий код может и должен** что-то сделать для восстановления: например, `IOException` при работе с файлами (можно повторить попытку, запросить другой путь, показать сообщение пользователю). Ключевой критерий: это **ожидаемая** ситуация, которая является частью контракта метода.


### 3. Что такое unchecked exception (Runtime Exception)

Unchecked exception — наследник `RuntimeException`, который компилятор не обязывает обрабатывать. Обычно сигнализирует о **программных ошибках** (нарушение инвариантов, неверные аргументы, NPE), которые не должны происходить в корректно написанной программе. Обрабатывать их на месте обычно не нужно — нужно **исправлять причину** в коде.


### 4. Какие исключения нужно обрабатывать обязательно

Обязательно обрабатывать (или объявлять в `throws`) только **checked exceptions**. Unchecked (`RuntimeException`, `Error`) обрабатывать не обязательно — это вопрос дизайна и здравого смысла, но не требование компилятора.


### 5. Что находится в вершине иерархии исключений

В вершине иерархии находится класс **`java.lang.Throwable`**. От него наследуются два основных поддерева: `Error` и `Exception`. Всё, что можно «бросить» (`throw`) или поймать (`catch`), является наследником `Throwable`.


### 6. Что такое Throwable

`Throwable` — корневой класс для всех ошибок и исключений в Java. Он содержит:
- **`message`** — текстовое описание.
- **`cause`** — причина (другое `Throwable`, из-за которого возникло это).
- **`stackTrace`** — массив `StackTraceElement` с информацией о стеке вызовов в момент создания.
- Методы `getMessage()`, `getCause()`, `printStackTrace()`, `addSuppressed()`, `fillInStackTrace()`.

Создавать и бросать можно только наследников `Throwable`.


### 7. В чём разница между Error и Exception

- **`Error`** — серьёзные проблемы на уровне JVM/среды, которые приложение **не должно** пытаться обработать: `OutOfMemoryError`, `StackOverflowError`, `NoClassDefFoundError`. Это фатальные сбои, после которых нормальное продолжение обычно невозможно.
- **`Exception`** — проблемы уровня приложения, которые **можно и нужно** обрабатывать. Делится на checked и unchecked. `Error` и `Exception` — параллельные ветви иерархии `Throwable`, а не родитель-потомок.


### 8. Гарантируется ли выполнение блока finally

Блок `finally` выполняется **почти всегда**: и при нормальном завершении, и при исключении, и при `return`/`break`/`continue` из `try`/`catch`. **Не выполнится** только в исключительных случаях:
- `System.exit()` — JVM завершается.
- `Runtime.getRuntime().halt()`.
- Бесконечный цикл/зависание в `try`.
- Аварийное завершение JVM (kill -9, сбой питания).
- Если поток, выполняющий `finally`, был прерван (`Thread.stop()` — устаревший и опасный).


### 9. Что такое try-with-resources

`try-with-resources` (Java 7+) — конструкция, которая **автоматически закрывает** ресурсы, объявленные в заголовке `try`, после завершения блока (нормального или из-за исключения). Ресурс должен реализовывать `AutoCloseable`. Это устраняет необходимость писать `finally` с ручным `close()` и корректно обрабатывает подавленные исключения.

```java
try (FileInputStream in = new FileInputStream("file.txt");
     BufferedReader reader = new BufferedReader(new InputStreamReader(in))) {
    // работа с reader
} // reader и in закроются автоматически
```


### 10. Какие требования к ресурсам в try-with-resources

Ресурс должен реализовывать интерфейс **`java.lang.AutoCloseable`** (или его подинтерфейс `Closeable`). Метод `close()` будет вызван автоматически. Ресурсы закрываются в **обратном порядке** от объявления. С Java 9 можно использовать в `try-with-resources` уже объявленные effectively final переменные: `try (existingResource) { ... }`.


### 11. Что такое AutoCloseable интерфейс

`AutoCloseable` (`java.lang.AutoCloseable`, Java 7) — функциональный интерфейс с единственным методом `void close() throws Exception`. Он является основой для `try-with-resources`. Любой класс, реализующий его, может быть использован как ресурс в `try-with-resources` и будет автоматически закрыт.


### 12. В чём разница между AutoCloseable и Closeable

- **`AutoCloseable`** (`java.lang`, Java 7) — более общий интерфейс, `close()` может выбрасывать `Exception`. Предназначен для любых ресурсов.
- **`Closeable`** (`java.io`, Java 5) — расширяет `AutoCloseable`, но `close()` объявлен как `throws IOException` (более узкий тип), а также требует **идемпотентности**: повторный вызов `close()` не должен причинять вреда. Используется в основном для I/O-ресурсов.

Любой `Closeable` является `AutoCloseable`, но не наоборот.


### 13. Можно ли создавать кастомные исключения

**Да**. Для этого нужно унаследоваться от `Exception` (checked) или `RuntimeException` (unchecked). Обычно определяют конструкторы, принимающие `message`, `cause` или оба, и вызывают соответствующий `super(...)`. Пример:

```java
public class OrderNotFoundException extends RuntimeException {
    public OrderNotFoundException(Long id) {
        super("Order not found: " + id);
    }
}
```


### 14. Когда стоит создавать свои исключения

- Когда нужно **семантически** отделить специфичную ошибку домена от общих (например, `InsufficientFundsException` вместо общего `RuntimeException`).
- Когда вызывающий код должен **по-разному обрабатывать** разные типы ошибок.
- Когда нужно **добавить контекст** (например, ID сущности, код ошибки), которого нет в стандартных исключениях.
- Когда ошибка является частью **публичного API** и должна быть задокументирована в контракте.

Не стоит создавать своё исключение, если подходит стандартное (`IllegalArgumentException`, `IllegalStateException`, `UnsupportedOperationException` и т.д.).


### 15. Что лучше: наследоваться от Exception или RuntimeException

Зависит от природы ошибки:
- **От `RuntimeException`** — если ошибка представляет **программную ошибку** (нарушение контракта, неверный аргумент, недопустимое состояние), которую вызывающий код не обязан обрабатывать. Это современный тренд: многие фреймворки (Spring) предпочитают unchecked-исключения, чтобы не «загрязнять» сигнатуры методов.
- **От `Exception`** — если ошибка **ожидаема** и вызывающий код **обязан** её обработать для восстановления (например, `InsufficientFundsException` в банковском API, где клиент должен решить, что делать).

Правило: если сомневаетесь — выбирайте `RuntimeException`, но убедитесь, что ошибка действительно программная, а не ожидаемая внешняя проблема.


### 16. Что такое stack trace

**Stack trace (трассировка стека)** — это снимок **стека вызовов** в момент создания исключения. Он содержит последовательность `StackTraceElement` — имя класса, имя метода, имя файла и номер строки для каждого кадра стека, от места создания исключения до точки его перехвата (или до `main`). Это главный инструмент для диагностики: он показывает, **где именно** произошла ошибка и **какой путь** привёл к ней.


### 17. Что делает метод printStackTrace()

`printStackTrace()` выводит stack trace исключения в **стандартный поток ошибок** (`System.err`) в читаемом текстовом формате. У него есть перегрузки для `PrintStream` и `PrintWriter`, позволяющие направить вывод в файл или логгер. В продакшене использовать его напрямую не рекомендуется — лучше логировать исключение через логгер (SLF4J, Logback), который добавит контекст, уровни и метаданные.


### 18. Как правильно логировать исключения

- Использовать **логгер** (SLF4J + Logback/Log4j2), а не `printStackTrace()`.
- Передавать **сам объект исключения** последним аргументом, чтобы логгер записал полный stack trace: `log.error("Failed to process order {}", orderId, e)`.
- **Не** использовать конкатенацию строк для сообщения — использовать параметризованные сообщения.
- Логировать на **правильном уровне**: `error` для ошибок, требующих внимания; `warn` для ожидаемых проблем; `debug` для диагностики.
- Не логировать одно и то же исключение на нескольких уровнях (двойное логирование).
- Включать **контекст** (ID запроса, пользователя, входные параметры), но **не логировать** конфиденциальные данные (пароли, токены, PII).
- Для проверяемых исключений, которые обрабатываются, логировать только при необходимости.


### 19. Что такое оборачивание (wrapping) исключений

**Wrapping (оборачивание)** — это перехват исключения и бросание нового исключения, содержащего оригинал в качестве **cause**. Это позволяет:
- Добавить **контекст** («не удалось сохранить заказ»), не теряя исходную причину.
- **Сменить тип** исключения (например, checked `SQLException` → unchecked `DataAccessException`), чтобы не «протекать» деталям инфраструктуры в бизнес-слой.
- Сохранить **stack trace** оригинала через `initCause()` или конструктор с `cause`.

Пример: `throw new OrderProcessingException("Failed to save order " + id, e);`


### 20. Почему не стоит глотать исключения (catch empty)

Пустой `catch` **скрывает проблему**: программа продолжает работу в некорректном состоянии, ошибка не логируется, и её причина остаётся неизвестной. Это приводит к:
- **Трудноуловимым багам**: данные могут быть в несогласованном состоянии, а симптом проявится далеко от места ошибки.
- **Потере диагностики**: stack trace и причина теряются навсегда.
- **Нарушению контракта**: вызывающий код думает, что операция успешна.

Если исключение действительно можно игнорировать, это нужно **явно задокументировать** комментарием и хотя бы залогировать на уровне `debug`/`warn`.


### 21. Что делает ключевое слово throws

`throws` в сигнатуре метода **объявляет**, какие checked-исключения метод может пробросить. Это часть контракта: вызывающий код обязан либо обработать их, либо пробросить дальше. `throws` не обрабатывает исключение и не влияет на unchecked — их можно объявлять, но компилятор этого не требует.


### 22. Можно ли пробросить checked exception из метода без throws

**Нет, напрямую нельзя**. Компилятор потребует либо объявить его в `throws`, либо обработать. Однако существуют обходные пути, нарушающие проверку компилятора:
- **«Sneaky throw»** через generic-хак (`@SuppressWarnings("unchecked")` и приведение `Throwable` к `RuntimeException`) — исключение пробрасывается, но компилятор «не видит» checked-типа.
- **Рефлексия** и `Unsafe.throwException()`.
- **Лямбды/обёртки**, скрывающие checked-исключение внутри unchecked.

Все эти приёмы считаются хаками и должны использоваться крайне осторожно, так как нарушают контракт метода и сбивают с толку вызывающий код.


### 23. Что произойдёт, если в блоке finally тоже возникнет исключение

Если в `finally` возникает исключение, оно **заменяет** (подавляет) исключение, возникшее в `try` или `catch`. Исходное исключение **теряется**, и вызывающий код увидит только исключение из `finally`. Это классическая ловушка: например, `finally` вызывает `close()`, который бросает `IOException`, и настоящее исключение из `try` пропадает.

Решения:
- Использовать **`try-with-resources`**, который корректно обрабатывает подавленные исключения (`addSuppressed()`).
- В `finally` оборачивать потенциально опасный код в собственный `try-catch`, чтобы не подавить основное исключение.
- Использовать `Throwable.addSuppressed()` вручную, если пишете свою логику закрытия ресурсов.


### 24. Что такое suppressed exceptions

**Suppressed exceptions (подавленные исключения)** — это механизм (Java 7+), позволяющий прикрепить к основному исключению **дополнительные** исключения, возникшие при обработке (например, при закрытии ресурсов в `try-with-resources`), не теряя их. Они доступны через `Throwable.getSuppressed()`. `try-with-resources` автоматически добавляет исключения из `close()` как suppressed к основному исключению из `try`, если `close()` тоже бросил исключение. Это решает проблему потери исключений из `finally`.


### 25. Можно ли несколько catch блоков для одного try

**Да**. Один `try` может иметь несколько `catch`-блоков для разных типов исключений. JVM выбирает **первый подходящий** (наиболее специфичный) `catch` сверху вниз. Важно располагать `catch`-блоки от **более конкретных** типов к **более общим**, иначе компилятор выдаст ошибку о недостижимом коде (например, `catch (Exception e)` перед `catch (IOException e)` — ошибка).


### 26. Что такое multi-catch (catching multiple exceptions)

**Multi-catch** (Java 7+) — синтаксис, позволяющий обработать **несколько типов исключений одним `catch`-блоком**:

```java
try {
    // ...
} catch (IOException | SQLException e) {
    log.error("Failed", e);
}
```

Переменная `e` в таком блоке является **effectively final** (нельзя переприсвоить) и имеет тип **наименьшего общего предка** перечисленных типов (в примере — `Exception`). Это уменьшает дублирование кода.


### 27. В каком порядке располагать catch блоки

От **самых конкретных** (подклассов) к **самым общим** (суперклассам). Например:

```java
try { ... }
catch (FileNotFoundException e) { ... }  // конкретный
catch (IOException e) { ... }            // общий
catch (Exception e) { ... }              // самый общий
```

Если поставить общий `catch` раньше, компилятор сообщит, что последующие блоки **недостижимы** (unreachable code), так как общий тип перехватит всё.


### 28. Можно ли повторно бросить исключение

**Да**. В `catch`-блоке можно выполнить `throw e;` (или `throw new ...` с оборачиванием). Повторный бросок **того же** исключения сохраняет его stack trace (если не вызывать `fillInStackTrace()`). Это полезно для логирования и проброса наверх. С Java 7 работает **precise rethrow**: если в `catch` объявлен тип `Exception`, но компилятор видит, что фактически могут быть только `IOException` и `SQLException`, он позволяет объявить в `throws` только эти конкретные типы.


### 29. Что такое exception chaining

**Exception chaining (цепочка исключений)** — это практика сохранения **причины** (`cause`) исключения при оборачивании. Новое исключение создаётся с передачей оригинала в конструктор (`new MyException("msg", cause)`) или через `initCause(cause)`. Это позволяет при диагностике пройти по цепочке `getCause()` до **корневой причины** (`root cause`), не теряя информацию о каждом уровне. `printStackTrace()` и логгеры автоматически отображают всю цепочку («Caused by: ...»).
