# Records и Дженерики


### 1. Что такое Record в Java и с какой версии они доступны?

**Record** — это специальный тип класса в Java, предназначенный для хранения неизменяемых данных. Он был введен в **Java 16** (после preview в Java 14 и 15) в рамках проекта Amber.

Основная цель Record — предоставить лаконичный синтаксис для классов, которые являются простыми "контейнерами данных" («поля, только поля и ничего, кроме полей»), и автоматически сгенерировать для них весь необходимый шаблонный код.

Для каждого компонента, объявленного в заголовке записи, компилятор автоматически создает:
- `private final` поле.
- Метод доступа (геттер), имя которого совпадает с именем компонента.
- Участие в методах `equals()`, `hashCode()` и `toString()`.
- Канонический конструктор, принимающий все компоненты.

### 2. В чём основные отличия Record от обычного класса?

Ключевые отличия:
- **Неизменяемость:** Все поля Record являются `final`. В обычном классе поля могут быть изменяемыми.
- **Наследование:** Record неявно является `final` и не может быть расширен. Также Record не может наследовать другой класс (кроме неявного `java.lang.Record`).
- **Связь состояния и API:** В Record имена полей, параметров конструктора и методов доступа строго связаны. В обычном классе этой связи может не быть.
- **Автоматическая генерация кода:** Record автоматически генерирует конструктор, геттеры, `equals()`, `hashCode()` и `toString()`, что избавляет от boilerplate-кода.
- **Отсутствие сеттеров:** Поскольку Record неизменяем, методы-сеттеры не генерируются.

### 3. Можно ли наследоваться от Record или наследовать Record от другого класса?

Нет. Все классы Record являются неявно `final`, поэтому от них нельзя наследоваться. Также Record не может явно наследовать другой класс, так как все они уже наследуют `java.lang.Record`.

### 4. Можно ли добавлять дополнительные методы в Record?

Да, можно. В тело Record можно добавлять обычные, статические методы и константы. Это позволяет включать в запись бизнес-логику, связанную с ее данными.

### 5. Какие методы автоматически генерируются для Record?

Для Record автоматически генерируются:
- Канонический конструктор (со всеми компонентами).
- Методы доступа для каждого компонента (геттеры).
- `equals()` и `hashCode()`.
- `toString()`.

### 6. Можно ли переопределить конструктор в Record?

Да, можно. Хотя канонический конструктор генерируется автоматически, вы можете объявить его явно, чтобы добавить логику валидации или нормализации данных. Кроме того, можно создавать дополнительные конструкторы с другим набором параметров, которые должны делегировать вызов каноническому конструктору через `this(...)`.

### 7. Что такое компактный конструктор (compact constructor) в Record?

Это специальная форма канонического конструктора, которая позволяет избежать повторного объявления параметров и явного присваивания полей. В компактном конструкторе вы пишете только логику проверки или нормализации, а компилятор автоматически добавляет неявные параметры и код присваивания `this.x = x` в конце.

Пример:
```java
public record Point(int x, int y) {
    public Point { // Компактный конструктор
        if (x < 0 || y < 0) {
            throw new IllegalArgumentException("Coordinates must be non-negative");
        }
        // Присваивание this.x = x и this.y = y произойдет автоматически
    }
}
```

### 8. Можно ли объявлять статические поля и методы в Record?

Да, можно. В Record разрешено объявлять статические поля, статические методы и статические инициализаторы. Это полезно для создания констант или фабричных методов.

### 9. Являются ли поля Record финальными?

Да, все поля, соответствующие компонентам Record, являются неявно `private final`.

### 10. Можно ли использовать Record как ключ в HashMap?

Да, и это одна из рекомендуемых практик. Поскольку Record автоматически генерирует корректные и согласованные реализации `equals()` и `hashCode()`, основанные на всех его полях, он идеально подходит для использования в качестве ключа в `HashMap` или элемента в `HashSet`.

### 11. Что такое дженерики (Generics) в Java?

Дженерики — это механизм параметризованных типов, который позволяет создавать классы, интерфейсы и методы, работающие с различными типами данных, обеспечивая при этом строгую проверку типов на этапе компиляции. Это позволяет писать более безопасный и переиспользуемый код, избегая явных приведений типов и ошибок `ClassCastException` во время выполнения.

### 12. В чём преимущества использования дженериков?

- **Безопасность типов:** Ошибки несоответствия типов выявляются на этапе компиляции, а не во время выполнения.
- **Устранение приведений типов:** Вы можете использовать типизированные объекты без явного приведения, что делает код чище и безопаснее.
- **Переиспользуемый код:** Один обобщенный алгоритм или структура данных могут работать с разными типами.
- **Читаемость:** Код становится более понятным, так как тип элементов коллекции или параметр метода явно указан в сигнатуре.

### 13. Что такое type erasure (стирание типов)?

Стирание типов — это процесс, с помощью которого компилятор Java реализует дженерики. Во время компиляции вся информация о параметрах типа стирается. Параметры типа заменяются их верхними границами (или `Object`, если граница не указана). Это сделано для обратной совместимости с кодом, написанным до появления дженериков, и для того, чтобы дженерики не создавали новых классов во время выполнения, не добавляя накладных расходов.

### 14. Можно ли создать массив дженерик-типа?

Создать массив параметризованного типа напрямую (например, `new List<String>[10]`) нельзя — это вызовет ошибку компиляции. Это связано со стиранием типов: во время выполнения массив не будет знать о своем параметре типа, что может привести к нарушению безопасности типов. В качестве обходного пути можно использовать массив сырого типа с приведением (`(List<String>[]) new List<?>[10]`), но это приведет к предупреждению о непроверяемом приведении.

### 15. Что такое bounded type parameters?

Ограниченные параметры типа позволяют указать, что параметр типа должен быть подтипом определенного класса или реализовывать определенный интерфейс. Это задается с помощью ключевого слова `extends`.

Пример: `<T extends Comparable<T>>` означает, что тип `T` должен реализовывать интерфейс `Comparable`.

### 16. В чём разница между `<? extends T>` и `<? super T>`?

- `<? extends T>` (Upper Bounded Wildcard): Означает "любой тип, который является `T` или его подтипом". Такой список можно только читать (Producer). Вы не можете добавить в него элементы (кроме `null`), так как компилятор не знает точного типа.
- `<? super T>` (Lower Bounded Wildcard): Означает "любой тип, который является `T` или его супертипом". В такой список можно добавлять элементы типа `T` (Consumer). Читать из него можно только как `Object`.

### 17. Что такое PECS (Producer Extends Consumer Super)?

PECS — это мнемоническое правило для использования wildcard-типов:
- **Producer Extends:** Если параметризованный тип является **производителем** (вы только читаете из него данные), используйте `<? extends T>`.
- **Consumer Super:** Если параметризованный тип является **потребителем** (вы только записываете в него данные), используйте `<? super T>`.

### 18. Можно ли использовать примитивные типы как параметры дженериков?

Нет, параметры типа в дженериках могут быть только ссылочными типами. Для использования примитивов (например, `int`, `double`) необходимо применять их классы-обертки (`Integer`, `Double` и т.д.). Автоматическая упаковка (autoboxing) происходит автоматически.

### 19. Что такое raw types и почему их следует избегать?

Raw type (сырой тип) — это использование обобщенного типа без указания параметров типа (например, `List` вместо `List<String>`). Это следует избегать, потому что при использовании raw types теряется вся информация о типе, и компилятор не может обеспечить проверку безопасности типов. Это может привести к ошибкам `ClassCastException` во время выполнения, которые было бы легко предотвратить на этапе компиляции.

### 20. Что произойдёт при попытке создать экземпляр дженерик-типа через `new T()`?

Напрямую создать экземпляр параметра типа через `new T()` нельзя, так как из-за стирания типов компилятор не знает, какой именно класс нужно инстанцировать. Это приведет к ошибке компиляции.

### 21. В чём разница между `List<?>` и `List<Object>`?

- `List<Object>` — это список, который может содержать элементы типа `Object` (то есть любые объекты). В него можно добавлять любые объекты. Однако `List<String>` **не** является подтипом `List<Object>`.
- `List<?>` — это список **неизвестного типа**. `List<String>`, `List<Integer>` и любой другой `List` являются его подтипами. Поэтому `List<?>` удобно использовать в параметрах методов, которые должны принимать списки любого типа. Однако в `List<?>` можно добавлять только `null`, так как компилятор не знает фактического типа списка.

### 22. Можно ли перегружать методы, отличающиеся только дженерик-параметрами?

Нет. Из-за стирания типов методы, которые отличаются только параметрами типа, после стирания будут иметь одинаковую сигнатуру. Например, методы `void method(List<String> list)` и `void method(List<Integer> list)` после стирания станут `void method(List list)`, что вызовет ошибку компиляции, так как это недопустимая перегрузка.

### 23. Что такое recursive type bound?

Рекурсивная граница типа — это параметр типа, который ограничен выражением, включающим его самого. Это позволяет выразить отношения, где тип сравнивается или связан с самим собой. Классический пример — метод для поиска максимума в списке, элементы которого можно сравнивать между собой:
```java
public static <T extends Comparable<T>> T max(List<T> list) { ... }
```
Здесь `T` должен реализовывать `Comparable<T>`, то есть уметь сравнивать себя с другими объектами того же типа `T`. Это гарантирует, что мы не сможем случайно сравнить яблоко с апельсином в рамках этого метода.

### 24. Как работают дженерики с наследованием (является ли `List<String>` подтипом `List<Object>`)?

Нет, `List<String>` **не** является подтипом `List<Object>`. Несмотря на то, что `String` является подтипом `Object`, для параметризованных типов это правило не работает. Это сделано для сохранения безопасности типов. Если бы `List<String>` был подтипом `List<Object>`, то через ссылку на `List<Object>` можно было бы добавить в список `Integer`, что нарушило бы его изначальный тип.

### 25. Что такое bridge methods и зачем они нужны?

Bridge-методы — это синтетические методы, которые генерируются компилятором для сохранения полиморфизма после стирания типов. Они необходимы, когда класс расширяет параметризованный класс или реализует параметризованный интерфейс с конкретным типом.

Например, если у вас есть `class Node<T> { void setData(T data) {...} }` и `class MyNode extends Node<Integer> { void setData(Integer data) {...} }`. После стирания типов метод `Node.setData` станет `setData(Object)`, а `MyNode.setData` останется `setData(Integer)`. Без bridge-метода вызов `setData` через ссылку на `Node` не будет полиморфным. Компилятор генерирует в `MyNode` bridge-метод `setData(Object)`, который приводит аргумент к `Integer` и вызывает `setData(Integer)`, обеспечивая корректную работу полиморфизма.

### 26. Можно ли использовать несколько ограничений (bounds) для одного параметра типа?

Да, можно. Параметр типа может иметь несколько ограничений, разделенных символом `&`. При этом первым должно быть указано имя класса (если оно есть), а затем — интерфейсы.

Пример: `<T extends Number & Comparable<T> & Serializable>`.

### 27. Как реализовать шаблон Singleton с помощью Record?

Технически Singleton можно реализовать с помощью Record, объявив статическое константное поле экземпляра:

```java
public record AppConfig(String environment, int timeout) {
    public static final AppConfig INSTANCE = new AppConfig("production", 30);

    public static AppConfig getInstance() {
        return INSTANCE;
    }
}
```

Однако у этого подхода есть важные ограничения:
- **Нет строгого контроля:** В публичном Record канонический конструктор **должен** быть публичным. Это значит, что любой клиентский код может вызвать `new AppConfig(...)` и создать дополнительные экземпляры, нарушив паттерн Singleton.
- **Обход через рефлексию:** Конструктор можно вызвать через рефлексию.

Чтобы предотвратить создание дополнительных экземпляров, можно добавить защиту в компактный конструктор с использованием `AtomicBoolean`:

```java
public record AppConfig(String url) {
    private static final AtomicBoolean INITIALIZED = new AtomicBoolean(false);
    public static final AppConfig INSTANCE = new AppConfig("https://api.prod.com");

    public AppConfig {
        if (INITIALIZED.getAndSet(true)) {
            throw new IllegalStateException("Singleton already initialized!");
        }
    }
}
```

Но даже в этом случае **Enum** остается «золотым стандартом» для реализации Singleton в Java, так как он обеспечивает абсолютную уникальность экземпляра на уровне JVM и невосприимчив к атакам через рефлексию и сериализацию.
