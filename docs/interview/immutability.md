# Иммутабельность

### 1. Что такое иммутабельный (неизменяемый) объект

Иммутабельный (неизменяемый) объект — это объект, состояние которого не может быть изменено после его создания. Все поля такого объекта устанавливаются ровно один раз, и любая операция, которая, как может показаться, должна его изменить, на самом деле возвращает **новый** объект с измененными значениями, оставляя исходный объект нетронутым. Это означает, что если у вас есть ссылка на иммутабельный объект, вы можете быть уверены, что его состояние не изменится неожиданно для вас.


### 2. Какие преимущества даёт использование иммутабельных объектов

Иммутабельность дает несколько ключевых преимуществ:
- **Потокобезопасность (Thread Safety)**: это главное преимущество. Иммутабельные объекты можно свободно разделять между потоками без синхронизации, так как их состояние не может быть изменено. Это устраняет целый класс ошибок, связанных с гонками данных (race conditions).
- **Упрощение логики и отладки**: если метод получает иммутабельный объект, можно быть уверенным, что его состояние не изменится во время выполнения. Это делает код более предсказуемым и его легче понимать.
- **Возможность свободного совместного использования (Free Sharing)**: поскольку объект не может измениться, вы можете безопасно передавать его в другие части программы или потоки, не создавая защитных копий.
- **Надежные хеш-ключи**: иммутабельные объекты идеально подходят для использования в качестве ключей в `HashMap` или элементах `HashSet`, так как их хеш-код не может измениться после добавления в коллекцию.


### 3. Как создать иммутабельный класс в Java

Для создания иммутабельного класса в Java необходимо следовать набору правил:
1.  **Объявите все поля как `private` и `final`**. Это гарантирует, что поля не могут быть изменены после инициализации в конструкторе.
2.  **Не предоставляйте методы-сеттеры** (или любые другие методы, изменяющие состояние объекта).
3.  **Объявите класс как `final`**. Это предотвращает создание подклассов, которые могли бы переопределить методы и изменить поведение класса, нарушив его иммутабельность.
4.  **Если поля содержат ссылки на изменяемые (mutable) объекты, обеспечьте их защиту**:
    - Не позволяйте изменять эти объекты через методы класса.
    - Не делитесь ссылками на эти изменяемые объекты. При передаче в конструктор создавайте **защитные копии (defensive copies)** и сохраняйте ссылки на них. Аналогично, при возврате из методов создавайте копии внутренних изменяемых объектов, чтобы не возвращать оригинальные ссылки.

```java
// Иммутабельный класс
public final class Money {
    private final long amount;
    private final Currency currency;

    public Money(long amount, Currency currency) {
        this.amount = amount;
        this.currency = currency; // Currency — неизменяемый enum
    }

    public long getAmount() {
        return amount;
    }

    public Currency getCurrency() {
        return currency;
    }

    // Метод, возвращающий новый объект
    public Money add(Money other) {
        if (this.currency != other.currency) {
            throw new IllegalArgumentException("Different currencies");
        }
        return new Money(this.amount + other.amount, this.currency);
    }
}

// Использование:
Money m1 = new Money(100, Currency.USD);
Money m2 = m1.add(new Money(50, Currency.USD));
System.out.println(m1.getAmount()); // 100 (неизменён)
System.out.println(m2.getAmount()); // 150 (новый объект)
```


### 4. Почему класс String является иммутабельным

Класс `String` был сделан иммутабельным по трем основным причинам: **дизайн, эффективность и безопасность**.
- **Дизайн и String Pool**: Благодаря иммутабельности стало возможным существование **пула строк (String Intern Pool)**. Когда вы создаете строковый литерал, JVM проверяет, есть ли уже такая строка в пуле, и если есть, возвращает ссылку на существующий объект. Это экономит память. Если бы строки были изменяемыми, изменение строки через одну ссылку привело бы к изменению значения для всех других ссылок, указывающих на тот же объект в пуле.
- **Безопасность (Security)**: Строки широко используются в качестве параметров для многих классов Java, например, при открытии файлов или сетевых соединений. Если бы строки были изменяемыми, злоумышленник мог бы изменить строку, представляющую, например, имя файла, после проверки безопасности, что привело бы к серьезным уязвимостям.
- **Эффективность (Efficiency)**: Хеш-код строки часто используется, например, в `HashMap`. Благодаря иммутабельности хеш-код строки всегда остается неизменным, поэтому его можно вычислить один раз и закешировать, не беспокоясь о том, что он изменится. Это избавляет от необходимости пересчитывать хеш-код при каждом использовании.


### 5. Какие последствия иммутабельности String

Основные последствия иммутабельности `String`:
- **Безопасное совместное использование**: Строки можно безопасно передавать между потоками без синхронизации.
- **Эффективное кеширование хеш-кода**: Хеш-код вычисляется один раз и кешируется, что ускоряет работу с хеш-коллекциями.
- **Работа String Pool**: Пул строк позволяет экономить память за счет повторного использования существующих строковых литералов.
- **Потенциальные проблемы с производительностью**: При частых модификациях строк (например, в цикле) создается множество новых объектов, что может привести к накладным расходам. В таких случаях рекомендуется использовать `StringBuilder` или `StringBuffer`.
- **Обход через рефлексию**: Хотя `String` спроектирован как иммутабельный, с помощью рефлексии можно получить доступ к внутреннему массиву символов и изменить его, нарушив иммутабельность. Однако это является злоупотреблением и может привести к непредсказуемым последствиям.


### 6. Почему иммутабельные объекты thread-safe

Иммутабельные объекты являются потокобезопасными (thread-safe) по своей сути, потому что их состояние не может быть изменено после создания. В многопоточной среде, когда несколько потоков имеют доступ к одному и тому же иммутабельному объекту, они могут только **читать** его состояние. Поскольку нет операций записи, которые могли бы изменить состояние, не возникает ситуаций гонки данных (race conditions), и, следовательно, нет необходимости в синхронизации доступа к объекту. Каждый поток всегда будет видеть одно и то же, неизменное состояние объекта, что и обеспечивает потокобезопасность.


### 7. Что такое ключевое слово final и как оно помогает в создании иммутабельных классов

Ключевое слово `final` в Java означает, что сущность (переменная, метод или класс) не может быть изменена. В контексте создания иммутабельных классов `final` играет ключевую роль:
- **`final` поля**: Поле, объявленное как `final`, должно быть инициализировано ровно один раз (в конструкторе или при объявлении) и не может быть переназначено впоследствии. Это гарантирует, что ссылка на объект в поле не изменится после завершения работы конструктора.
- **`final` класс**: Класс, объявленный как `final`, не может быть расширен. Это предотвращает создание подклассов, которые могли бы переопределить методы и изменить поведение класса, нарушив его иммутабельность.

Важно понимать, что `final` поле, ссылающееся на изменяемый объект, не делает этот объект иммутабельным. Вы не можете переназначить ссылку, но сам объект, на который она указывает, может быть изменен. Поэтому для полной иммутабельности необходимо также использовать защитные копии.


### 8. Достаточно ли сделать все поля final для иммутабельности

Нет, **недостаточно**. Объявление всех полей `final` — это только один из шагов. Если поле класса ссылается на **изменяемый (mutable)** объект (например, `Date`, `List`, `StringBuilder`), то, даже если сама ссылка `final`, содержимое этого объекта может быть изменено извне. Это нарушает иммутабельность, так как состояние вашего объекта может измениться без вызова его методов.

Например, если у вас есть `final List<String> names`, вы не можете присвоить этому полю новый список, но вы можете вызвать `names.add(...)` и изменить содержимое существующего списка. Чтобы класс был по-настоящему иммутабельным, необходимо либо использовать только иммутабельные компоненты, либо применять **защитное копирование (defensive copying)** для всех изменяемых полей.


### 9. Что делать, если поле класса ссылается на мутабельный объект

Если поле класса ссылается на мутабельный (изменяемый) объект, необходимо предпринять специальные меры предосторожности, чтобы обеспечить иммутабельность класса. Ключевой инструмент для этого — **защитное копирование (defensive copying)**. Вам нужно:
1.  **Принимать копию**: В конструкторе, когда вы получаете изменяемый объект в качестве параметра, создавайте его глубокую копию и сохраняйте ссылку на эту копию в поле. Это предотвращает внешнее изменение объекта через переданную ссылку.
2.  **Возвращать копию**: В методах-геттерах, которые возвращают ссылку на внутренний изменяемый объект, также возвращайте его копию, а не оригинальную ссылку. Это предотвращает изменение внутреннего состояния объекта через возвращенную ссылку.

Таким образом, вы изолируете внутреннее состояние вашего объекта от внешнего мира.


### 10. Что такое defensive copy (защитная копия)

**Защитная копия (defensive copy)** — это создание копии объекта для защиты от нежелательных изменений. В контексте иммутабельности это практика, при которой класс, содержащий ссылку на изменяемый объект, создает и хранит **копию** этого объекта, а не оригинальную ссылку. Аналогично, при возврате такого объекта из метода возвращается его копия. Это гарантирует, что внутреннее состояние класса не может быть изменено извне через переданные или возвращенные ссылки. Defensive copying является важным приемом для обеспечения истинной иммутабельности, когда классы не могут быть полностью построены на иммутабельных компонентах.

```java
// Defensive copy для Date
public final class Appointment {
    private final Date time;

    public Appointment(Date time) {
        // Принимаем копию
        this.time = (Date) time.clone();
    }

    public Date getTime() {
        // Возвращаем копию
        return (Date) time.clone();
    }
}

// Без defensive copy:
Appointment appt = new Appointment(new Date());
Date originalDate = new Date();
Appointment appt2 = new Appointment(originalDate);
originalDate.setTime(System.currentTimeMillis() + 86400000);
// appt2.getTime() изменилось! (без clone)

// С defensive copy:
Appointment appt3 = new Appointment(new Date());
Date date = new Date();
Appointment appt4 = new Appointment(date);
date.setTime(System.currentTimeMillis() + 86400000);
System.out.println(appt4.getTime().equals(date)); // false (изолировано)
```


### 11. Когда нужно делать defensive copy

Защитное копирование необходимо в следующих ситуациях:
- **В конструкторе**, когда вы получаете в качестве параметра объект, который может быть изменен извне (например, `Date`, `List`, массив), и хотите сохранить его состояние в своем иммутабельном объекте.
- **В методах-геттерах**, когда вы возвращаете ссылку на внутренний изменяемый объект. Чтобы вызывающий код не мог изменить внутреннее состояние вашего объекта, вы должны вернуть копию.
- **При работе с коллекциями**: если вы возвращаете коллекцию, которая может быть изменена, или принимаете ее в качестве параметра, также следует рассмотреть создание копии.

Основное правило: делайте защитную копию всякий раз, когда вы передаете ссылку на изменяемый объект через границу вашего класса (в конструкторе или методе).


### 12. Как защитить коллекцию от изменений

Существует несколько способов защитить коллекцию от нежелательных изменений:
1.  **Использовать неизменяемые (immutable) коллекции**: Начиная с Java 9, появились фабричные методы `List.of()`, `Set.of()`, `Map.of()`, которые создают действительно неизменяемые коллекции. Попытка изменить их приведет к `UnsupportedOperationException`.
2.  **Использовать методы `copyOf()`**: Методы `List.copyOf()`, `Set.copyOf()`, `Map.copyOf()` создают неизменяемую копию существующей коллекции.
3.  **Использовать `Collections.unmodifiableList()`**: Этот метод создает **неизменяемое представление (view)** над существующей коллекцией. Важно понимать, что он не создает копию. Если исходная коллекция будет изменена, эти изменения будут видны через неизменяемое представление. Поэтому этот метод не подходит для создания истинно иммутабельных объектов, если исходная коллекция может быть изменена.
4.  **Возвращать защитную копию**: В геттере можно возвращать `new ArrayList<>(internalList)`, чтобы вызывающий код получил копию, изменения в которой не затронут внутреннюю коллекцию.


### 13. Что такое Collections.unmodifiableList() и как это работает

`Collections.unmodifiableList()` — это статический метод, который возвращает **неизменяемое представление (unmodifiable view)** над указанным списком. Это означает, что вы не можете добавлять, удалять или изменять элементы через возвращенный список — любая попытка вызовет `UnsupportedOperationException`.

Однако **это не создает копию**. Возвращенный список является "оберткой" над исходным списком. Если исходный список будет изменен через другую ссылку, эти изменения будут видны и через неизменяемое представление. Поэтому `Collections.unmodifiableList()` **не следует** использовать для создания защитных копий или обеспечения истинной иммутабельности. Он полезен только для того, чтобы предоставить клиентскому коду read-only доступ к коллекции, которая не должна изменяться через этот конкретный интерфейс.


### 14. В чём разница между shallow copy и deep copy

- **Shallow copy (поверхностная копия)**: Создает новый объект, но копирует только значения полей. Для полей, которые являются ссылками на другие объекты, копируется только **ссылка**, а не сам объект. В результате оригинал и копия указывают на одни и те же вложенные объекты. Изменение вложенного объекта через копию будет видно и в оригинале.
- **Deep copy (глубокая копия)**: Создает новый объект и рекурсивно копирует все вложенные объекты. Оригинал и копия полностью независимы друг от друга. Изменения в копии никак не влияют на оригинал.

Для обеспечения истинной иммутабельности при наличии изменяемых полей необходима именно **глубокая копия**.


### 15. Можно ли наследоваться от иммутабельного класса

Технически, да, можно, если класс не объявлен как `final`. Однако это **не рекомендуется**, поскольку подкласс может переопределить методы и изменить поведение класса, нарушив его иммутабельность. Например, подкласс может добавить изменяемое поле или переопределить метод-геттер таким образом, чтобы он возвращал изменяемое значение. Чтобы гарантировать иммутабельность, класс следует объявлять `final`.


### 16. Почему иммутабельный класс должен быть final

Иммутабельный класс должен быть `final`, чтобы **предотвратить наследование и переопределение его методов**. Если класс не является `final`, подкласс может переопределить методы (например, геттеры) и изменить их поведение. Например, подкласс может вернуть изменяемую ссылку или изменить состояние, нарушив тем самым контракт иммутабельности, который гарантировал родительский класс. Объявление класса `final` — это самый простой и надежный способ гарантировать, что поведение класса не будет изменено через наследование.


### 17. Что произойдёт, если переопределить геттер в подклассе иммутабельного класса

Если переопределить геттер в подклассе иммутабельного класса, можно **нарушить иммутабельность**. Например, можно создать подкласс, который переопределяет геттер так, чтобы он возвращал новый объект при каждом вызове или, что еще хуже, возвращал ссылку на изменяемый объект, который можно модифицировать. Это может привести к тому, что код, который полагается на иммутабельность родительского класса, будет работать некорректно. Именно поэтому иммутабельные классы рекомендуется делать `final`.


### 18. Как работает String pool и как это связано с иммутабельностью

**String Pool (пул строк)** — это специальная область в куче Java, где хранятся строковые литералы. Когда вы создаете строку с помощью литерала (например, `"hello"`), JVM сначала проверяет, есть ли уже такая строка в пуле. Если есть, она возвращает ссылку на существующий объект, а не создает новый. Это позволяет экономить память.

Этот механизм **возможен только благодаря иммутабельности `String`**. Если бы строки были изменяемыми, изменение строки через одну ссылку привело бы к изменению значения для всех других ссылок, указывающих на тот же объект в пуле, что привело бы к непредсказуемому поведению и ошибкам.


### 19. Можно ли изменить значение String через рефлексию

**Да, технически можно**. С помощью рефлексии можно получить доступ к внутреннему полю `value` класса `String` (которое содержит массив символов), сделать его доступным (`setAccessible(true)`) и изменить содержимое массива. Это позволяет обойти механизм иммутабельности.

Однако это **крайне не рекомендуется** и является злоупотреблением. Такой подход нарушает инкапсуляцию, может привести к непредсказуемым последствиям (особенно если строка находится в String Pool и используется другими частями системы) и делает код хрупким и зависимым от деталей реализации JVM.


### 20. Что такое Record и как он помогает создавать иммутабельные классы

**Record** (запись) — это специальный тип класса, introduced in Java 16, предназначенный для создания **неизменяемых (shallowly immutable) классов-носителей данных**. Record автоматически генерирует конструктор, геттеры (методы доступа), а также методы `equals()`, `hashCode()` и `toString()` на основе объявленных компонентов.

Все поля Record являются `private final`, и для них не генерируются сеттеры. Это делает Record отличным инструментом для создания простых иммутабельных классов. Однако важно помнить, что Record обеспечивает только **поверхностную (shallow) иммутабельность**. Если один из компонентов Record является ссылкой на изменяемый объект, этот объект все еще можно изменить, и для полной иммутабельности потребуется защитное копирование.

```java
// Record: автоматическая генерация методов
public record Point(int x, int y) {
    // Автоматически создаются:
    // - Point(int x, int y) — конструктор
    // - int x(), int y() — геттеры
    // - equals(), hashCode(), toString()
}

Point p1 = new Point(1, 2);
Point p2 = new Point(1, 2);

System.out.println(p1.x());    // 1
System.out.println(p1.equals(p2)); // true
System.out.println(p1.hashCode() == p2.hashCode()); // true

// Record — immutable:
// p1.x = 10; // Compile error!
```


### 21. Почему LocalDate, LocalDateTime иммутабельны

Классы `java.time` (такие как `LocalDate`, `LocalDateTime`, `Instant`) были спроектированы как **глубоко иммутабельные (deeply immutable)** с самого начала. Это было сознательное решение, принятое для решения проблем старых классов `Date` и `Calendar`, которые были изменяемыми и не потокобезопасными.

Иммутабельность `java.time` обеспечивает:
- **Потокобезопасность**: их можно безопасно использовать в многопоточных средах.
- **Предсказуемость**: значение даты/времени не может измениться неожиданно.
- **Простоту использования**: любая операция, которая "изменяет" дату, на самом деле возвращает новый объект (например, `localDate.plusDays(1)` возвращает новый `LocalDate`).

Это делает API `java.time` гораздо более надежным и удобным для работы с датами и временем.


### 22. В чём преимущества иммутабельных объектов для кэширования

Иммутабельные объекты идеально подходят для кэширования по нескольким причинам:
- **Безопасность совместного использования**: Поскольку состояние объекта не может измениться, вы можете безопасно кэшировать его и возвращать множеству клиентов, не беспокоясь о том, что один клиент изменит объект и повлияет на других.
- **Отсутствие необходимости в защитном копировании**: При извлечении из кэша не нужно создавать защитные копии, так как объект не может быть изменен. Это повышает производительность и снижает нагрузку на сборщик мусора.
- **Надежность**: Кэшированные данные всегда будут соответствовать тому состоянию, которое было сохранено, что упрощает логику и отладку.


### 23. Как иммутабельность влияет на производительность

Влияние иммутабельности на производительность **неоднозначно**:
- **Потенциальные недостатки**: Создание нового объекта при каждом "изменении" может привести к увеличению нагрузки на сборщик мусора и потреблению памяти, особенно в сценариях с частыми модификациями (например, в цикле).
- **Потенциальные преимущества**: Иммутабельные объекты могут **снизить** нагрузку на память в сценариях с кэшированием и совместным использованием, так как нет необходимости создавать защитные копии. Кроме того, они могут быть оптимизированы JVM (например, с помощью escape analysis).

В целом, для сценариев с интенсивными вычислениями и частыми модификациями состояния мутабельные объекты могут быть более производительными. Однако для обеспечения безопасности, надежности и простоты кода иммутабельность часто является предпочтительным выбором, а ее потенциальные недостатки могут быть смягчены.


### 24. Что такое persistent data structures

**Persistent data structures (персистентные структуры данных)** — это структуры данных, которые при модификации сохраняют свою предыдущую версию. Вместо изменения существующей структуры, операция модификации создает **новую версию** структуры, которая разделяет большую часть своей структуры с предыдущей версией (структурное совместное использование или structural sharing). Это обеспечивает эффективное использование памяти и позволяет обращаться к любым предыдущим версиям данных.

Иммутабельные объекты в Java можно рассматривать как простейшую форму персистентных структур. Персистентные структуры данных являются фундаментальной концепцией в функциональном программировании и все чаще используются в Java (например, в библиотеках вроде Vavr).


### 25. Есть ли недостатки у иммутабельных объектов

Да, у иммутабельных объектов есть некоторые недостатки:
- **Накладные расходы на создание объектов**: При каждом "изменении" создается новый объект. В сценариях с частыми модификациями это может привести к большому количеству выделений памяти и нагрузке на сборщик мусора.
- **Сложность реализации**: Для классов с изменяемыми полями требуется тщательное защитное копирование, что усложняет код.
- **Несовместимость с некоторыми фреймворками**: Некоторые фреймворки (например, ORM, такие как Hibernate) традиционно ожидают наличия сеттеров и изменяемых сущностей для своей работы. Хотя эта ситуация улучшается, могут потребоваться дополнительные усилия для интеграции.
- **Снижение читаемости при использовании Builder**: Для классов с большим количеством полей может потребоваться паттерн Builder, что увеличивает объем кода.


### 26. Как реализовать Builder pattern для иммутабельного класса

Паттерн **Builder** часто используется для создания иммутабельных классов со множеством параметров, чтобы избежать создания "телескопических" конструкторов. Реализация выглядит следующим образом:
1.  Создается статический вложенный класс `Builder`.
2.  `Builder` имеет те же поля, что и основной класс, но они **не** являются `final` и имеют сеттеры, возвращающие `this` (для chaining).
3.  Основной класс имеет **private** конструктор, принимающий `Builder` в качестве параметра.
4.  Метод `build()` в `Builder` вызывает этот private конструктор и передает себя.
5.  В конструкторе основного класса выполняется защитное копирование изменяемых полей.

Это позволяет создавать иммутабельные объекты гибко и читаемо.


### 27. Можно ли использовать иммутабельные объекты как ключи в HashMap

**Да, и это настоятельно рекомендуется**. Иммутабельные объекты — идеальные кандидаты для ключей в `HashMap` (и элементах `HashSet`), потому что их хеш-код не может измениться после добавления в коллекцию. Это гарантирует, что объект всегда будет найден в правильной "корзине" (bucket) хеш-таблицы. Если бы ключ был изменяемым, его хеш-код мог бы измениться после добавления в `HashMap`, что привело бы к тому, что объект стал бы "потерянным" для коллекции.


### 28. Что произойдёт, если изменить мутабельный ключ в HashMap

Если использовать мутабельный объект в качестве ключа в `HashMap` и изменить его состояние (и, следовательно, его хеш-код) после добавления в коллекцию, произойдут серьезные проблемы. `HashMap` вычисляет хеш-код ключа в момент добавления и использует его для определения "корзины", в которой будет храниться запись. При поиске `HashMap` снова вычисляет хеш-код переданного ключа. Если ключ был изменен, его новый хеш-код будет указывать на **другую корзину**, и `HashMap` не найдет запись. В результате запись становится **недоступной** (потерянной) для `get()` и других операций, хотя физически она все еще находится в коллекции.

Именно поэтому **никогда не следует использовать мутабельные объекты в качестве ключей в хеш-коллекциях**.


### 29. Как правильно работать с коллекциями в иммутабельных классах

При работе с коллекциями в иммутабельных классах необходимо соблюдать особую осторожность, так как стандартные коллекции (например, `ArrayList`, `HashMap`) являются изменяемыми. Правильные подходы:
1.  **Использовать неизменяемые коллекции**: Если возможно, используйте фабричные методы `List.of()`, `Set.of()`, `Map.of()` или `List.copyOf()` для хранения коллекций внутри иммутабельного класса.
2.  **Применять защитное копирование**: Если вы принимаете коллекцию в конструкторе, создавайте ее **глубокую копию** (например, `new ArrayList<>(inputList)`) и сохраняйте эту копию. В геттерах возвращайте копию внутренней коллекции, а не оригинал.
3.  **Не использовать `Collections.unmodifiableList()` как замену копированию**: Помните, что этот метод создает только **представление (view)**, а не копию. Если исходная коллекция будет изменена, изменения будут видны через это представление.
4.  **Обеспечить глубокую иммутабельность**: Если коллекция содержит изменяемые элементы, необходимо также обеспечить их защитное копирование или использовать иммутабельные элементы.
