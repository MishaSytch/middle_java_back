# String

### 1. Как работает String Pool

String Pool (пул строк) — это специальная область памяти, где JVM хранит уникальные экземпляры строковых литералов. Когда вы создаете строку с помощью литерала (например, `"hello"`), JVM сначала проверяет, есть ли уже такая строка в пуле. Если есть, она возвращает ссылку на существующий объект, а не создает новый. Это позволяет повторно использовать строки и экономить память. Если строки с таким значением в пуле нет, она создается и помещается в пул.


### 2. В чём разница между созданием String через литерал и через new

- **Через литерал** (`String s = "hello"`): JVM проверяет String Pool. Если строка с таким значением уже там есть, возвращается ссылка на существующий объект. Если нет — создается новый объект в пуле, и возвращается ссылка на него.
- **Через `new`** (`String s = new String("hello")`): **всегда** создается новый объект в куче (heap), независимо от того, есть ли такая строка в пуле. Строка из литерала-аргумента при этом уже находится в пуле, но `new` создает отдельную копию в куче.

```java
String a = "hello";
String b = "hello";
String c = new String("hello");

System.out.println(a == b);      // true (обе ссылки на объект в пуле)
System.out.println(a == c);      // false (c — отдельный объект в куче)
System.out.println(a.equals(c)); // true (содержимое одинаковое)

// intern() возвращает ссылку на объект из пула
String d = c.intern();
System.out.println(a == d);      // true
```


### 3. Когда стоит использовать intern()

Метод `intern()` позволяет вручную поместить строку в String Pool или получить ссылку на уже существующую там строку с таким же значением. Его стоит использовать, когда вы работаете с большим количеством строк, полученных динамически (например, из базы данных или сети), и хотите **сэкономить память**, сократив количество дублирующихся строковых объектов. Однако `intern()` может быть медленным, так как он работает с хеш-таблицей пула, поэтому его не стоит применять без необходимости.


### 4. Почему String является иммутабельным

Строки в Java сделаны иммутабельными по нескольким причинам:
- **String Pool**: только иммутабельность позволяет безопасно разделять одну строку между множеством ссылок в пуле.
- **Безопасность**: строки часто используются для хранения конфиденциальных данных (пароли, имена файлов, URL). Если бы их можно было изменить, это привело бы к уязвимостям.
- **Кеширование хеш-кода**: хеш-код строки вычисляется один раз и кешируется. Если бы строка могла измениться, хеш-код стал бы недействительным, что нарушило бы работу `HashMap` и других коллекций.
- **Потокобезопасность**: иммутабельные строки можно безопасно использовать в многопоточной среде без синхронизации.


### 5. Когда использовать StringBuilder, а когда StringBuffer

- **`StringBuilder`**: используйте в **однопоточных** сценариях, когда требуется частая модификация строк (например, в циклах). Он быстрее, так как его методы не синхронизированы.
- **`StringBuffer`**: используйте в **многопоточных** сценариях, когда один и тот же буфер строк может модифицироваться из нескольких потоков. Все его методы синхронизированы, что обеспечивает потокобезопасность.

В большинстве случаев рекомендуется `StringBuilder`, так как необходимость в потокобезопасном буфере строк возникает редко.

```java
// StringBuilder: быстрая сборка строки в цикле
StringBuilder sb = new StringBuilder();
for (int i = 0; i < 1000; i++) {
    sb.append(i).append(",");
}
String result = sb.toString();

// ❌ Неэффективно: создание множества промежуточных String-объектов
String s = "";
for (int i = 0; i < 1000; i++) {
    s += i + ","; // Каждый + создает новый String
}
```


### 6. Почему StringBuffer медленнее StringBuilder

`StringBuffer` медленнее, потому что все его методы (например, `append`, `insert`) объявлены как `synchronized`. Это означает, что каждый вызов метода требует захвата и освобождения блокировки монитора объекта, что создает дополнительные накладные расходы. `StringBuilder` не имеет этой синхронизации, поэтому работает быстрее.


### 7. Что происходит при конкатенации строк через оператор +

При конкатенации строк через `+` создается **новый объект `String`**, содержащий результат объединения. Исходные строки остаются неизменными. В цикле это может привести к созданию множества промежуточных объектов и значительным накладным расходам.


### 8. Как компилятор Java оптимизирует конкатенацию строк

Начиная с **Java 9** (в рамках JEP 280), компилятор `javac` генерирует байт-код с инструкцией `invokedynamic`, которая ссылается на `StringConcatFactory`. Эта фабрика во время выполнения выбирает наиболее эффективный способ конкатенации для конкретного случая (например, используя `StringBuilder` или прямой вызов `String.concat()`), что позволяет JIT-компилятору дополнительно оптимизировать код. До Java 9 компилятор просто заменял `+` на цепочку вызовов `StringBuilder.append()`.


### 9. Можно ли использовать == для сравнения String

Использовать `==` для сравнения строк **не рекомендуется**, так как этот оператор сравнивает **ссылки** на объекты, а не их содержимое. Две строки с одинаковым содержимым могут быть разными объектами в памяти (например, если одна создана через `new`), и тогда `==` вернет `false`. Единственный случай, когда `==` может сработать — если обе строки гарантированно взяты из String Pool (например, оба литерала), но полагаться на это в общем коде не стоит.


### 10. В чём разница между == и equals() для String

- **`==`** сравнивает **ссылки** (идентичность объектов): указывают ли две переменные на один и тот же объект в памяти.
- **`equals()`** сравнивает **содержимое** (значения) строк: одинаковы ли последовательности символов, независимо от того, являются ли объекты разными экземплярами.

Для сравнения строк всегда следует использовать `equals()` (или `equalsIgnoreCase()` при необходимости).

```java
String a = new String("hello");
String b = new String("hello");

System.out.println(a == b);        // false (разные объекты в памяти)
System.out.println(a.equals(b));   // true (содержимое одинаковое)

// Безопасное сравнение с null:
String x = null;
System.out.println("hello".equals(x)); // false (без NPE)
// System.out.println(x.equals("hello")); // NPE!
```


### 11. Где хранится String Pool (в какой области памяти)

До **Java 7** String Pool располагался в области **PermGen** (Permanent Generation). Начиная с **Java 7**, пул строк был перенесен в **основную кучу (main heap)**. В **Java 8** PermGen был полностью удален и заменен на Metaspace, но String Pool остался в куче.


### 12. Может ли String Pool вызвать OutOfMemoryError

**Да**, может. В версиях **до Java 7**, когда пул находился в PermGen (области с фиксированным размером), чрезмерное интернирование строк могло привести к ошибке `OutOfMemoryError: PermGen space`. После переноса пула в кучу (Java 7+) эта конкретная ошибка PermGen исчезла, но слишком большое количество интернированных строк все еще может привести к `OutOfMemoryError: Java heap space`, так как пул теперь занимает память кучи.


### 13. Что делает метод substring() и как он работал до Java 7

Метод `substring()` возвращает новую строку, которая является подстрокой исходной.

**До Java 7** (точнее, до Java 7u6) `substring()` работал очень эффективно с точки зрения использования памяти: он **не копировал символы**. Вместо этого новый объект `String` хранил ссылку на **тот же самый внутренний массив символов** (`char[]`), что и исходная строка, а также значения `offset` и `count`, указывающие на начало и длину подстроки.


### 14. Почему изменили реализацию substring() в Java 7

Реализация `substring()` до Java 7 приводила к **утечкам памяти**. Если вы создавали небольшую подстроку из очень большой строки и сохраняли ее, исходная большая строка не могла быть собрана сборщиком мусора, потому что подстрока продолжала ссылаться на ее внутренний массив символов. Это могло приводить к значительному и неочевидному потреблению памяти.

В **Java 7u6** реализацию изменили (JDK-6924259): `substring()` теперь **всегда создает новую копию** нужного фрагмента символов. Это устранило проблему утечки памяти, но сделало операцию `substring()` **O(n)** по сложности (где n — длина подстроки), а не O(1), как было раньше.


### 15. Как работает метод split()

Метод `split(String regex)` разбивает строку на массив строк, используя заданное **регулярное выражение** в качестве разделителя. Он возвращает массив `String[]`, содержащий подстроки между совпадениями с регулярным выражением. Например, `"a,b,c".split(",")` вернет `["a", "b", "c"]`. Важно помнить, что аргумент — это именно регулярное выражение, поэтому специальные символы (например, `.` или `|`) нужно экранировать.


### 16. В чём особенность метода replace() vs replaceAll()

- **`replace(CharSequence target, CharSequence replacement)`**: выполняет **простую замену подстроки** на другую подстроку. Он не использует регулярные выражения и работает буквально. Это быстрее и безопаснее, если вам нужно заменить фиксированную последовательность символов.
- **`replaceAll(String regex, String replacement)`**: выполняет замену, используя **регулярное выражение** для поиска совпадений. Он более мощный, но и более медленный, так как требует компиляции регулярного выражения. Используйте его, когда нужна замена по шаблону (например, `replaceAll("\\s+", " ")` для замены всех последовательностей пробелов на один пробел).


### 17. Что такое String encoding (кодировка)

Кодировка (encoding) — это правило, по которому символы (например, буквы, цифры, знаки препинания) преобразуются в последовательность байтов для хранения или передачи. Внутри Java `String` всегда хранится в **UTF-16** (до Java 9 — как `char[]` с 2 байтами на символ). Однако при преобразовании строки в байты (например, для записи в файл или отправки по сети) или из байтов используется конкретная кодировка, такая как UTF-8, ISO-8859-1 (Latin-1) и другие. Неправильный выбор кодировки при преобразовании может привести к появлению "кракозябр" (mojibake).


### 18. Как правильно конвертировать String в byte[] и обратно

Для преобразования используются методы класса `String` с указанием кодировки:
- **String → byte[]**: `byte[] bytes = str.getBytes(StandardCharsets.UTF_8);`
- **byte[] → String**: `String str = new String(bytes, StandardCharsets.UTF_8);`

**Всегда указывайте кодировку явно** (например, `StandardCharsets.UTF_8`). Если не указать, будет использована платформенно-зависимая кодировка по умолчанию, что может привести к несовместимости и ошибкам при переносе кода между системами.


### 19. Что такое compact strings в Java 9+

**Compact Strings** — это оптимизация внутреннего представления строк, появившаяся в **Java 9** (JEP 254). До Java 9 `String` всегда хранил символы в массиве `char[]`, где каждый символ занимал **2 байта** (UTF-16). Однако многие строки состоят только из символов Latin-1 (ISO-8859-1), для которых достаточно **1 байта**.

Начиная с Java 9, `String` внутренне использует массив `byte[]` и дополнительное поле-кодировщик (`coder`):
- Если все символы строки могут быть представлены в Latin-1, используется **1 байт на символ** (экономия памяти до 50%).
- Если в строке есть символы, требующие более 1 байта (например, кириллица, иероглифы), строка хранится как **UTF-16** (2 байта на символ).

Это нововведение значительно снижает потребление памяти для типичных приложений, где большинство строк — латиница.


### 20. Как узнать, сколько памяти занимает String

Точный размер объекта `String` в памяти зависит от JVM, версии Java и содержимого строки. Приблизительно:
- **До Java 9**: заголовок объекта + ссылка на `char[]` + `int hash` + `int offset` + `int count` + сам массив `char[]` (2 байта × длина).
- **Java 9+ (Compact Strings)**: заголовок объекта + ссылка на `byte[]` + `int hash` + `byte coder` + `boolean hashIsZero` + сам массив `byte[]` (1 байт × длина для Latin-1 или 2 байта × длина для UTF-16).

Для точного измерения можно использовать инструменты вроде **JOL (Java Object Layout)** или **Java Flight Recorder**.


### 21. Можно ли изменить содержимое String через рефлексию

**Технически да, можно**, но это **крайне не рекомендуется** и является злоупотреблением. С помощью рефлексии можно получить доступ к внутреннему полю `value` (массиву `char[]` до Java 9 или `byte[]` в Java 9+), сделать его доступным (`setAccessible(true)`) и изменить его элементы.

Однако это:
- Нарушает иммутабельность `String`.
- Может привести к непредсказуемым последствиям, если строка находится в String Pool и используется другими частями системы.
- Делает код хрупким и зависимым от деталей реализации JVM.


### 22. Что такое String deduplication в G1 GC

**String Deduplication** (дедупликация строк) — это оптимизация, доступная в **G1 Garbage Collector** начиная с **Java 8u20**. Она включается флагом `-XX:+UseStringDeduplication`.

В отличие от интернирования (`intern()`), которое канонизирует строки (заменяет все дубликаты одной ссылкой в пуле), дедупликация **не изменяет ссылки** на объекты `String`. Вместо этого G1 GC находит объекты `String` с одинаковым содержимым и заставляет их **разделять один и тот же внутренний массив символов** (`byte[]` или `char[]`). Это уменьшает потребление памяти, не меняя видимую семантику строк и не требуя явного вызова `intern()`.


### 23. Почему String implements Comparable и CharSequence

- **`Comparable<String>`**: `String` реализует `Comparable`, чтобы обеспечить **естественный порядок сортировки** строк. Это позволяет сортировать строки в алфавитном (лексикографическом) порядке с помощью `Collections.sort()`, `Arrays.sort()` или методов вроде `TreeMap`, `TreeSet`, которые полагаются на `Comparable`. Метод `compareTo()` сравнивает строки посимвольно.
- **`CharSequence`**: `CharSequence` — это интерфейс, представляющий **последовательность символов**. Реализуя его, `String` (наряду с `StringBuilder` и `StringBuffer`) может использоваться единообразно в API, которые работают с последовательностями символов, например, в методах `Pattern.matcher(CharSequence)`, `StringBuilder.append(CharSequence)` и других. Это обеспечивает полиморфизм и гибкость при работе с разными строковыми типами.
