# Kafka

### 1. Что такое топик (topic) в Kafka

Топик — это логическое имя, под которым публикуются сообщения. Это категория или канал, в который продюсеры записывают данные, а консьюмеры из него читают. Топик является логическим контейнером для сообщений и не хранит данные сам по себе — данные распределяются по его партициям. Каждый топик имеет набор настроек, определяющих поведение данных, включая время хранение (retention), политику очистки (cleanup.policy) и количество партиций.

```java
// Создание топика через Kafka AdminClient
import org.apache.kafka.clients.admin.*;

Properties props = new Properties();
props.put(AdminClientConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");

try (AdminClient admin = AdminClient.create(props)) {
    NewTopic topic = new NewTopic("orders", 3, (short) 3); // 3 партиции, replication factor 3
    topic.configs(Map.of(
        "retention.ms", "604800000",  // 7 дней
        "cleanup.policy", "delete"
    ));
    admin.createTopics(List.of(topic));
}
```


### 2. Что такое партиция (partition) и зачем она нужна

Партиция — это физическая единица хранения в рамках топика. Сообщения внутри одной партиции строго упорядочены и имеют уникальный, монотонно возрастающий идентификатор, называемый offset.

Партиции нужны для обеспечения ключевых свойств Kafka:
- **Горизонтальное масштабирование**: разные партиции одного топика могут находиться на разных брокерах, что позволяет распределить нагрузку и объём данных по всему кластеру.
- **Параллелизм**: несколько консьюмеров (в рамках одной consumer group) могут одновременно читать разные партиции, увеличивая общую пропускную способность.
- **Упорядоченность**: гарантия порядка сообщений обеспечивается в рамках одной партиции, а не всего топика.


### 3. Как данные распределяются по партициям

Способ распределения зависит от стратегии, выбранной в продюсере:
- **По ключу**: если у сообщения есть ключ, Kafka вычисляет хеш от ключа и по модулю количества партиций определяет номер партиции. Это гарантирует, что все сообщения с одинаковым ключом попадут в одну и ту же партицию и будут обработаны в порядке отправки.
- **Без ключа**: если ключ равен `null`, используется стратегия **round-robin** (циклическое распределение по партициям) или **случайная** стратегия (в старых версиях). Это обеспечивает равномерную балансировку, но не даёт гарантий порядка между сообщениями, отправленными без ключа.

```java
// Producer: отправка с ключом и без ключа
import org.apache.kafka.clients.producer.*;

Properties props = new Properties();
props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);

try (KafkaProducer<String, String> producer = new KafkaProducer<>(props)) {
    // С ключом: все сообщения с orderId=123 попадут в одну партицию
    ProducerRecord<String, String> record1 = new ProducerRecord<>("orders", "123", "order-created");
    producer.send(record1);

    // Без ключа: round-robin по партициям
    ProducerRecord<String, String> record2 = new ProducerRecord<>("orders", "order-paid");
    producer.send(record2);
}
```


### 4. Что такое ключ сообщения и как он влияет на партиционирование

Ключ сообщения — это необязательный атрибут, который используется продюсером для управления тем, в какую партицию попадёт сообщение. Наличие ключа является основным способом обеспечить **локальную упорядоченность**: все сообщения с одинаковым ключом гарантированно записываются в одну и ту же партицию и сохраняют порядок отправки.

Платой за это может стать **data skew (перекос данных)**: если один ключ встречается гораздо чаще других, соответствующая ему партиция может стать «горячей», что приведёт к неравномерной нагрузке на брокеры и консьюмеры.


### 5. Что такое Consumer Group

Consumer Group — это механизм, позволяющий нескольким консьюмерам координированно читать данные из топика. Ключевое правило: **каждая партиция в рамках одной consumer group может быть назначена только одному консьюмеру**. Это обеспечивает параллельную обработку без дублирования: если один консьюмер упадёт, его партиции будут перераспределены между оставшимися живыми членами группы.

```java
// Consumer: чтение из топика в consumer group
import org.apache.kafka.clients.consumer.*;

Properties props = new Properties();
props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(ConsumerConfig.GROUP_ID_CONFIG, "order-processors");  // Consumer group
props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class);
props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class);
props.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "earliest");

try (KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props)) {
    consumer.subscribe(List.of("orders"));

    while (true) {
        ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
        for (ConsumerRecord<String, String> record : records) {
            System.out.printf("key=%s, value=%s, partition=%d, offset=%d%n",
                record.key(), record.value(), record.partition(), record.offset());
        }
    }
}
```


### 6. Как работает балансировка консьюмеров в группе

Балансировка (assignment) выполняется с помощью **partition assignment strategy**. Каждый консьюмер при вступлении в группу запускает процесс **rebalance**, в ходе которого группа коллективно решает, какие партиции какому консьюмеру назначить. Распространённые стратегии:
- **Range**: назначает последовательные диапазоны партиций для каждого топика отдельно.
- **RoundRobin**: распределяет партиции по кругу между всеми консьюмерами и всеми подписанными топиками.
- **Sticky**: старается сохранить существующее назначение партиций как можно дольше, чтобы минимизировать «перетасовку» при rebalance.


### 7. Можно ли иметь больше консьюмеров, чем партиций

Да, можно, но **избыточные консьюмеры будут простаивать**. В одной consumer group одновременно активными являются не более чем `количество партиций` консьюмеров. Если консьюмеров больше, чем партиций, лишние экземпляры будут подключены к группе, но не получат ни одной партиции и не будут обрабатывать сообщения. Это может быть полезно для «горячего резерва», но не даёт прироста пропускной способности.


### 8. Что произойдёт при добавлении нового консьюмера в группу

Добавление нового консьюмера в группу инициирует **rebalance**. В ходе rebalance все консьюмеры группы временно приостанавливают чтение, группа заново перераспределяет партиции между всеми участниками (включая нового), и только после завершения перераспределения обработка возобновляется. Это кратковременная остановка обработки — плата за динамическое масштабирование.


### 9. Какие гарантии доставки сообщений предоставляет Kafka

По умолчанию Kafka обеспечивает **at-least-once** (как минимум однократную) доставку. Это означает, что сообщение не будет потеряно, но в случае сбоев или повторных попыток может быть доставлено более одного раза. Пользователь может реализовать **at-most-once**, отключив повторные попытки в продюсере и коммитя offset до обработки. Семантика **exactly-once** (ровно один раз) достигается за счёт идемпотентного продюсера и транзакций.


### 10. В чём разница между at-most-once, at-least-once и exactly-once

- **At-most-once (не более одного раза)**: offset коммитится **до** обработки сообщения. Если обработка упадёт, сообщение будет потеряно, но дубликатов не возникнет. Подходит для некритичных данных (метрики, логи), где потеря допустима.
- **At-least-once (как минимум один раз)**: offset коммитится **после** успешной обработки. При сбое после обработки, но до коммита, сообщение будет обработано повторно, что может привести к дубликатам. Это стандартный выбор для большинства продакшн-систем.
- **Exactly-once (ровно один раз)**: сообщение обрабатывается ровно один раз, без потерь и дубликатов. Требует идемпотентного продюсера и/или транзакций, а также идемпотентной обработки на стороне консьюмера (или транзакционного связывания коммита offset с записью результата).

```java
// At-least-once: коммит после обработки
while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, String> record : records) {
        try {
            processMessage(record.value());  // Обработка
            // Если здесь будет ошибка — offset не закоммитится,
            // сообщение будет перечитано при следующей итерации
        } catch (Exception e) {
            // Логирование, возможно retry
            throw e;
        }
    }
    consumer.commitSync();  // Коммит ПОСЛЕ успешной обработки всех сообщений
}
```


### 11. Как настроить exactly-once семантику

Для exactly-once в Kafka необходимо:
1.  Включить **идемпотентность продюсера**: `enable.idempotence=true`. Это предотвращает дублирование сообщений на уровне продюсера при повторных отправках.
2.  Для транзакционной записи в несколько партиций или для атомарного коммита offset вместе с результатами обработки используется **Transactional API**: задать `transactional.id` и использовать методы `beginTransaction()`, `commitTransaction()`, `abortTransaction()`.
3.  На стороне консьюмера установить `isolation.level=read_committed`, чтобы читать только зафиксированные транзакционные сообщения.

Если внешняя система (например, база данных) не поддерживает транзакции вместе с Kafka, exactly-once достигается через **идемпотентную обработку** на стороне консьюмера (дедупликация по уникальному ID).


### 12. Что такое offset в Kafka

Offset — это уникальный, монотонно возрастающий целочисленный идентификатор, который присваивается каждому сообщению внутри **партиции**. Он является «адресом» сообщения в рамках партиции и позволяет консьюмеру отслеживать, до какого места в партиции он уже дочитал. Offset уникален только в пределах одной партиции; offsets в разных партициях независимы.


### 13. Как работает commit offset

Commit offset — это операция, которой консьюмер сообщает Kafka (специальному внутреннему топику `__consumer_offsets`), что он успешно обработал сообщения вплоть до определённого offset. При перезапуске или перебалансировке консьюмер начинает чтение с последнего закоммиченного offset. Коммит может быть автоматическим (по таймеру) или ручным (явный вызов `commitSync()`/`commitAsync()`).


### 14. В чём разница между auto commit и manual commit

- **Auto commit**: консьюмер автоматически коммитит offset с периодичностью, заданной параметром `auto.commit.interval.ms` (по умолчанию 5 секунд), независимо от того, завершилась ли обработка сообщений успешно. Это просто, но может привести к потере сообщений (если коммит произошёл до обработки) или к дубликатам (если сбой после обработки, но до коммита).
- **Manual commit**: разработчик явно вызывает `commitSync()` или `commitAsync()` в коде после успешной обработки. Это даёт полный контроль над семантикой доставки (at-least-once, at-most-once) и является предпочтительным для критичных данных.


### 15. Что такое rebalancing и когда он происходит

Rebalance — это процесс перераспределения партиций между консьюмерами внутри одной consumer group. Он происходит, когда:
- В группу добавляется новый консьюмер или покидает существующий.
- Изменяется количество партиций в подписанном топике.
- Изменяется набор топиков, на которые подписана группа (например, топик удалён).

Во время rebalance **все консьюмеры группы временно останавливают обработку**, пока не завершится новое распределение партиций.


### 16. Что такое репликация в Kafka

Репликация — это механизм обеспечения отказоустойчивости и долговечности данных в Kafka. Каждая партиция имеет **replication factor** — количество копий (реплик), которые хранятся на разных брокерах. Одна из реплик назначается **лидером**, остальные — **фолловерами**. Если брокер с лидером выходит из строя, один из фолловеров становится новым лидером, и партиция продолжает работать.


### 17. Что такое leader и follower реплики

- **Leader** — это реплика, которая обрабатывает все запросы чтения и записи для данной партиции от продюсеров и консьюмеров. Только лидер принимает новые сообщения.
- **Follower** — это реплики, которые пассивно копируют данные с лидера. Они не обслуживают клиентов (в стандартной конфигурации) и нужны для обеспечения избыточности и быстрого переключения при отказе лидера.


### 18. Что такое ISR (In-Sync Replicas)

ISR — это набор реплик партиции (включая лидера), которые **полностью синхронизированы с лидером** и не отстают от него дольше, чем допускает настройка `replica.lag.time.max.ms`. Только реплики из ISR имеют право быть избранными новым лидером при отказе текущего. Параметр `min.insync.replicas` задаёт минимальный размер ISR, при котором продюсер с `acks=all` может успешно записать данные; если ISR меньше этого значения, запись будет отклонена.


### 19. Как Kafka обеспечивает отказоустойчивость

Отказоустойчивость Kafka строится на сочетании:
- **Репликации**: каждая партиция существует в нескольких копиях на разных брокерах.
- **Leader election**: при отказе лидера один из ISR-фолловеров автоматически становится новым лидером.
- **ISR и `acks=all`**: продюсер может подтверждать запись только после того, как данные приняты всеми (или минимальным числом) синхронными репликами, гарантируя, что данные не будут потеряны при отказе одного брокера.


### 20. Что такое producer acknowledgment и какие режимы существуют (acks=0,1,all)

`acks` определяет, когда продюсер считает запись успешной:
- **`acks=0`**: продюсер не ждёт подтверждения от брокера вообще. Максимальная пропускная способность, но возможна потеря данных при сбое брокера.
- **`acks=1`**: продюсер ждёт подтверждения только от **лидера** партиции. Лидер подтверждает запись сразу после сохранения в свой лог, не дожидаясь репликации на фолловеры. Возможна потеря данных, если лидер упадёт до того, как фолловеры успеют скопировать запись.
- **`acks=all`** (или `-1`): продюсер ждёт подтверждения от **всех реплик в ISR**. Это самая надёжная опция, гарантирующая, что данные сохранятся даже при отказе лидера (при условии, что `min.insync.replicas` > 1).

```java
// Producer конфигурация для надёжности
Properties props = new Properties();
props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(ProducerConfig.ACKS_CONFIG, "all");  // Ждать всех реплик в ISR
props.put(ProducerConfig.RETRIES_CONFIG, 3);   // Повторные попытки
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true); // Идемпотентность
props.put(ProducerConfig.MAX_IN_FLIGHT_REQUESTS_PER_CONNECTION, 5);
```


### 21. Что такое batch в Kafka producer

Batch (пакет) — это механизм группировки нескольких сообщений продюсером перед отправкой их в брокер. Продюсер накапливает сообщения в памяти и отправляет их одним запросом, когда достигается лимит по размеру (`batch.size`, по умолчанию 16KB) или по времени (`linger.ms`, по умолчанию 0). Батчинг значительно повышает пропускную способность за счёт сокращения количества сетевых запросов, но может увеличить задержку.


### 22. Как работает компрессия сообщений

Компрессия сжимает батч сообщений перед отправкой в брокер, что снижает нагрузку на сеть и дисковое пространство. Kafka поддерживает несколько кодеков: `gzip`, `snappy`, `lz4`, `zstd`. Степень сжатия и скорость зависят от кодека: `lz4` и `zstd` обычно обеспечивают хороший баланс между степенью сжатия и нагрузкой на CPU. Компрессия включается на стороне продюсера параметром `compression.type`; брокер и консьюмеры автоматически распаковывают данные.


### 23. Что такое idempotent producer

Идемпотентный продюсер — это режим работы продюсера (`enable.idempotence=true`), при котором Kafka гарантирует, что повторная отправка сообщения (например, из-за сетевого сбоя или таймаута) **не приведёт к дублированию** в логе партиции. Продюсер присваивает каждому сообщению порядковый номер (sequence number), и брокер отбрасывает сообщения с уже виденными номерами. Идемпотентность является основой для exactly-once семантики и обычно используется вместе с `acks=all`.


### 24. Как обрабатывать ошибки при чтении сообщений

Стратегии обработки ошибок в консьюмере:
- **Повторные попытки (retry) с backoff**: для временных ошибок (сетевые сбои, временная недоступность внешней системы) можно повторить обработку сообщения несколько раз с увеличивающейся задержкой, не коммитя offset.
- **Пропуск (skip)**: для «ядовитых» сообщений (malformed, десериализация не удалась), которые никогда не обработаются успешно, можно закоммитить offset, чтобы не блокировать партицию, и залогировать ошибку.
- **Dead Letter Queue (DLQ)**: после исчерпания повторных попыток отправить сообщение в специальный DLQ-топик для последующего анализа и ручной обработки.


### 25. Что такое DLQ (Dead Letter Queue)

DLQ — это специальный топик, куда отправляются сообщения, которые не удалось обработать после всех повторных попыток. DLQ позволяет:
- Не блокировать обработку остальных сообщений в партиции «ядовитым» сообщением.
- Сохранить проблемное сообщение для последующей диагностики, ручного исправления и повторной обработки (replay).
- Отделить сбойные сообщения от основного потока данных.

Для DLQ обычно настраивают увеличенный retention, чтобы иметь достаточно времени на разбор проблемы.


### 26. Как мониторить lag консьюмера

**Consumer lag** — это разница между последним offset, записанным в партицию продюсером, и последним offset, закоммиченным консьюмером. Лаг показывает, насколько консьюмер отстаёт от потока данных. Для мониторинга используются:
- **Утилиты командной строки**: `kafka-consumer-groups.sh --describe` показывает lag по каждой партиции и группе.
- **Специализированные инструменты**: Burrow (специализированный сервис для проверки lag), Klag, kafkatop.
- **Метрики**: Kafka предоставляет метрики `records-lag-max` и другие через JMX; их можно экспортировать в Prometheus/Grafana для алертинга.


### 27. Что такое retention policy

Retention policy (политика хранения) определяет, **как долго** Kafka хранит сообщения в топике, прежде чем удалить их. Настраивается на уровне топика параметром `cleanup.policy`, который может принимать два основных значения:
- **`delete`** (по умолчанию): старые сегменты лога удаляются по достижении лимита по времени (`retention.ms`) или по размеру (`retention.bytes`).
- **`compact`**: Kafka сохраняет **последнее значение для каждого ключа** в партиции, удаляя более старые записи с тем же ключом. Это полезно для хранения «текущего состояния» (например, последний профиль пользователя).


### 28. Как удаляются старые сообщения из топика

Удаление старых сообщений происходит на уровне **сегментов лога**. Партиция разбита на сегменты (файлы). Когда активный сегмент достигает лимита (`segment.ms` или `segment.bytes`), создаётся новый. Фоновый процесс проверяет сегменты и удаляет те, которые:
- Старше `retention.ms` (для политики `delete`).
- Превышают общий лимит `retention.bytes` (удаляются самые старые).
- Для политики `compact` — процесс «компакции» перезаписывает сегменты, удаляя устаревшие записи с одинаковыми ключами.

Важно: удаление сегментов не затрагивает активный сегмент, в который идёт запись.


### 29. Можно ли читать сообщения из определённой партиции

Да, можно. Хотя стандартный консьюмер подписывается на топик целиком и получает назначенные ему партиции, существует два способа читать из конкретной партиции:
- **Ручное назначение партиции (`assign`)**: вместо `subscribe()` можно вызвать `consumer.assign(Collections.singletonList(new TopicPartition("topic", partitionNumber)))`. В этом случае консьюмер не входит в consumer group (не участвует в rebalance) и читает только указанную партицию.
- **Утилиты командной строки**: `kafka-console-consumer` поддерживает опцию `--partition <номер>`, позволяющую читать только из указанной партиции.


### 30. Как реализовать фильтрацию сообщений на стороне консьюмера

Kafka не предоставляет встроенного механизма фильтрации на стороне брокера по содержимому сообщения (кроме ключа для партиционирования). Фильтрация выполняется **на стороне клиента (консьюмера)**:
- **Проверка в коде**: после `poll()` консьюмер получает `ConsumerRecord` и может проверить его ключ, значение или заголовки, пропуская ненужные сообщения. Offset при этом всё равно коммитится (если вы не хотите их перечитывать).
- **Использование `Predicate`**: в некоторых клиентских библиотеках (например, Spring Kafka) можно передать `Predicate` в `poll()` для фильтрации на уровне клиента.
- **Пропуск через `seek()`**: если сообщение не нужно, можно вызвать `consumer.seek()` для перехода к следующему offset, не коммитя текущий, но это скорее для управления позицией, чем для фильтрации.

Фильтрация «на лету» экономит ресурсы обработки, но не сокращает объём данных, передаваемых по сети. Для уменьшения объёма трафика используют **разделение на разные топики** по категориям или **компакцию** с ключами.
