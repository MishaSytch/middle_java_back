# ООП и SOLID


### 1. Что такое принцип Single Responsibility и как его применять?

**Single Responsibility Principle (SRP)** гласит, что у класса должна быть только одна причина для изменения. Другими словами, класс должен быть сосредоточен на выполнении одной четко определенной задачи или ответственности.

**Как применять:** На практике это означает, что если у вас есть класс, который одновременно занимается, например, валидацией данных, сохранением в базу данных и отправкой уведомлений, его следует разделить на несколько классов, каждый из которых будет отвечать за свою часть работы.

### 2. Приведите пример нарушения принципа Single Responsibility

Классический пример — класс `UserService`, который выполняет слишком много функций: валидирует email, сохраняет пользователя в базу данных (`entityManager.persist`), отправляет приветственное письмо и ведет аудит.

❌ Нарушение — один класс на всё:

```java
@Service
public class UserService {
    @PersistenceContext private EntityManager em;
    private final MailClient mail;
    private final AuditLog audit;

    public User register(User user) {
        if (!user.getEmail().matches("[\\w.]+@[\\w.]+\\.[a-z]+")) throw new IllegalArgumentException();
        em.persist(user);
        mail.send(user.getEmail(), "Welcome!");
        audit.log("REGISTER", user.getId());
        return user;
    }
}
```

✅ Разделение ответственностей — каждый класс делает одно:

```java
@Service
public class UserService {
    private final UserRepository repo;
    private final EmailValidator validator;
    private final WelcomeMailer mailer;
    private final AuditLogger audit;

    public User register(User user) {
        validator.validate(user.getEmail());
        User saved = repo.save(user);
        mailer.sendWelcome(saved);
        audit.log("REGISTER", saved.getId());
        return saved;
    }
}
```


### 3. Что такое принцип Open/Closed?

**Open/Closed Principle (OCP)** гласит, что программные сущности (классы, модули, функции) должны быть **открыты для расширения, но закрыты для модификации**. Это означает, что вы должны иметь возможность добавить новую функциональность, не изменяя существующий код.

### 4. Как рефакторить код, нарушающий принцип Open/Closed?

Типичное нарушение — это класс с множеством условных операторов `if/else` или `switch`, которые проверяют тип объекта, чтобы выполнить для него специфичное действие. Например, класс `DiscountCalculator` с конструкцией `if (order.getType().equals("VIP")) { ... } else if (...)`.

**Рефакторинг:** Вместо этого следует вынести логику для каждого типа в отдельный класс, реализующий общий интерфейс. Например, создать интерфейс `DiscountStrategy` с методом `calculate(Order order)`. Затем для каждого типа скидки (VIP, Regular и т.д.) создать свой класс, реализующий этот интерфейс. Теперь, чтобы добавить новый тип скидки, вы просто создаете новый класс-стратегию, не меняя существующий код.

❌ Нарушение OCP — ветвление по типу:

```java
public class DiscountCalculator {
    public BigDecimal calculate(Order order) {
        if (order.getType().equals("VIP")) {
            return order.getAmount().multiply(new BigDecimal("0.30"));
        } else if (order.getType().equals("REGULAR")) {
            return order.getAmount().multiply(new BigDecimal("0.05"));
        }
        return BigDecimal.ZERO;
    }
}
```

✅ OCP — общий интерфейс + отдельные стратегии (новый тип = новый класс):

```java
public interface DiscountStrategy {
    BigDecimal calculate(Order order);
}

@Component
public class VipStrategy implements DiscountStrategy {
    public BigDecimal calculate(Order order) {
        return order.getAmount().multiply(new BigDecimal("0.30"));
    }
}

@Component
public class RegularStrategy implements DiscountStrategy {
    public BigDecimal calculate(Order order) {
        return order.getAmount().multiply(new BigDecimal("0.05"));
    }
}
```


### 5. Что такое принцип Liskov Substitution?

**Liskov Substitution Principle (LSP)** утверждает, что объекты подкласса должны быть полностью взаимозаменяемы с объектами базового класса, не нарушая корректность программы. Это означает, что подкласс должен расширять поведение базового класса, а не изменять или сужать его.

### 6. Приведите пример нарушения принципа Liskov Substitution

Классический пример — отношение между `Rectangle` (Прямоугольник) и `Square` (Квадрат).

Если `Square` наследуется от `Rectangle`, то у него есть методы `setWidth()` и `setHeight()`. Однако, в отличие от прямоугольника, установка ширины квадрата должна изменять и его высоту, чтобы он оставался квадратом. Это нарушает контракт, заложенный в `Rectangle`. Клиентский код, который работает с `Rectangle`, может установить ширину в 5, а высоту в 10, ожидая площадь 50. Если вместо `Rectangle` ему подсунуть `Square`, площадь может оказаться 100, что нарушит работу программы.

❌ Нарушение — `Square` меняет поведение `set*` относительно контракта `Rectangle`:

```java
class Rectangle {
    protected double width, height;
    public void setWidth(double w)  { this.width = w; }
    public void setHeight(double h) { this.height = h; }
    public double area() { return width * height; }
}

class Square extends Rectangle {
    public void setWidth(double w)  { width = height = w; }
    public void setHeight(double h) { width = height = h; }
}

// Клиент, ожидающий поведение Rectangle:
Rectangle r = new Square();
r.setWidth(5);   // у Square это также задаст height = 5
r.setHeight(10);
System.out.println(r.area()); // 100, а не ожидаемые 50
```


### 7. Что такое принцип Interface Segregation?

**Interface Segregation Principle (ISP)** гласит, что клиенты не должны зависеть от методов, которые они не используют. Другими словами, лучше создавать множество специализированных, "узких" интерфейсов, чем один большой "толстый" интерфейс.

### 8. Что такое принцип Dependency Inversion?

**Dependency Inversion Principle (DIP)** состоит из двух правил:
1.  Модули высокого уровня не должны зависеть от модулей низкого уровня. Оба должны зависеть от абстракций.
2.  Абстракции не должны зависеть от деталей. Детали должны зависеть от абстракций.

На практике это означает, что ваш бизнес-класс (высокий уровень) не должен напрямую создавать экземпляр конкретного класса для работы с базой данных (низкий уровень). Вместо этого он должен зависеть от интерфейса `Repository`, а конкретная реализация будет внедрена извне.

### 9. Зачем вообще нужны принципы SOLID?

SOLID — это набор принципов объектно-ориентированного проектирования, которые помогают создавать программные системы, которые являются:
- **Понятными и читаемыми** (maintainable).
- **Гибкими и расширяемыми** (scalable).
- **Устойчивыми к изменениям** (robust).
- **Легко тестируемыми**.

Следование этим принципам помогает предотвратить появление "жесткого" и "хрупкого" кода, который сложно сопровождать и развивать.

### 10. Что такое композиция и наследование?

- **Наследование (Inheritance)** — это механизм, при котором новый класс (наследник) получает поля и методы другого класса (родителя). Это отношение **«является» (IS-A)**. Например, `Car` (Машина) является `Vehicle` (Транспортным средством).
- **Композиция (Composition)** — это механизм, при котором класс содержит в себе экземпляры других классов и делегирует им выполнение работы. Это отношение **«имеет» (HAS-A)**. Например, `Car` имеет `Engine` (Двигатель).

### 11. В каких случаях лучше использовать композицию вместо наследования?

Общая рекомендация — **«предпочитайте композицию наследованию»**. Композицию следует использовать, когда:
- Между классами существует отношение «имеет» (HAS-A), а не «является» (IS-A).
- Вы хотите переиспользовать код, но не хотите жесткой связи с родительским классом, которая присуща наследованию.
- Вам нужно, чтобы поведение можно было легко изменить во время выполнения программы, подставив другую реализацию.

Наследование оправдано только тогда, когда существует истинное, стабильное отношение «является» (IS-A), и подкласс является частным случаем родителя, не нарушая его контракт (принцип LSP).

### 12. Что такое делегирование в ООП?

**Делегирование (Delegation)** — это техника, при которой объект вместо выполнения задачи самостоятельно передает ее другому объекту (своему "делегату"). Это ключевой механизм, лежащий в основе композиции. Например, класс `Car` может делегировать задачу "завестись" объекту `Engine`, вызывая его метод `start()`.

### 13. Как принцип Single Responsibility связан с cohesion?

**Cohesion (Связность)** — это мера того, насколько сильно методы и данные внутри класса связаны друг с другом и сфокусированы на одной задаче. SRP и cohesion тесно связаны: класс, следующий SRP, обладает **высокой связностью (high cohesion)**, потому что все его элементы служат одной цели. Класс, нарушающий SRP, имеет **низкую связность (low cohesion)**, так как его методы и данные относятся к разным, несвязанным концепциям.

### 14. Что произойдёт, если класс имеет несколько причин для изменения?

Если у класса несколько причин для изменения, это приводит к ряду негативных последствий:
- **Хрупкость:** Изменение в одной части класса (например, в логике валидации) может неожиданно сломать другую его часть (например, логику сохранения в БД).
- **Сложность тестирования:** Тестирование одной ответственности требует настройки и мока всех остальных, что усложняет и замедляет тесты.
- **Низкая переиспользуемость:** Вы не сможете использовать логику, скажем, отправки email из этого класса в другом месте, не притащив за собой весь остальной функционал.

### 15. Как SOLID помогает в тестировании кода?

SOLID-принципы значительно упрощают тестирование:
- **SRP:** Классы с одной ответственностью проще тестировать, так как у них меньше зависимостей и сценариев для проверки.
- **DIP:** Зависимость от абстракций (интерфейсов) позволяет легко подменять реальные реализации на **моки (mocks)** или **заглушки (stubs)** в тестах. Это позволяет тестировать класс в изоляции от его внешних зависимостей (баз данных, сетевых вызовов и т.д.).
- **OCP и LSP:** Позволяют легко расширять поведение системы и быть уверенным, что новые подклассы не нарушат работу существующих тестов.

### 16. Как принцип Dependency Inversion связан с Dependency Injection?

**Dependency Inversion Principle (DIP)** — это принцип проектирования, который говорит *что* делать: классы должны зависеть от абстракций, а не от конкретных реализаций.

**Dependency Injection (DI)** — это паттерн, который показывает *как* этого добиться. DI — это способ реализации DIP, при котором зависимости класса не создаются внутри него, а **внедряются (inject)** извне, например, через конструктор.

Таким образом, DI является одним из практических способов выполнения принципа DIP.

### 17. Что такое Law of Demeter (принцип наименьшего знания)?

**Law of Demeter (LoD)**, или **Принцип наименьшего знания**, гласит, что объект должен иметь как можно меньше знаний о других объектах. В частности, метод объекта должен вызывать методы только у:
1.  Самого себя (`this`).
2.  Объектов, переданных ему в качестве параметров.
3.  Объектов, которые он создает.
4.  Своих непосредственных полей (компонентов).

Нарушением считается цепочка вызовов, такая как `a.getB().getC().doSomething()`, потому что объект `a` "знает" о внутренней структуре `b` и `c`.

### 18. Как рефакторить God Object (божественный объект)?

**God Object (Божественный объект)** — это антипаттерн, при котором один класс "знает" и "делает" слишком много, нарушая SRP.

**Рефакторинг** заключается в **декомпозиции** этого класса на несколько меньших, узкоспециализированных классов, каждый из которых будет отвечать за одну область (например, `UserService`, `AuthService`, `PaymentService`, `NotificationService`).

### 19. Как SOLID принципы помогают при расширении функционала?

SOLID-принципы делают систему **открытой для расширения**. Благодаря OCP, вы можете добавить новую функциональность (например, новый тип скидки или новый способ оплаты), просто создав новый класс-реализацию, не изменяя существующий, уже протестированный код. Это снижает риск внесения ошибок в работающую систему.

### 20. Можно ли следовать всем принципам SOLID одновременно?

В идеале — да, и к этому нужно стремиться. Однако на практике могут возникать компромиссы. Например, чрезмерное следование SRP может привести к появлению большого количества мелких классов, что усложнит навигацию по коду. Принципы SOLID — это руководство, а не догма, и их применение требует здравого смысла и баланса.

### 21. Как определить, что класс имеет одну ответственность?

Вот несколько практических признаков:
- Вы можете описать назначение класса **одним предложением без союза "и"**.
- У класса не очень много полей и методов, и они логически связаны.
- Изменения в разных частях системы (например, в формате отчетов и в способе аутентификации) не требуют изменения этого класса.
- Имя класса не содержит слов вроде "Manager", "Handler", "Util", которые часто указывают на размытую ответственность.

### 22. Какие антипаттерны противоречат SOLID принципам?

Многие "плохие" практики проектирования нарушают принципы SOLID. Вот некоторые из них:
- **God Object (Божественный объект):** Нарушает **SRP**, так как концентрирует в себе множество обязанностей.
- **Spaghetti Code (Спагетти-код):** Отсутствие структуры и четких границ ответственности, что противоречит **SRP** и **OCP**.
- **Copy-Paste Programming:** Ведет к дублированию кода и нарушает **DRY** (Don't Repeat Yourself), что часто является следствием несоблюдения **OCP** (неумение расширять, поэтому копируют).
- **Anemic Domain Model (Анемичная модель предметной области):** Классы данных содержат только поля и геттеры/сеттеры, а вся логика вынесена в отдельные сервисы. Это может нарушать **инкапсуляцию** и приводить к разбросу логики, что не способствует **SRP**.
- **Singleton (в некоторых контекстах):** Чрезмерное использование синглтонов может приводить к скрытым зависимостям и сложностям в тестировании, что противоречит идеям **DIP**.
