# Java 17/21: современные фичи языка


### 1. Что нового появилось в Java 17 (LTS)

Java 17 — LTS-релиз (сентябрь 2021), целевая версия после миграций с Java 8/11. Ключевые изменения:

- **Sealed classes** (JEP 409, финализировано) — ограничение иерархии наследования (см. вопрос про sealed).
- **Pattern Matching for instanceof** (JEP 394, финализировано в 16) — проверка типа + привязка переменной одним выражением.
- **Records** (финализированы в 16) — неизменяемые классы-данные (см. раздел 20).
- **Strongly Encapsulated JDK Internals** (JEP 403) — рефлексия во внутренние API JDK (`sun.*`) по умолчанию запрещена; старые библиотеки требуют `--add-opens`.
- **Switch expressions** (финализированы в 14) — `switch` как выражение с `->` и `yield`.
- **Text blocks** (финализированы в 15) — многострочные строки.
- **Removed**: AOT/JIT-компилятор Graal из JDK, апплеты, RMI Activation; `SecurityManager` объявлен deprecated for removal.
- **New Random** API (`RandomGenerator`), macOS ARM64-порт, экспериментальный Vector API.

Практический смысл для прикладного разработчика: меньше boilerplate (records, switch, text blocks), безопаснее код (sealed + pattern matching), строже инкапсуляция JDK.

### 2. Что нового появилось в Java 21 (LTS)

Java 21 — LTS-релиз (сентябрь 2023), крупнейший релиз языка за годы:

- **Virtual Threads** (JEP 444, финализировано) — лёгкие потоки для масштабируемых блокирующих приложений (см. раздел «Многопоточность»).
- **Sequenced Collections** (JEP 431) — интерфейсы `SequencedCollection/List/Set/Map` с `getFirst()/getLast()/reversed()`.
- **Record Patterns** (JEP 440) — деструктуризация record в pattern matching.
- **Pattern Matching for switch** (JEP 441, финализировано) — `switch` по типам, `when`-условия, exhaustiveness.
- **String Templates** (JEP 430, preview) — впоследствии **убраны** из языка (в 2024 Java не пошла дальше preview) — на собесе можно упомянуть, что это preview-эксперимент, не production-фича.
- **Generational ZGC** (JEP 439) — поколенческий режим ZGC.
- **Key encapsulation mechanism** (post-quantum криптография), **Structured Concurrency** и **Scoped Values** — в preview.
- **Deprecation of the Windows 32-bit x86 port**, подготовка к удалению `finalization` (deprecated).

Практический эффект: высоконагруженные блокирующие приложения получают дешёвую конкурентность (virtual threads), язык приобретает выразительный pattern matching.

### 3. Что такое sealed classes и зачем они нужны

**Sealed-класс** (Java 17) — класс, который явно перечисляет своих наследников: `permits`. Наследовать может только перечисленное; сами наследники обязаны быть `final`, `sealed` или `non-sealed`. Это «закрытая» иерархия: компилятор знает **все** возможные подтипы.

```java
public sealed interface Shape permits Circle, Rectangle, Triangle {}
public record Circle(double radius) implements Shape {}          // final по умолчанию у record
public record Rectangle(double w, double h) implements Shape {}
public non-sealed class Polygon implements Shape {}              // открыт для всех
// class Hexagon implements Shape {}  <- ошибка компиляции: нет в permits
```

Зачем это нужно:
- **Доменные модели с конечным набором вариантов** — как enum, но с полями и данными (сумма/перевод/возврат в платёжном домене).
- **Исчерпывающий pattern matching** (см. следующий вопрос): компилятор проверяет, что switch покрыл все подтипы — добавили новый вариант, и все незакрытые switch'и в проекте перестали компилироваться.
- **Инкапсуляция API**: библиотека открывает расширение только там, где хочет.

Sealed-типы + records + pattern matching образуют «алгебраические типы данных» — фундамент для надёжного моделирования состояний (например, `sealed interface OrderState permits New, Paid, Shipped, Cancelled`).

### 4. Что такое Pattern Matching for instanceof (Java 16)

Классическая последовательность «проверь тип — приведи — используй» сжимается в одно выражение с **привязанной переменной**, область видимости которой — только ветка, где условие истинно:

```java
// Было (до Java 16)
if (obj instanceof String) {
    String s = (String) obj;
    System.out.println(s.length());
}

// Стало
if (obj instanceof String s) {
    System.out.println(s.length());   // s — уже приведённая строка
}
// s видна и в негативной ветке, если условие «отрицается» позже:
if (!(obj instanceof String s) || s.isEmpty()) { ... } // корректно: s в scope
```

Плюсы: меньше кода, нет возможности ошибиться с приведением, читаемость. В связке со sealed-типами и switch (следующие вопросы) это превращает обработку полиморфных данных в декларативное описание вариантов. Неглубокая ловушка: переменная-паттерн получает значение только после успешной проверки, поэтому в сложных условиях порядок `instanceof` имеет значение.

### 5. Что такое Pattern Matching for switch (Java 21)

Java 21 финализировала `switch` с паттернами: селектор сравнивается с **типовыми паттернами**, условиями `when` и `null`. Ключевые свойства:

- **Типовые паттерны**: `case Circle c -> ...`;
- **Guard-условия**: `case Rectangle r when r.area() > 100 -> ...`;
- **Null-обработка**: `case null -> ...` (больше не нужен `if (x == null)` перед switch);
- **Исчерпываемость (exhaustiveness)**: если селектор — sealed-тип, компилятор требует покрыть **все** варианты (или иметь `default`);
- **Доминирование**: более общий паттерн (`default`) должен идти после специфичных.

```java
static String describe(Shape shape) {
    return switch (shape) {                    // Shape — sealed interface
        case Circle c        -> "круг r=" + c.radius();
        case Rectangle r when r.w() == r.h() -> "квадрат";
        case Rectangle r     -> "прямоугольник " + r.w() + "x" + r.h();
        case null            -> "нет фигуры";
        case Triangle t      -> "треугольник";
    };  // default не нужен: все подтипы sealed-иерархии покрыты
}
```

Это заменяет цепочки `if-else instanceof` и Visitor-паттерн в простых случаях: обработка всех вариантов модели — в одном месте, а добавление нового подтипа даёт ошибку компиляции во всех неполных switch'ах.

### 6. Что такое record patterns (Java 21)

**Record patterns** — деструктуризация record прямо в паттерне: вместо доступа к компонентам через геттеры вы «распаковываете» значения в переменные. Работает в `instanceof` и в `switch`, поддерживает вложенность.

```java
record Point(int x, int y) {}
record Line(Point start, Point end) {}

static void print(Object obj) {
    if (obj instanceof Line(Point(var x1, var y1), Point(var x2, var y2))) {
        // все координаты распакованы за один шаг, без null-проверок компонентов
        System.out.println("dx=" + (x2 - x1) + ", dy=" + (y2 - y1));
    }
}

static double length(Shape s) {
    return switch (s) {
        case Line(Point(var x1, var y1), Point(var x2, var y2)) ->
            Math.hypot(x2 - x1, y2 - y1);
        default -> 0;
    };
}
```

Record patterns «параюсятся» с sealed-типами: полная декларативная обработка дерева объектов без Visitor. Нюанс: record pattern не совпадает, если record равен `null`; вложенные паттерны позволяют описывать структуры произвольной глубины.
### 7. Что такое switch expressions и чем они отличаются от классического switch

**Switch-выражения** (финализированы в Java 14) — `switch`, который **возвращает значение**. Отличия от старого оператора:

- **Стрелочный синтаксис `->`**: без fall-through, `break` не нужен.
- **Выражение, а не оператор**: результат присваивается переменной.
- **`yield`** — возврат значения из блочного ветвления `case -> { yield value; }`.
- **Исчерпываемость**: для выражения switch по enum/sealed должны быть покрыты все варианты (или `default`) — ошибка компиляции иначе.
- Допускается несколько меток в одном case: `case MON, TUE ->`.

```java
int days = switch (month) {
    case JAN, MAR, MAY, JUL, AUG, OCT, DEC -> 31;
    case APR, JUN, SEP, NOV                -> 30;
    case FEB -> {
        int y = year;
        yield (y % 4 == 0 && y % 100 != 0) || y % 400 == 0 ? 29 : 28; // блок + yield
    }
};  // switch как выражение: обязано покрыть все enum-значения

// Старый синтаксис тоже улучшен: multi-label без fall-through
switch (code) {
    case 200, 201 -> log.info("OK");
    case 404      -> log.warn("Not Found");
    default       -> log.error("Unknown");
}
```

Практическая ценность: исчезает целый класс ошибок (забытый `break`, случайный fall-through), компилятор ловит неполную обработку enum, код «маппинга значения» становится однострочным.

### 8. Что такое text blocks и как с ними работать

**Text blocks** (финализированы в Java 15) — многострочные строковые литералы в тройных кавычках `"""`. Компилятор: определяет **общий отступ** по закрывающему разделителю, убирает его, обрабатывает escape-последовательности; полезные управляющие последовательности: `\s` (явный пробел), `\<перевод строки>` (продолжение строки без переноса).

```java
String json = """
    {
      "name": "Anna",
      "role": "admin"
    }""";
// Отступ считается от позиции закрывающих """: JSON без ведущих пробелов

String query = """
    SELECT u.name, COUNT(o.id)
    FROM users u
    JOIN orders o ON o.user_id = u.id
    WHERE u.created_at > ?
      AND u.status = 'ACTIVE'\
    GROUP BY u.name
    """;
// Обратный слэш в конце строки склеивает строки: AND ... GROUP BY в одну строку

String html = """
    <html>\
      <body>Hello</body>\
    </html>""";   // однострочный результат
```

Применение: SQL, JSON, HTML-шаблоны, ожидаемые ответы в тестах (`assertEquals(текст-блок, actual)`). Тонкость: инцидентный пробел важен — позиция закрывающих `"""` определяет, сколько отступа срежется; `\s` сохраняет значимый пробел перед переносом.

### 9. Что такое var (local variable type inference) и когда его использовать

**`var`** (Java 10) — вывод типа **локальной** переменной: компилятор выводит тип из инициализатора. Это не «динамический тип» — тип строго статический, просто не продублирован текстом.

```java
var users = new HashMap<UUID, List<Order>>();   // очевидно из правой части — var уместен
for (var entry : users.entrySet()) { ... }      // тип длинный, но однозначный
var now = LocalDateTime.now();

User user = userService.find(id);  // тип важен слева — лучше явно
var result = userService.process(input); // тип справа невидим — var скрывает смысл
```

Рекомендации (совпадают с гайдами OpenJDK/Google): используйте `var`, когда тип очевиден из правой части (`new`, литерал, фабрика с именем типа) или когда явный тип — простыня (`Map<String, List<CompletableFuture<Order>>>`). Не используйте, когда инициализатор не показывает тип (вызов метода с невнятным именем, цепочки, ternary с разными типами). Цель — читаемость, а не «меньше букв».

### 10. Каковы ограничения var

`var` работает **только** для локальных переменных с инициализатором. Нельзя:

- **Поля класса** — тип поля должен быть объявлен явно;
- **Параметры методов** и возвращаемые типы (в Java; в record/lambda-параметрах — можно как в `(var x, var y) -> ...`);
- **Без инициализатора**: `var x;` — ошибка (нечего выводить);
- **`var x = null;`** — тип неизвестен;
- **Массивы**: `var arr = {1, 2, 3};` — нельзя, но `var arr = new int[]{1,2,3};` — можно;
- **Лямбды и ссылки на методы** как инициализатор: `var f = () -> 1;` — нельзя (неоднозначно), нужен явный функциональный тип;
- **try-with-resources** — можно; **catch-параметр** — можно (Java 11? нет: catch — нельзя, только с Java 10 var в ресурсах и локальных). Точнее: `catch (var ex)` не поддерживается, переменная исключения объявляется как раньше.

```java
var list = new ArrayList<String>(); // OK: тип ArrayList<String> (не List!)
list.add("a");
var copy = list;                    // копия ССЫЛКИ, тип ArrayList<String>

var stream = list.stream();         // OK
// var nums = {1, 2};               // ошибка компиляции
// var lambda = s -> s.length();    // ошибка: нужен явный тип Function<String, Integer>
```

Важная ловушка: `var list = new ArrayList<String>()` даёт **статический тип ArrayList**, а не `List` — при рефакторинге на интерфейс это может скрыть зависимость от конкретной реализации.

### 11. Что такое Optional и как его правильно использовать

**`Optional<T>`** (Java 8) — контейнер, явно выражающий в типе возможность отсутствия значения, вместо возврата `null` и NPE в рантайме. `Optional` — часть **API-контракта**: метод, возвращающий `Optional`, честно говорит «значения может не быть, обработай это».

Корректные паттерны:

```java
// 1. Возврат из репозитория/поиска
public Optional<User> findByEmail(String email) { ... }

// 2. Чтение с дефолтом
String city = user.getAddress()
                  .map(Address::city)
                  .orElse("unknown");

// 3. Действие только при наличии
user.getPhone().ifPresent(sms::send);

// 4. Действие с двумя ветками
findById(id).ifPresentOrElse(this::activate,
                             () -> log.warn("Пользователь {} не найден", id));

// 5. Ошибка, если нет
User u = findById(id).orElseThrow(() -> new NotFoundException(id));
```

Метод `Optional` создают: `of(value)` (не null, иначе NPE), `ofNullable(value)`, `empty()`. Он **иммутабелен** и безопасен для передачи. Основная идея: `Optional` в цепочках `map/flatMap/filter` заменяет каскад null-проверок и делает поток данных явным.

### 12. В чём разница между orElse() и orElseGet()

Принципиальная разница — **ленивость**:

- **`orElse(T other)`** принимает готовое значение: выражение-аргумент вычисляется **всегда**, даже когда Optional не пуст.
- **`orElseGet(Supplier<T>)`** принимает лямбду: вызывается **только** если значения нет.

```java
Optional<String> name = Optional.of("Anna");

// ПЛОХО: expensiveFallback() выполнится всегда, хотя name есть!
String a = name.orElse(expensiveFallback());

// ХОРОШО: fallback вызовется только при пустом Optional
String b = name.orElseGet(this::expensiveFallback);

// Проверяемо:
Optional<Integer> empty = Optional.empty();
Integer x = empty.orElse(create());  // в логе: "create() вызван"
Integer y = empty.orElseGet(() -> create()); // то же, но для непустого — не вызовется
```

Практическое правило: константа или уже вычисленное значение — `orElse`; anything вычисляемое (вызов метода, запрос в БД, конструирование объекта) — **`orElseGet`**. `orElse` с вызовом тяжёлого метода — классическая скрытая деградация производительности в проде.

### 13. Как работают map, flatMap, filter, or и ifPresentOrElse у Optional

`Optional` — монада с стандартным набором преобразований:

- **`map(Function<T,U>)`** — преобразовать значение, если есть (аналог `Stream.map` для 0/1 элемента);
- **`flatMap(Function<T,Optional<U>>)`** — преобразование, которое само возвращает Optional (не даёт `Optional<Optional<T>>`);
- **`filter(Predicate)`** — оставить значение, если предикат истинен;
- **`or(Supplier<Optional<T>>)`** (Java 9) — альтернативный источник, если текущий пуст (цепочка fallback'ов);
- **`ifPresent(Consumer)`** / **`ifPresentOrElse(Consumer, Runnable)`** (Java 9) — побочный эффект при наличии/отсутствии;
- **`stream()`** (Java 9) — превратить `Optional` в `Stream` из 0/1 элементов — удобно внутри flatMap по потоку.

```java
// Цепочка fallback'ов: кэш -> БД -> внешний сервис
Optional<Profile> p = cache.get(id)
    .or(() -> repository.find(id))
    .or(() -> api.fetch(id));

// flatMap: метод уже возвращает Optional
Optional<String> email = findById(id)
    .flatMap(User::getPrimaryAccount)   // возвращает Optional<Account>
    .map(Account::email);

// Optional в стриме: пропустить «дыры»
List<String> phones = ids.stream()
    .map(this::phoneById)      // Stream<Optional<String>>
    .flatMap(Optional::stream) // только существующие
    .toList();
```

Правило выбора: преобразование в обычное значение — `map`; преобразование, возвращающее Optional — `flatMap`.

### 14. Какие антипаттерны использования Optional вы знаете

`Optional` часто используют неправильно, сводя пользу на нет:

1. **`optional.get()` без проверки** — `NoSuchElementException`, тот же NPE, но с другим именем. `get()` — наследие Java 8, концептуально renamed в `orElseThrow()`.
2. **`isPresent() + get()`** — императивный код вместо `map/ifPresent/orElse`: смысл Optional теряется.
3. **Optional в полях класса** — поля должны быть nullable-примитивами или гарантированно заполнены; `Optional` не сериализуем, добавляет аллокации. В доменной модели пустоту выражают `null` + документация или null-объект.
4. **Optional в параметрах метода** — делает API запутаннее; лучше перегрузки или nullability-аннотации.
5. **`Optional.of(x)` на возможном null** — мгновенный NPE; нужен `ofNullable`.
6. **Возврат `null` из метода с Optional** — нарушение контракта (нужен `Optional.empty()`).
7. **Optional для коллекций** — вместо `Optional<List<T>>` возвращайте пустую коллекцию (`List.of()`).
8. **Оборачивание в Optional внутри горячих циклов** — лишние объекты; на критичном пути — проверки на null.

```java
// Антипаттерн
if (userOpt.isPresent()) { return userOpt.get().name(); } else { return "n/a"; }

// Идиоматично
return userOpt.map(User::name).orElse("n/a");
```

### 15. Чем List.of() отличается от Arrays.asList()

Оба создают «фиксированные» списки, но с разными свойствами:

| Свойство | `List.of(...)` (Java 9) | `Arrays.asList(...)` |
|---|---|---|
| Изменение размера (add/remove) | `UnsupportedOperationException` | `UnsupportedOperationException` |
| `set(index, value)` | Запрещён — **полностью иммутабелен** | Разрешён — **изменяет** исходный массив |
| `null` элементы | Запрещены (`NullPointerException`) | Разрешены |
| Хранение | Своя компактная структура `ImmutableCollections` | Обёртка над переданным массивом |
| Реакция на изменение исходного массива | Независим | Список «видит» изменения массива |

```java
String[] arr = {"a", "b"};
List<String> fromArray = Arrays.asList(arr);
arr[0] = "X";
System.out.println(fromArray.get(0));  // "X" — список ссылается на массив!

List<String> immutable = List.of("a", "b");
// immutable.set(0, "X");  // UnsupportedOperationException
// List.of("a", null);     // NPE при создании
```

Семейство фабрик: `Set.of`, `Map.of` (до 10 пар), `Map.ofEntries(entry(...))` — все полностью иммутабельны, запрещают null, идеальны как константы и дефолты. Копии: `List.copyOf(collection)` (если источник уже immutable — вернёт его же без копирования), `stream().toList()`.

### 16. Чем Stream.toList() (Java 16) отличается от collect(Collectors.toList())

Java 16 добавила короткий терминальный метод `toList()`:

- **`stream.toList()`** — возвращает **неизменяемый** список (аналог `List.copyOf`); нельзя `add/set`; не гарантирует конкретный класс реализации; null-элементы допустимы (в отличие от `List.of`).
- **`collect(Collectors.toList())`** — возвращает изменяемый `ArrayList`, поддерживающий последующие модификации.
- **`collect(Collectors.toUnmodifiableList())`** — неизменяемый список, выбрасывает NPE, если в потоке был null (семантика `List.of`).

```java
List<String> a = stream.filter(Objects::nonNull).toList();     // immutable
List<String> b = stream.collect(Collectors.toList());          // ArrayList, изменяемый
a.add("x");   // UnsupportedOperationException
b.add("x");   // OK
```

Практика: по умолчанию используйте `toList()` — короче и безопаснее (никто не испортит коллекцию мутацией); если после стрима нужно модифицировать список осознанно — `collect(toList())` или обёртка `new ArrayList<>(stream.toList())`.

### 17. Что такое SequencedCollection (Java 21)

Java 21 закрыла многолетнюю дыру API коллекций: не существовало единого интерфейса для коллекций **с определённым порядком встречи**. Теперь:

- **`SequencedCollection<E>`** — `getFirst()`, `getLast()`, `addFirst(E)`, `addLast(E)`, `removeFirst()`, `removeLast()` + **`reversed()`** — реверсивное представление (живой view, а не копия);
- **`SequencedSet`** (дополнительно гарантирует уникальность) и **`SequencedMap`** — `putFirst/putLast`, `pollFirstEntry/pollLastEntry`, `sequencedKeySet()`, `reversed()`.

```java
List<Integer> list = new ArrayList<>(List.of(1, 2, 3));
list.addFirst(0);                    // раньше: list.add(0, 0)
list.getLast();                      // раньше: list.get(list.size() - 1)
System.out.println(list.reversed()); // [3, 2, 1, 0] — view: изменения синхронны

LinkedHashMap<String, Integer> map = new LinkedHashMap<>();
map.putFirst("first", 1);
System.out.println(map.reversed());  // реверсивный порядок обхода
```

До Java 21 операции «первый/последний» были разбросаны: у `List` — через индексы, у `Deque` — свои методы, у `LinkedHashSet` — только через iterator hack. `reversed()` заменяет `descendingIterator()`, `Collections.reverse`-копии и `Lists.reverse` из Guava. Для `ImmutableCollections` (`List.of`) `reversed()` работает без копирования.

### 18. Какие полезные мелкие улучшения API появились в Java 9–17

Мелочи, которые часто спрашивают «в связке» с фичами:

- **Helpful NullPointerExceptions** (Java 14): NPE-сообщение говорит, что именно null: `Cannot invoke "String.length()" because the return value of "User.name()" is null`.
- **String API**: `isBlank()`, `strip()/stripLeading()/stripTrailing()` (unicode-aware, в отличие от trim), `lines()` (Stream по строкам), `repeat(n)`, `chars()`; Java 12: `indent(n)`, `transform(Function)`; Java 15: `formatted(args)` (аналог `format`, но на строке); Java 21: `indexOf(str, fromIndex)` улучшения не считаются — стоит упомянуть `String.split` с limit и `isEmpty()` (давно) как базис.
- **Files.readString / writeString** (Java 11) — чтение/запись файла в строку в одну строку кода.
- **Collection.toArray(IntFunction)** (Java 11): `list.toArray(String[]::new)` без каста.
- **Predicate.not(...)** (Java 11): `.filter(Predicate.not(String::isBlank))` вместо `x -> !x.isBlank()`.
- **CompletableFuture improvements** (Java 9): `orTimeout`, `completeOnTimeout`, `delayedExecutor`.
- **InputStream.transferTo(OutputStream)** (Java 9), **Process API** обновлён, **HttpClient** новый (Java 11, `java.net.http`).
- **Deprecations**: `new Integer(...)` (Java 9, используйте `Integer.valueOf`), ThreadGroup-методы, `SecurityManager`.

```java
String text = Files.readString(Path.of("config.json")); // одна строка вместо чтения в цикле
List<String> lines = text.lines().filter(Predicate.not(String::isBlank)).toList();
String s = "  hi  ".strip();               // "hi"
String report = "Пользователь %s: %d".formatted(name, count);
```
