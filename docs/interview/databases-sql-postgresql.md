# Базы данных / SQL / PostgreSQL

### 1. Для чего нужны индексы

Индексы в базах данных — это специальные структуры данных, которые ускоряют операции поиска, сортировки и соединения строк, позволяя СУБД находить нужные данные без полного сканирования таблицы. По сути, индекс работает как алфавитный указатель в книге: вместо того чтобы перелистывать все страницы в поисках нужного термина, вы сразу открываете нужную страницу.

Основное назначение индексов — **повышение производительности запросов** (особенно `SELECT`, `UPDATE`, `DELETE` с условиями `WHERE`, а также `JOIN` и `ORDER BY`). Без индекса СУБД вынуждена выполнять последовательное сканирование (`Seq Scan`), проверяя каждую строку таблицы, что при больших объёмах данных может быть крайне медленно. Индекс позволяет сократить количество читаемых страниц до O(log n), где n — число строк.

Пример создания индекса и проверки его работы (таблица `orders` из `test.session.sql`):

```sql
-- Индекс по времени создания заказа (частый фильтр по диапазону)
CREATE INDEX idx_orders_created_at ON orders (created_at);

-- До индекса: Seq Scan по всей таблице (500 000 строк)
-- После: Bitmap Index Scan / Index Scan по узкому диапазону
EXPLAIN ANALYZE
SELECT id, total_amount
FROM orders
WHERE created_at > NOW() - INTERVAL '1 month';
```

### 2. Как работает B-tree индекс

B-tree (Balanced tree) — наиболее распространённый тип индекса в реляционных СУБД. Это сбалансированное дерево, в котором все листовые узлы находятся на одном уровне (одинаковой глубине от корня), что гарантирует примерно одинаковое время доступа к любому значению.

Структура B-tree индекса:
- **Корневая страница (root page)**: содержит граничные значения и указатели на дочерние внутренние страницы.
- **Внутренние страницы (internal pages)**: промежуточные уровни, каждый узел содержит ключи и указатели, направляющие поиск к нужному листу.
- **Листовые страницы (leaf pages)**: хранят фактические значения индексированного столбца и указатели на строки таблицы (row IDs). Листовые страницы связаны между собой, что делает эффективными диапазонные запросы (`BETWEEN`, `>`, `<`).

Поиск по B-tree начинается с корня, на каждом уровне выбирается правильный указатель на основе сравниваемого значения, и так до листовой страницы. Сложность поиска — **O(log n)**. Например, для миллионов строк дерево обычно имеет глубину 3–4 уровня, то есть для поиска нужно прочитать всего 3–4 страницы. B-tree поддерживает как точечный поиск (`WHERE id = 42`), так и диапазонный (`WHERE age BETWEEN 25 AND 35`), а также сортировку (`ORDER BY`).


### 3. Что такое составной индекс

Составной (композитный, многоколоночный) индекс — это индекс, построенный по **двум или более столбцам** таблицы. В B-tree такого индекса ключи сортируются сначала по первому столбцу, затем внутри одинаковых значений первого столбца — по второму и т.д.. Например, для индекса `CREATE INDEX idx ON table (a, b, c)` записи упорядочены по `a`, затем по `b`, затем по `c`.

Составной индекс может быть использован для запросов, которые фильтруют по **префиксу** ключа: по `a`, по `(a, b)`, по `(a, b, c)`. Запрос, который фильтрует только по `b` или только по `c`, обычно **не может** эффективно использовать этот индекс (без использования дополнительных механизмов, таких как index skip scan). Это правило называют **«левым префиксом»**.

Составные индексы полезны, когда запросы часто фильтруют или сортируют по комбинации столбцов. Однако не рекомендуется создавать индексы по более чем 3–4 столбцам, так как они занимают много места и редко бывают полезны, если только рабочая нагрузка не очень специфична.

Пример на таблице `order_items` (фильтр по `order_id` + сортировка по `quantity`):

```sql
-- Составной индекс: сначала по order_id, затем по quantity
CREATE INDEX idx_oi_order_qty ON order_items (order_id, quantity);

-- Использует индекс по префиксу (order_id) + сортировка без extra Sort
SELECT product_id, quantity
FROM order_items
WHERE order_id = 1234
ORDER BY quantity DESC;

-- ❌ Этот запрос НЕ использует idx_oi_order_qty эффективно
--    (фильтрует только по quantity — не левый префикс)
SELECT order_id, quantity
FROM order_items
WHERE quantity > 5;
```

### 4. Когда стоит создавать индекс

Индекс стоит создавать, когда:
- **Столбец часто используется в условиях `WHERE`**, особенно с высокой селективностью (когда условие отбирает небольшую долю строк).
- **Столбец используется в `JOIN`** для соединения таблиц (внешние ключи).
- **Столбец используется в `ORDER BY`** или `GROUP BY`, чтобы избежать сортировки.
- **Запросы выполняются часто** и их ускорение критично для приложения.
- **Таблица большая**, и полное сканирование становится дорогим.

Индекс особенно полезен, когда запрос возвращает лишь небольшую часть строк (`high selectivity`). Для маленьких таблиц (несколько тысяч строк) индекс может быть не нужен — последовательное сканирование и так быстрое.


### 5. Какие недостатки индексов

Индексы имеют ряд недостатков:
- **Занимают дисковое пространство**: индекс — это отдельная структура, которая может занимать значительный объём.
- **Замедляют операции записи (`INSERT`, `UPDATE`, `DELETE`)**: при каждом изменении данных в индексированном столбце СУБД должна обновить и сам индекс, что создаёт дополнительную нагрузку.
- **Требуют обслуживания**: индексы нужно периодически перестраивать (например, `REINDEX` или `VACUUM` в PostgreSQL), чтобы избежать их раздувания.
- **Могут не использоваться**: планировщик может проигнорировать индекс, если посчитает, что полное сканирование дешевле (например, при низкой селективности).
- **Увеличивают сложность**: слишком много индексов усложняет администрирование и может ухудшить общую производительность.


### 6. Что такое кардинальность индекса

**Кардинальность (cardinality)** — это количество **уникальных значений** в индексированном столбце. Высокая кардинальность означает, что в столбце много разных значений (например, `email`, `id`), низкая — что значений мало и они часто повторяются (например, `пол`, `статус`).

Кардинальность тесно связана с **селективностью (selectivity)** — долей строк, удовлетворяющих условию. Чем выше кардинальность, тем выше селективность и тем полезнее индекс для точечных запросов. Индекс по столбцу с низкой кардинальностью (например, `boolean`) часто бесполезен, так как даже при поиске по значению будет возвращена большая часть таблицы, и полное сканирование окажется быстрее. Планировщик запросов использует статистику кардинальности (собираемую через `ANALYZE`) для оценки стоимости различных планов.

Проверить кардинальность и селективность на реальных данных:

```sql
-- Сколько уникальных значений в столбце (после ANALYZE)
SELECT count(DISTINCT status) AS unique_statuses,
       count(*)               AS total_rows,
       count(DISTINCT status) * 1.0 / count(*) AS selectivity
FROM orders;
-- status: 4 уникальных значения из 500 000 строк → selectivity ≈ 0.000008
-- → индекс по status практически бесполезен (возвращает ~25% таблицы)

-- Сравните со столбцом высокой кардинальности:
SELECT count(DISTINCT user_id) * 1.0 / count(*) AS user_id_selectivity
FROM orders;
-- user_id: почти 100 000 уникальных значений → высокий индекс полезен
```

### 7. Какие типы JOIN существуют

Основные типы JOIN в SQL:
- **`INNER JOIN`** (или просто `JOIN`): возвращает только те строки, для которых есть совпадение в **обеих** таблицах.
- **`LEFT JOIN`** (`LEFT OUTER JOIN`): возвращает **все строки из левой таблицы** и совпадающие строки из правой; если совпадения нет, правая часть заполняется `NULL`.
- **`RIGHT JOIN`** (`RIGHT OUTER JOIN`): возвращает все строки из **правой таблицы** и совпадающие из левой; несовпадающие левые строки заполняются `NULL`.
- **`FULL JOIN`** (`FULL OUTER JOIN`): возвращает все строки из **обеих таблиц**, заполняя `NULL` там, где нет совпадения.
- **`CROSS JOIN`**: возвращает **декартово произведение** двух таблиц (каждая строка одной соединяется с каждой строкой другой).
- **`SELF JOIN`**: соединение таблицы с самой собой (частный случай, не отдельный синтаксис).

Примеры на таблицах `users` и `orders`:

```sql
-- INNER JOIN: только пользователи, у которых есть заказы
SELECT u.username, o.total_amount
FROM users u
JOIN orders o ON u.id = o.user_id;

-- LEFT JOIN: все пользователи, включая тех, у кого нет заказов (NULL в orders)
SELECT u.username, o.total_amount
FROM users u
LEFT JOIN orders o ON u.id = o.user_id;

-- CROSS JOIN: декартово произведение (каждый пользователь × каждый заказ)
-- Используется редко, например для генерации сетки данных
SELECT u.username, o.id AS order_id
FROM users u
CROSS JOIN orders o;
```

### 8. В чём разница между INNER JOIN и LEFT JOIN

- **`INNER JOIN`** возвращает только те строки, которые имеют совпадение в **обеих** соединяемых таблицах. Строки без совпадения отбрасываются.
- **`LEFT JOIN`** возвращает **все строки из левой таблицы**, даже если для них нет совпадения в правой. Для таких строк столбцы правой таблицы заполняются `NULL`.

Ключевое практическое следствие: если в `LEFT JOIN` добавить условие на правую таблицу в `WHERE` (например, `WHERE right_table.column = 'value'`), это фактически превратит `LEFT JOIN` в `INNER JOIN`, так как строки с `NULL` в правой части не пройдут фильтр. Чтобы сохранить семантику `LEFT JOIN`, условия на правую таблицу нужно размещать в секции `ON`, а не `WHERE`.

Демонстрация на `users` / `orders` (найти пользователей, у которых есть заказы со статусом `PAID`, **включая** пользователей без таких заказов):

```sql
-- ❌ Неправильно: условие в WHERE — превращает LEFT JOIN в INNER JOIN,
--    пользователи без PAID-заказов пропадут из результата
SELECT u.username, o.id
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
WHERE o.status = 'PAID';

-- ✅ Правильно: условие на правую таблицу в ON —
--    пользователи без PAID-заказов останутся (o.id = NULL)
SELECT u.username, o.id
FROM users u
LEFT JOIN orders o ON u.id = o.user_id AND o.status = 'PAID';
```

### 9. Что лучше: JOIN или подзапрос

Однозначного ответа нет — оба инструмента имеют свои области применения, и современные СУБД (включая PostgreSQL) часто оптимизируют их одинаково, преобразуя подзапросы в соединения (или наоборот).

- **`JOIN`** обычно предпочтительнее, когда нужно **объединить данные из нескольких таблиц** и вернуть столбцы из обеих. Он часто более читаем и лучше оптимизируется.
- **Подзапрос** (в `SELECT`, `WHERE` или `FROM`) удобен, когда:
  - Нужно вычислить **агрегатное значение** для фильтрации (`WHERE salary > (SELECT AVG(salary) FROM employees)`).
  - Нужно проверить **существование** (`EXISTS` / `NOT EXISTS`) — часто эффективнее, чем `JOIN` с `DISTINCT`.
  - Запрос логически проще выразить через подзапрос.

С точки зрения производительности: **коррелированные подзапросы** (см. вопрос 10) могут выполняться медленно, так как выполняются для каждой строки внешнего запроса. Некоррелированные подзапросы обычно оптимизируются хорошо. В PostgreSQL планировщик часто переписывает подзапросы в соединения, поэтому разница может быть незначительной. Рекомендуется **измерять** производительность через `EXPLAIN ANALYZE`.


### 10. Что такое коррелированный подзапрос

**Коррелированный подзапрос (correlated subquery)** — это подзапрос, который ссылается на столбцы из **внешнего запроса**. В отличие от обычного (некоррелированного) подзапроса, который вычисляется один раз, коррелированный подзапрос **выполняется для каждой строки** внешнего запроса (концептуально). Пример:

```sql
SELECT e.name
FROM employees e
WHERE e.salary > (SELECT AVG(salary) FROM employees WHERE department_id = e.department_id);
```

Здесь подзапрос ссылается на `e.department_id` из внешнего запроса, поэтому средняя зарплата вычисляется для каждого отдела. Коррелированные подзапросы могут быть неэффективными на больших данных, но иногда их можно переписать через `JOIN` с агрегацией или оконные функции для повышения производительности.


### 11. В чём разница между WHERE и HAVING

- **`WHERE`** фильтрует **отдельные строки** **до** группировки (до `GROUP BY`). Он не может содержать агрегатные функции (`SUM`, `COUNT`, `AVG` и т.д.).
- **`HAVING`** фильтрует **сгруппированные результаты** **после** `GROUP BY`. Он применяется к результатам агрегатных функций и может содержать их.

Порядок выполнения: `FROM` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `ORDER BY`. Таким образом, `WHERE` ограничивает набор строк, попадающих в группировку, а `HAVING` — какие группы останутся в результате.

Пример на `orders`: суммарный оборот по категориям, только по оплаченным заказам и только категории с оборотом выше 10 000:

```sql
SELECT p.category,
       SUM(oi.price_at_moment * oi.quantity) AS revenue
FROM order_items oi
JOIN orders   o ON oi.order_id = o.id
JOIN products p ON oi.product_id = p.id
WHERE o.status = 'PAID'                 -- WHERE: фильтрует строки ДО группировки
GROUP BY p.category
HAVING SUM(oi.price_at_moment * oi.quantity) > 10000;  -- HAVING: фильтрует группы ПОСЛЕ
```

### 12. Что делает GROUP BY

**`GROUP BY`** группирует строки, имеющие одинаковые значения в указанных столбцах, в **одну строку результата**. Обычно используется вместе с агрегатными функциями (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`), которые вычисляются для каждой группы. Например:

```sql
SELECT department_id, COUNT(*) AS employee_count
FROM employees
GROUP BY department_id;
```

Этот запрос вернёт количество сотрудников в каждом отделе. Все неагрегированные столбцы в `SELECT` должны быть перечислены в `GROUP BY` (или быть функционально зависимыми от них).


### 13. Когда использовать HAVING

`HAVING` используется, когда нужно **отфильтровать результаты агрегации** после `GROUP BY`. Например, найти отделы, где средняя зарплата превышает 50000:

```sql
SELECT department_id, AVG(salary) AS avg_salary
FROM employees
GROUP BY department_id
HAVING AVG(salary) > 50000;
```

`HAVING` также может использоваться без `GROUP BY` (тогда он фильтрует результат агрегации по всей таблице), но это менее распространено. Если условие не содержит агрегатных функций и применяется к отдельным строкам, следует использовать `WHERE` — это эффективнее, так как фильтрация происходит раньше.


### 14. Что такое оконные функции (Window Functions)

**Оконные функции** — это функции, которые выполняют вычисления над набором строк, связанных с текущей строкой, **не сворачивая** результат в одну строку (в отличие от `GROUP BY`). Каждая строка сохраняет свою индивидуальность, но при этом получает дополнительное вычисленное значение.

Синтаксис: `function_name(...) OVER (PARTITION BY ... ORDER BY ...)`. `PARTITION BY` делит строки на группы (окна), а `ORDER BY` определяет порядок внутри окна. Оконные функции позволяют вычислять ранги, скользящие средние, нарастающие итоги, сравнивать значения с предыдущей/следующей строкой (`LAG`/`LEAD`) и многое другое. Они являются мощным инструментом аналитики, позволяющим избежать сложных самосоединений и подзапросов.

Пример: нарастающий оборот (running total) по дням и средняя сумма заказа за последние 7 дней:

```sql
SELECT
    date_trunc('day', created_at) AS day,
    SUM(total_amount) AS daily_revenue,
    SUM(SUM(total_amount)) OVER (ORDER BY date_trunc('day', created_at)) AS running_total,
    AVG(SUM(total_amount)) OVER (
        ORDER BY date_trunc('day', created_at)
        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
    ) AS avg_revenue_7d
FROM orders
WHERE status = 'PAID'
GROUP BY date_trunc('day', created_at)
ORDER BY day;
```

### 15. Что делает ROW_NUMBER()

**`ROW_NUMBER()`** — оконная функция, которая присваивает каждой строке **уникальный последовательный номер** в рамках окна, определяемого `OVER (ORDER BY ...)`. Нумерация начинается с 1 и продолжается без пропусков, даже если значения в `ORDER BY` совпадают (дубликаты получают разные номера).

Пример:
```sql
SELECT name, salary,
       ROW_NUMBER() OVER (ORDER BY salary DESC) AS row_num
FROM employees;
```
Этот запрос пронумерует сотрудников по убыванию зарплаты: самый высокооплачиваемый получит 1, следующий — 2 и т.д., даже если у двух сотрудников зарплата одинакова.


### 16. Что делает RANK() и DENSE_RANK()

Обе функции присваивают ранги на основе `ORDER BY` в окне, но по-разному обрабатывают **совпадающие значения (ties)**:

- **`RANK()`**: при совпадении значений присваивает **одинаковый ранг**, но следующий ранг **пропускается**. Например, если два сотрудника делят 1-е место, следующий получит 3-й ранг (1, 1, 3, ...).
- **`DENSE_RANK()`**: при совпадении значений также присваивает одинаковый ранг, но **не пропускает** следующий номер. В примере выше следующий получит 2-й ранг (1, 1, 2, ...).

`ROW_NUMBER()` всегда даёт уникальные номера без повторов. Выбор функции зависит от бизнес-требований: нужен ли «плотный» рейтинг или с пропусками.

Пример (топ пользователей по сумме заказов, наглядно видно различие рангов при равных значениях):

```sql
SELECT
    u.username,
    SUM(o.total_amount) AS total_spent,
    ROW_NUMBER()   OVER (ORDER BY SUM(o.total_amount) DESC) AS row_num,
    RANK()         OVER (ORDER BY SUM(o.total_amount) DESC) AS rank,
    DENSE_RANK()   OVER (ORDER BY SUM(o.total_amount) DESC) AS dense_rank
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE o.status = 'PAID'
GROUP BY u.username
ORDER BY total_spent DESC
LIMIT 10;
```

Если у двух пользователей сумма одинакова: `RANK` выдаст `1, 1, 3`, а `DENSE_RANK` — `1, 1, 2`.

### 17. Как работает MVCC в PostgreSQL

**MVCC (Multi-Version Concurrency Control)** — это механизм управления параллелизмом, который позволяет нескольким транзакциям работать с данными одновременно, **не блокируя** друг друга. В отличие от традиционных СУБД, использующих блокировки, PostgreSQL создаёт **множество версий** каждой строки.

Когда транзакция изменяет (`UPDATE`) или удаляет (`DELETE`) строку, PostgreSQL **не перезаписывает** существующую строку, а создаёт **новую версию** (для `UPDATE`) или помечает старую как удалённую (для `DELETE`). Старая версия остаётся физически в таблице, пока её не удалит `VACUUM`.

Каждая транзакция видит **снимок (snapshot)** базы данных на определённый момент времени. Снимок определяется номерами транзакций (XID): транзакция видит только те версии строк, которые были закоммичены **до** её начала (в зависимости от уровня изоляции).

Главное преимущество MVCC: **чтение никогда не блокирует запись, а запись никогда не блокирует чтение**. Это обеспечивает высокую степень параллелизма и предсказуемое время отклика. Плата за это — необходимость регулярного `VACUUM` для очистки «мёртвых» версий строк.

Демонстрация (две сессии, таблица `orders`):

```sql
-- Сессия A
BEGIN;
SELECT total_amount FROM orders WHERE id = 1;   -- видит, например, 100.00
-- (ждём, пока Сессия B сделает UPDATE, но тот ещё не закоммитил)

-- Сессия B
BEGIN;
UPDATE orders SET total_amount = 999.99 WHERE id = 1;   -- создаёт новую версию, A этого не видит
-- SELECT в Сессии A всё ещё вернёт 100.00 (snapshot не изменился)
ROLLBACK;  -- откатываем, чтобы не испортить данные

-- Сессия A
COMMIT;
-- После COMMIT в Сессии B и нового BEGIN в A — будет видно 100.00 (откат),
-- а при COMMIT обновления — 999.99.
```

Проверить число версий строки до VACUUM:

```sql
SELECT id, xmin, xmax   -- xmin = xid создателя, xmax = xid удалителя (0, если активна)
FROM orders
WHERE id = 1;
```

### 18. Что такое VACUUM в PostgreSQL

**`VACUUM`** — это служебная команда PostgreSQL, которая выполняет «сборку мусора»: удаляет физически **мёртвые версии строк** (dead tuples), которые больше не видны ни одной активной транзакции, и освобождает занимаемое ими место для повторного использования.

Зачем нужен `VACUUM`:
- **Восстановление дискового пространства**: без него таблицы и индексы будут бесконечно расти, даже если строки удаляются или обновляются.
- **Обновление статистики**: `VACUUM` (вместе с `ANALYZE`) обновляет статистику, используемую планировщиком запросов.
- **Обновление visibility map**: ускоряет index-only scans.
- **Защита от wraparound XID**: предотвращает исчерпание номеров транзакций, которое может привести к остановке базы.

`VACUUM` бывает **стандартным** (работает параллельно с другими операциями, но не возвращает место ОС, а только помечает его для повторного использования) и **`VACUUM FULL`** (полностью перестраивает таблицу, возвращает место ОС, но требует эксклюзивной блокировки и работает медленно). Обычно `VACUUM` запускается автоматически демоном **autovacuum**, но может выполняться и вручную.

Замерить эффект на `orders` (таблица с большим числом UPDATE/DELETE):

```sql
-- До VACUUM: видим «раздутый» размер и количество мёртвых строк
SELECT
    relname,
    pg_size_pretty(pg_total_relation_size(relid)) AS total_size,
    n_dead_tup,
    n_live_tup
FROM pg_stat_user_tables
WHERE relname = 'orders';

-- Ручной VACUUM (стандартный, без блокировки)
VACUUM orders;

-- После VACUUM: n_dead_tup → 0, размер может уменьшиться
-- (но место возвращается в free space внутри файла, не в ОС — для этого нужен VACUUM FULL)
```

### 19. Зачем нужен ANALYZE

**`ANALYZE`** — это команда, которая собирает **статистику о распределении данных** в таблицах: количество строк, количество уникальных значений в столбцах, гистограммы распределения, корреляции между столбцами и т.д. Эта статистика сохраняется в системных каталогах (`pg_statistic`) и используется **планировщиком запросов** для оценки стоимости различных планов выполнения.

Без актуальной статистики планировщик может выбрать **неоптимальный план** (например, использовать индекс там, где лучше было бы последовательное сканирование, или наоборот), что приведёт к медленному выполнению запросов. `ANALYZE` рекомендуется запускать после значительных изменений данных (массовая загрузка, удаление, обновление) или регулярно (autovacuum делает это автоматически). `VACUUM` и `ANALYZE` часто выполняются вместе (команда `VACUUM ANALYZE`).


### 20. Что такое explain plan

**Explain plan (план выполнения)** — это описание того, **как СУБД собирается выполнять запрос**: какие таблицы и в каком порядке будут прочитаны, какие алгоритмы соединения (`Nested Loop`, `Hash Join`, `Merge Join`) будут использованы, какие индексы будут задействованы и сколько примерно строк будет обработано на каждом этапе.

В PostgreSQL план выполнения получается командой **`EXPLAIN`**. Она показывает **предполагаемый** план и оценку стоимости, но **не выполняет** сам запрос. С добавлением **`EXPLAIN ANALYZE`** запрос **фактически выполняется**, и к плану добавляется **реальная статистика**: фактическое время выполнения каждого узла (в миллисекундах) и фактическое количество обработанных строк. Это позволяет сравнить оценки планировщика с реальностью и выявить проблемные места.

Анализ плана — ключевой инструмент оптимизации. Основные показатели: `cost` (оценка стоимости), `rows` (оценка количества строк), `actual time` и `actual rows` (реальные значения). Большое расхождение между оценкой и реальностью часто указывает на устаревшую статистику или проблему с предикатом.

Типичный план запроса «оборот по категориям за месяц» (как в `run.sql`):

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT p.category, SUM(oi.price_at_moment * oi.quantity) AS revenue
FROM order_items oi
JOIN products p ON oi.product_id = p.id
JOIN orders   o ON oi.order_id = o.id AND o.created_at > NOW() - INTERVAL '1 month'
GROUP BY p.category;
```

```text
Aggregate  (cost=...  rows=5)  (actual time=... rows=5)
  Group Key: p.category
  Buffers: shared hit=...
  ->  Hash Join  (cost=...  rows=...)   -- соединение oi с orders
        Hash Cond: (oi.order_id = o.id)
        ->  Seq Scan on order_items oi   -- ⚠️ полное сканирование 1.5M строк
        ->  Hash
              ->  Bitmap Heap Scan on orders o   -- ✅ используется индекс idx_orders_created_at
                    Recheck Cond: (created_at > ...)
                    ->  Bitmap Index Scan on idx_orders_created_at
  ->  Hash  ...
        ->  Seq Scan on products p
```

На что смотреть: `Seq Scan` по большой таблице (кандидат на индекс), `Hash Cond` / `Merge Cond` (условия соединения), расхождение `rows` (оценка) и `actual rows` (реальность), `Buffers` (I/O нагрузка).

### 21. Как оптимизировать медленные запросы

Оптимизация медленных запросов — итеративный процесс. Основные шаги:

1.  **Идентифицировать медленные запросы**: включить логирование медленных запросов (`log_min_duration_statement` в PostgreSQL) или использовать `pg_stat_statements` для поиска самых ресурсоёмких запросов.
2.  **Проанализировать план выполнения** через `EXPLAIN ANALYZE`: найти узлы с наибольшим фактическим временем и наибольшим расхождением между оценкой и реальностью. Обратить внимание на `Seq Scan` по большим таблицам, неэффективные `Nested Loop` с большим числом итераций, сортировки на диске.
3.  **Добавить или скорректировать индексы**: создать индексы по столбцам в `WHERE`, `JOIN`, `ORDER BY`. Рассмотреть составные индексы для часто используемых комбинаций. Проверить, что существующие индексы действительно используются.
4.  **Обновить статистику**: выполнить `ANALYZE` для таблиц, участвующих в запросе, если статистика устарела.
5.  **Переписать запрос**: заменить коррелированные подзапросы на `JOIN` или оконные функции; избегать `SELECT *` (выбирать только нужные столбцы); использовать `EXISTS` вместо `IN` с подзапросом, возвращающим много строк; разбить сложный запрос на CTE, если это улучшает план.
6.  **Рассмотреть денормализацию или материализованные представления** для часто выполняемых тяжёлых агрегатов.
7.  **Настроить параметры СУБД**: `work_mem` (для сортировок и хеш-соединений), `shared_buffers` (кэш) и другие, если проблема связана с нехваткой памяти.
8.  **Проверить блокировки**: если запрос ждёт блокировку, а не выполняется, это может быть причиной «медленности».

Важно: оптимизация должна быть **измеримой**. Всегда сравнивайте `EXPLAIN ANALYZE` до и после изменений.

Практический пример (запрос из `run.sql`):

```sql
-- ❌ До: условие на orders в JOIN, индекс по created_at может не помочь
--    (планировщик соединяет сначала oi × orders по order_id, фильтр по дате — позже)
EXPLAIN ANALYZE
SELECT p.category, SUM(oi.price_at_moment * oi.quantity) AS revenue
FROM order_items oi
JOIN products p ON oi.product_id = p.id
JOIN orders   o ON oi.order_id = o.id AND o.created_at > NOW() - INTERVAL '1 month'
GROUP BY p.category;

-- ✅ После: сначала отфильтровать нужные заказы (CTE), затем соединение —
--    индекс idx_orders_created_at срабатывает на малом наборе строк
EXPLAIN ANALYZE
WITH recent_orders AS MATERIALIZED (
    SELECT id FROM orders WHERE created_at > NOW() - INTERVAL '1 month'
)
SELECT p.category, SUM(oi.price_at_moment * oi.quantity) AS revenue
FROM order_items oi
JOIN recent_orders ro ON oi.order_id = ro.id
JOIN products       p ON oi.product_id = p.id
GROUP BY p.category;
```

Плюс: убедиться, что по `order_items (order_id)` есть индекс (`idx4`), чтобы соединение с `recent_orders` шло через `Index/Hash` без полного скана 1.5M строк.
