# Базы данных / SQL / PostgreSQL

### 1. Для чего нужны индексы

Индексы в базах данных — это специальные структуры данных, которые ускоряют операции поиска, сортировки и соединения строк, позволяя СУБД находить нужные данные без полного сканирования таблицы. По сути, индекс работает как алфавитный указатель в книге: вместо того чтобы перелистывать все страницы в поисках нужного термина, вы сразу открываете нужную страницу.

Основное назначение индексов — **повышение производительности запросов** (особенно `SELECT`, `UPDATE`, `DELETE` с условиями `WHERE`, а также `JOIN` и `ORDER BY`). Без индекса СУБД вынуждена выполнять последовательное сканирование (`Seq Scan`), проверяя каждую строку таблицы, что при больших объёмах данных может быть крайне медленно. Индекс позволяет сократить количество читаемых страниц до O(log n), где n — число строк.

Пример создания индекса и проверки его работы (таблица `orders` из `test.session.sql`):

```sql
-- Индекс по времени создания заказа (частый фильтр по диапазону)
CREATE INDEX idx_orders_created_at ON orders (created_at);

-- До индекса: Seq Scan по всей таблице (500 000 строк)
-- После: Bitmap Index Scan / Index Scan по узкому диапазону
EXPLAIN ANALYZE
SELECT id, total_amount
FROM orders
WHERE created_at > NOW() - INTERVAL '1 month';
```

### 2. Как работает B-tree индекс

B-tree (Balanced tree) — наиболее распространённый тип индекса в реляционных СУБД. Это сбалансированное дерево, в котором все листовые узлы находятся на одном уровне (одинаковой глубине от корня), что гарантирует примерно одинаковое время доступа к любому значению.

Структура B-tree индекса:
- **Корневая страница (root page)**: содержит граничные значения и указатели на дочерние внутренние страницы.
- **Внутренние страницы (internal pages)**: промежуточные уровни, каждый узел содержит ключи и указатели, направляющие поиск к нужному листу.
- **Листовые страницы (leaf pages)**: хранят фактические значения индексированного столбца и указатели на строки таблицы (row IDs). Листовые страницы связаны между собой, что делает эффективными диапазонные запросы (`BETWEEN`, `>`, `<`).

Поиск по B-tree начинается с корня, на каждом уровне выбирается правильный указатель на основе сравниваемого значения, и так до листовой страницы. Сложность поиска — **O(log n)**. Например, для миллионов строк дерево обычно имеет глубину 3–4 уровня, то есть для поиска нужно прочитать всего 3–4 страницы. B-tree поддерживает как точечный поиск (`WHERE id = 42`), так и диапазонный (`WHERE age BETWEEN 25 AND 35`), а также сортировку (`ORDER BY`).


### 3. Что такое составной индекс

Составной (композитный, многоколоночный) индекс — это индекс, построенный по **двум или более столбцам** таблицы. В B-tree такого индекса ключи сортируются сначала по первому столбцу, затем внутри одинаковых значений первого столбца — по второму и т.д.. Например, для индекса `CREATE INDEX idx ON table (a, b, c)` записи упорядочены по `a`, затем по `b`, затем по `c`.

Составной индекс может быть использован для запросов, которые фильтруют по **префиксу** ключа: по `a`, по `(a, b)`, по `(a, b, c)`. Запрос, который фильтрует только по `b` или только по `c`, обычно **не может** эффективно использовать этот индекс (без использования дополнительных механизмов, таких как index skip scan). Это правило называют **«левым префиксом»**.

Составные индексы полезны, когда запросы часто фильтруют или сортируют по комбинации столбцов. Однако не рекомендуется создавать индексы по более чем 3–4 столбцам, так как они занимают много места и редко бывают полезны, если только рабочая нагрузка не очень специфична.

Пример на таблице `order_items` (фильтр по `order_id` + сортировка по `quantity`):

```sql
-- Составной индекс: сначала по order_id, затем по quantity
CREATE INDEX idx_oi_order_qty ON order_items (order_id, quantity);

-- Использует индекс по префиксу (order_id) + сортировка без extra Sort
SELECT product_id, quantity
FROM order_items
WHERE order_id = 1234
ORDER BY quantity DESC;

-- ❌ Этот запрос НЕ использует idx_oi_order_qty эффективно
--    (фильтрует только по quantity — не левый префикс)
SELECT order_id, quantity
FROM order_items
WHERE quantity > 5;
```

### 4. Когда стоит создавать индекс

Индекс стоит создавать, когда:
- **Столбец часто используется в условиях `WHERE`**, особенно с высокой селективностью (когда условие отбирает небольшую долю строк).
- **Столбец используется в `JOIN`** для соединения таблиц (внешние ключи).
- **Столбец используется в `ORDER BY`** или `GROUP BY`, чтобы избежать сортировки.
- **Запросы выполняются часто** и их ускорение критично для приложения.
- **Таблица большая**, и полное сканирование становится дорогим.

Индекс особенно полезен, когда запрос возвращает лишь небольшую часть строк (`high selectivity`). Для маленьких таблиц (несколько тысяч строк) индекс может быть не нужен — последовательное сканирование и так быстрое.


### 5. Какие недостатки индексов

Индексы имеют ряд недостатков:
- **Занимают дисковое пространство**: индекс — это отдельная структура, которая может занимать значительный объём.
- **Замедляют операции записи (`INSERT`, `UPDATE`, `DELETE`)**: при каждом изменении данных в индексированном столбце СУБД должна обновить и сам индекс, что создаёт дополнительную нагрузку.
- **Требуют обслуживания**: индексы нужно периодически перестраивать (например, `REINDEX` или `VACUUM` в PostgreSQL), чтобы избежать их раздувания.
- **Могут не использоваться**: планировщик может проигнорировать индекс, если посчитает, что полное сканирование дешевле (например, при низкой селективности).
- **Увеличивают сложность**: слишком много индексов усложняет администрирование и может ухудшить общую производительность.


### 6. Что такое кардинальность индекса

**Кардинальность (cardinality)** — это количество **уникальных значений** в индексированном столбце. Высокая кардинальность означает, что в столбце много разных значений (например, `email`, `id`), низкая — что значений мало и они часто повторяются (например, `пол`, `статус`).

Кардинальность тесно связана с **селективностью (selectivity)** — долей строк, удовлетворяющих условию. Чем выше кардинальность, тем выше селективность и тем полезнее индекс для точечных запросов. Индекс по столбцу с низкой кардинальностью (например, `boolean`) часто бесполезен, так как даже при поиске по значению будет возвращена большая часть таблицы, и полное сканирование окажется быстрее. Планировщик запросов использует статистику кардинальности (собираемую через `ANALYZE`) для оценки стоимости различных планов.

Проверить кардинальность и селективность на реальных данных:

```sql
-- Сколько уникальных значений в столбце (после ANALYZE)
SELECT count(DISTINCT status) AS unique_statuses,
       count(*)               AS total_rows,
       count(DISTINCT status) * 1.0 / count(*) AS selectivity
FROM orders;
-- status: 4 уникальных значения из 500 000 строк → selectivity ≈ 0.000008
-- → индекс по status практически бесполезен (возвращает ~25% таблицы)

-- Сравните со столбцом высокой кардинальности:
SELECT count(DISTINCT user_id) * 1.0 / count(*) AS user_id_selectivity
FROM orders;
-- user_id: почти 100 000 уникальных значений → высокий индекс полезен
```

**`n_distinct` в `pg_stats`:** планировщик хранит оценку количества уникальных значений в системном каталоге `pg_stats` (поле `n_distinct`). Если Postgres знает, что в столбце всего 2–3 уникальных значения (например, `is_deleted`, `status`), он **никогда** не будет использовать по нему индекс — даже если вы его создали — потому что последовательное сканирование окажется дешевле.

```sql
-- Посмотреть, что знает планировщик о столбце
SELECT attname, n_distinct
FROM pg_stats
WHERE tablename = 'orders' AND attname = 'status';
-- n_distinct = 4 → планировщик знает, что уникальных значений мало
```

### 7. Какие типы JOIN существуют

Основные типы JOIN в SQL:
- **`INNER JOIN`** (или просто `JOIN`): возвращает только те строки, для которых есть совпадение в **обеих** таблицах.
- **`LEFT JOIN`** (`LEFT OUTER JOIN`): возвращает **все строки из левой таблицы** и совпадающие строки из правой; если совпадения нет, правая часть заполняется `NULL`.
- **`RIGHT JOIN`** (`RIGHT OUTER JOIN`): возвращает все строки из **правой таблицы** и совпадающие из левой; несовпадающие левые строки заполняются `NULL`.
- **`FULL JOIN`** (`FULL OUTER JOIN`): возвращает все строки из **обеих таблиц**, заполняя `NULL` там, где нет совпадения.
- **`CROSS JOIN`**: возвращает **декартово произведение** двух таблиц (каждая строка одной соединяется с каждой строкой другой).
- **`SELF JOIN`**: соединение таблицы с самой собой (частный случай, не отдельный синтаксис).

Примеры на таблицах `users` и `orders`:

```sql
-- INNER JOIN: только пользователи, у которых есть заказы
SELECT u.username, o.total_amount
FROM users u
JOIN orders o ON u.id = o.user_id;

-- LEFT JOIN: все пользователи, включая тех, у кого нет заказов (NULL в orders)
SELECT u.username, o.total_amount
FROM users u
LEFT JOIN orders o ON u.id = o.user_id;

-- CROSS JOIN: декартово произведение (каждый пользователь × каждый заказ)
-- Используется редко, например для генерации сетки данных
SELECT u.username, o.id AS order_id
FROM users u
CROSS JOIN orders o;
```

### 8. В чём разница между INNER JOIN и LEFT JOIN

- **`INNER JOIN`** возвращает только те строки, которые имеют совпадение в **обеих** соединяемых таблицах. Строки без совпадения отбрасываются.
- **`LEFT JOIN`** возвращает **все строки из левой таблицы**, даже если для них нет совпадения в правой. Для таких строк столбцы правой таблицы заполняются `NULL`.

Ключевое практическое следствие: если в `LEFT JOIN` добавить условие на правую таблицу в `WHERE` (например, `WHERE right_table.column = 'value'`), это фактически превратит `LEFT JOIN` в `INNER JOIN`, так как строки с `NULL` в правой части не пройдут фильтр. Чтобы сохранить семантику `LEFT JOIN`, условия на правую таблицу нужно размещать в секции `ON`, а не `WHERE`.

Демонстрация на `users` / `orders` (найти пользователей, у которых есть заказы со статусом `PAID`, **включая** пользователей без таких заказов):

```sql
-- ❌ Неправильно: условие в WHERE — превращает LEFT JOIN в INNER JOIN,
--    пользователи без PAID-заказов пропадут из результата
SELECT u.username, o.id
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
WHERE o.status = 'PAID';

-- ✅ Правильно: условие на правую таблицу в ON —
--    пользователи без PAID-заказов останутся (o.id = NULL)
SELECT u.username, o.id
FROM users u
LEFT JOIN orders o ON u.id = o.user_id AND o.status = 'PAID';
```

### 9. Что лучше: JOIN или подзапрос

Однозначного ответа нет — оба инструмента имеют свои области применения, и современные СУБД (включая PostgreSQL) часто оптимизируют их одинаково, преобразуя подзапросы в соединения (или наоборот).

- **`JOIN`** обычно предпочтительнее, когда нужно **объединить данные из нескольких таблиц** и вернуть столбцы из обеих. Он часто более читаем и лучше оптимизируется.
- **Подзапрос** (в `SELECT`, `WHERE` или `FROM`) удобен, когда:
  - Нужно вычислить **агрегатное значение** для фильтрации (`WHERE salary > (SELECT AVG(salary) FROM employees)`).
  - Нужно проверить **существование** (`EXISTS` / `NOT EXISTS`) — часто эффективнее, чем `JOIN` с `DISTINCT`.
  - Запрос логически проще выразить через подзапрос.

С точки зрения производительности: **коррелированные подзапросы** (см. вопрос 10) могут выполняться медленно, так как выполняются для каждой строки внешнего запроса. Некоррелированные подзапросы обычно оптимизируются хорошо. В PostgreSQL планировщик часто переписывает подзапросы в соединения, поэтому разница может быть незначительной. Рекомендуется **измерять** производительность через `EXPLAIN ANALYZE`.


### 10. Что такое коррелированный подзапрос

**Коррелированный подзапрос (correlated subquery)** — это подзапрос, который ссылается на столбцы из **внешнего запроса**. В отличие от обычного (некоррелированного) подзапроса, который вычисляется один раз, коррелированный подзапрос **выполняется для каждой строки** внешнего запроса (концептуально). Пример:

```sql
SELECT e.name
FROM employees e
WHERE e.salary > (SELECT AVG(salary) FROM employees WHERE department_id = e.department_id);
```

Здесь подзапрос ссылается на `e.department_id` из внешнего запроса, поэтому средняя зарплата вычисляется для каждого отдела. Коррелированные подзапросы могут быть неэффективными на больших данных, но иногда их можно переписать через `JOIN` с агрегацией или оконные функции для повышения производительности.


### 11. В чём разница между WHERE и HAVING

- **`WHERE`** фильтрует **отдельные строки** **до** группировки (до `GROUP BY`). Он не может содержать агрегатные функции (`SUM`, `COUNT`, `AVG` и т.д.).
- **`HAVING`** фильтрует **сгруппированные результаты** **после** `GROUP BY`. Он применяется к результатам агрегатных функций и может содержать их.

Порядок выполнения: `FROM` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `ORDER BY`. Таким образом, `WHERE` ограничивает набор строк, попадающих в группировку, а `HAVING` — какие группы останутся в результате.

Пример на `orders`: суммарный оборот по категориям, только по оплаченным заказам и только категории с оборотом выше 10 000:

```sql
SELECT p.category,
       SUM(oi.price_at_moment * oi.quantity) AS revenue
FROM order_items oi
JOIN orders   o ON oi.order_id = o.id
JOIN products p ON oi.product_id = p.id
WHERE o.status = 'PAID'                 -- WHERE: фильтрует строки ДО группировки
GROUP BY p.category
HAVING SUM(oi.price_at_moment * oi.quantity) > 10000;  -- HAVING: фильтрует группы ПОСЛЕ
```

### 12. Что делает GROUP BY

**`GROUP BY`** группирует строки, имеющие одинаковые значения в указанных столбцах, в **одну строку результата**. Обычно используется вместе с агрегатными функциями (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`), которые вычисляются для каждой группы. Например:

```sql
SELECT department_id, COUNT(*) AS employee_count
FROM employees
GROUP BY department_id;
```

Этот запрос вернёт количество сотрудников в каждом отделе. Все неагрегированные столбцы в `SELECT` должны быть перечислены в `GROUP BY` (или быть функционально зависимыми от них).


### 13. Когда использовать HAVING

`HAVING` используется, когда нужно **отфильтровать результаты агрегации** после `GROUP BY`. Например, найти отделы, где средняя зарплата превышает 50000:

```sql
SELECT department_id, AVG(salary) AS avg_salary
FROM employees
GROUP BY department_id
HAVING AVG(salary) > 50000;
```

`HAVING` также может использоваться без `GROUP BY` (тогда он фильтрует результат агрегации по всей таблице), но это менее распространено. Если условие не содержит агрегатных функций и применяется к отдельным строкам, следует использовать `WHERE` — это эффективнее, так как фильтрация происходит раньше.


### 14. Что такое оконные функции (Window Functions)

**Оконные функции** — это функции, которые выполняют вычисления над набором строк, связанных с текущей строкой, **не сворачивая** результат в одну строку (в отличие от `GROUP BY`). Каждая строка сохраняет свою индивидуальность, но при этом получает дополнительное вычисленное значение.

Синтаксис: `function_name(...) OVER (PARTITION BY ... ORDER BY ...)`. `PARTITION BY` делит строки на группы (окна), а `ORDER BY` определяет порядок внутри окна. Оконные функции позволяют вычислять ранги, скользящие средние, нарастающие итоги, сравнивать значения с предыдущей/следующей строкой (`LAG`/`LEAD`) и многое другое. Они являются мощным инструментом аналитики, позволяющим избежать сложных самосоединений и подзапросов.

Пример: нарастающий оборот (running total) по дням и средняя сумма заказа за последние 7 дней:

```sql
SELECT
    date_trunc('day', created_at) AS day,
    SUM(total_amount) AS daily_revenue,
    SUM(SUM(total_amount)) OVER (ORDER BY date_trunc('day', created_at)) AS running_total,
    AVG(SUM(total_amount)) OVER (
        ORDER BY date_trunc('day', created_at)
        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
    ) AS avg_revenue_7d
FROM orders
WHERE status = 'PAID'
GROUP BY date_trunc('day', created_at)
ORDER BY day;
```

### 15. Что делает ROW_NUMBER()

**`ROW_NUMBER()`** — оконная функция, которая присваивает каждой строке **уникальный последовательный номер** в рамках окна, определяемого `OVER (ORDER BY ...)`. Нумерация начинается с 1 и продолжается без пропусков, даже если значения в `ORDER BY` совпадают (дубликаты получают разные номера).

Пример:
```sql
SELECT name, salary,
       ROW_NUMBER() OVER (ORDER BY salary DESC) AS row_num
FROM employees;
```
Этот запрос пронумерует сотрудников по убыванию зарплаты: самый высокооплачиваемый получит 1, следующий — 2 и т.д., даже если у двух сотрудников зарплата одинакова.


### 16. Что делает RANK() и DENSE_RANK()

Обе функции присваивают ранги на основе `ORDER BY` в окне, но по-разному обрабатывают **совпадающие значения (ties)**:

- **`RANK()`**: при совпадении значений присваивает **одинаковый ранг**, но следующий ранг **пропускается**. Например, если два сотрудника делят 1-е место, следующий получит 3-й ранг (1, 1, 3, ...).
- **`DENSE_RANK()`**: при совпадении значений также присваивает одинаковый ранг, но **не пропускает** следующий номер. В примере выше следующий получит 2-й ранг (1, 1, 2, ...).

`ROW_NUMBER()` всегда даёт уникальные номера без повторов. Выбор функции зависит от бизнес-требований: нужен ли «плотный» рейтинг или с пропусками.

Пример (топ пользователей по сумме заказов, наглядно видно различие рангов при равных значениях):

```sql
SELECT
    u.username,
    SUM(o.total_amount) AS total_spent,
    ROW_NUMBER()   OVER (ORDER BY SUM(o.total_amount) DESC) AS row_num,
    RANK()         OVER (ORDER BY SUM(o.total_amount) DESC) AS rank,
    DENSE_RANK()   OVER (ORDER BY SUM(o.total_amount) DESC) AS dense_rank
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE o.status = 'PAID'
GROUP BY u.username
ORDER BY total_spent DESC
LIMIT 10;
```

Если у двух пользователей сумма одинакова: `RANK` выдаст `1, 1, 3`, а `DENSE_RANK` — `1, 1, 2`.

### 17. Как работает MVCC в PostgreSQL

**MVCC (Multi-Version Concurrency Control)** — это механизм управления параллелизмом, который позволяет нескольким транзакциям работать с данными одновременно, **не блокируя** друг друга. В отличие от традиционных СУБД, использующих блокировки, PostgreSQL создаёт **множество версий** каждой строки.

Когда транзакция изменяет (`UPDATE`) или удаляет (`DELETE`) строку, PostgreSQL **не перезаписывает** существующую строку, а создаёт **новую версию** (для `UPDATE`) или помечает старую как удалённую (для `DELETE`). Старая версия остаётся физически в таблице, пока её не удалит `VACUUM`.

Каждая транзакция видит **снимок (snapshot)** базы данных на определённый момент времени. Снимок определяется номерами транзакций (XID): транзакция видит только те версии строк, которые были закоммичены **до** её начала (в зависимости от уровня изоляции).

Главное преимущество MVCC: **чтение никогда не блокирует запись, а запись никогда не блокирует чтение**. Это обеспечивает высокую степень параллелизма и предсказуемое время отклика. Плата за это — необходимость регулярного `VACUUM` для очистки «мёртвых» версий строк.

Демонстрация (две сессии, таблица `orders`):

```sql
-- Сессия A
BEGIN;
SELECT total_amount FROM orders WHERE id = 1;   -- видит, например, 100.00
-- (ждём, пока Сессия B сделает UPDATE, но тот ещё не закоммитил)

-- Сессия B
BEGIN;
UPDATE orders SET total_amount = 999.99 WHERE id = 1;   -- создаёт новую версию, A этого не видит
-- SELECT в Сессии A всё ещё вернёт 100.00 (snapshot не изменился)
ROLLBACK;  -- откатываем, чтобы не испортить данные

-- Сессия A
COMMIT;
-- После COMMIT в Сессии B и нового BEGIN в A — будет видно 100.00 (откат),
-- а при COMMIT обновления — 999.99.
```

Проверить число версий строки до VACUUM:

```sql
SELECT id, xmin, xmax   -- xmin = xid создателя, xmax = xid удалителя (0, если активна)
FROM orders
WHERE id = 1;
```

### 18. Что такое VACUUM в PostgreSQL

**`VACUUM`** — это служебная команда PostgreSQL, которая выполняет «сборку мусора»: удаляет физически **мёртвые версии строк** (dead tuples), которые больше не видны ни одной активной транзакции, и освобождает занимаемое ими место для повторного использования.

Зачем нужен `VACUUM`:
- **Восстановление дискового пространства**: без него таблицы и индексы будут бесконечно расти, даже если строки удаляются или обновляются.
- **Обновление статистики**: `VACUUM` (вместе с `ANALYZE`) обновляет статистику, используемую планировщиком запросов.
- **Обновление visibility map**: ускоряет index-only scans.
- **Защита от wraparound XID**: предотвращает исчерпание номеров транзакций, которое может привести к остановке базы.

`VACUUM` бывает **стандартным** (работает параллельно с другими операциями, но не возвращает место ОС, а только помечает его для повторного использования) и **`VACUUM FULL`** (полностью перестраивает таблицу, возвращает место ОС, но требует эксклюзивной блокировки и работает медленно). Обычно `VACUUM` запускается автоматически демоном **autovacuum**, но может выполняться и вручную.

Замерить эффект на `orders` (таблица с большим числом UPDATE/DELETE):

```sql
-- До VACUUM: видим «раздутый» размер и количество мёртвых строк
SELECT
    relname,
    pg_size_pretty(pg_total_relation_size(relid)) AS total_size,
    n_dead_tup,
    n_live_tup
FROM pg_stat_user_tables
WHERE relname = 'orders';

-- Ручной VACUUM (стандартный, без блокировки)
VACUUM orders;

-- После VACUUM: n_dead_tup → 0, размер может уменьшиться
-- (но место возвращается в free space внутри файла, не в ОС — для этого нужен VACUUM FULL)
```

### 19. Зачем нужен ANALYZE

**`ANALYZE`** — это команда, которая собирает **статистику о распределении данных** в таблицах: количество строк, количество уникальных значений в столбцах, гистограммы распределения, корреляции между столбцами и т.д. Эта статистика сохраняется в системных каталогах (`pg_statistic`) и используется **планировщиком запросов** для оценки стоимости различных планов выполнения.

Без актуальной статистики планировщик может выбрать **неоптимальный план** (например, использовать индекс там, где лучше было бы последовательное сканирование, или наоборот), что приведёт к медленному выполнению запросов. `ANALYZE` рекомендуется запускать после значительных изменений данных (массовая загрузка, удаление, обновление) или регулярно (autovacuum делает это автоматически). `VACUUM` и `ANALYZE` часто выполняются вместе (команда `VACUUM ANALYZE`).


### 20. Что такое explain plan

**Explain plan (план выполнения)** — это описание того, **как СУБД собирается выполнять запрос**: какие таблицы и в каком порядке будут прочитаны, какие алгоритмы соединения (`Nested Loop`, `Hash Join`, `Merge Join`) будут использованы, какие индексы будут задействованы и сколько примерно строк будет обработано на каждом этапе.

В PostgreSQL план выполнения получается командой **`EXPLAIN`**. Она показывает **предполагаемый** план и оценку стоимости, но **не выполняет** сам запрос. С добавлением **`EXPLAIN ANALYZE`** запрос **фактически выполняется**, и к плану добавляется **реальная статистика**: фактическое время выполнения каждого узла (в миллисекундах) и фактическое количество обработанных строк. Это позволяет сравнить оценки планировщика с реальностью и выявить проблемные места.

Анализ плана — ключевой инструмент оптимизации. Основные показатели: `cost` (оценка стоимости), `rows` (оценка количества строк), `actual time` и `actual rows` (реальные значения). Большое расхождение между оценкой и реальностью часто указывает на устаревшую статистику или проблему с предикатом.

Типичный план запроса «оборот по категориям за месяц» (как в `run.sql`):

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT p.category, SUM(oi.price_at_moment * oi.quantity) AS revenue
FROM order_items oi
JOIN products p ON oi.product_id = p.id
JOIN orders   o ON oi.order_id = o.id AND o.created_at > NOW() - INTERVAL '1 month'
GROUP BY p.category;
```

```text
Aggregate  (cost=...  rows=5)  (actual time=... rows=5)
  Group Key: p.category
  Buffers: shared hit=...
  ->  Hash Join  (cost=...  rows=...)   -- соединение oi с orders
        Hash Cond: (oi.order_id = o.id)
        ->  Seq Scan on order_items oi   -- ⚠️ полное сканирование 1.5M строк
        ->  Hash
              ->  Bitmap Heap Scan on orders o   -- ✅ используется индекс idx_orders_created_at
                    Recheck Cond: (created_at > ...)
                    ->  Bitmap Index Scan on idx_orders_created_at
  ->  Hash  ...
        ->  Seq Scan on products p
```

На что смотреть: `Seq Scan` по большой таблице (кандидат на индекс), `Hash Cond` / `Merge Cond` (условия соединения), расхождение `rows` (оценка) и `actual rows` (реальность), `Buffers` (I/O нагрузка).

**Ключевые узлы плана — углублённый разбор:**

- **`Seq Scan`** — последовательное сканирование таблицы. По небольшой таблице — нормально, по большой — кандидат на индекс.
- **`Index Scan`** — чтение по индексу (одна строка за раз). Эффективен для узкого диапазона.
- **`Bitmap Index Scan` + `Bitmap Heap Scan`** — индекс возвращает набор страниц, затем таблица читается по этим страницам (в порядке расположения на диске). Эффективен для широкого диапазона (сборка множества строк).
- **`Index Only Scan`** — **самый быстрый** тип скана: данные читаются **только из индекса**, без обращения к таблице. Работает, если все нужные столбцы есть в индексе. Требует актуальный visibility map (обновляется `VACUUM`).
- **`Nested Loop Join`** — для каждой строки внешней таблицы выполняет внутреннюю. Эффективен для **маленьких** таблиц или когда внутренний запрос идёт по индексу. Плохо для больших × больших.
- **`Hash Join`** — строит хеш-таблицу по одной стороне, затем сканирует другую и находит совпадения. Эффективен для **больших несортированных** таблиц.
- **`Merge Join`** — обе стороны уже отсортированы (по индексу или после `Sort`), соединение идёт за один проход. Эффективен для **больших отсортированных** данных.
- **`Sort`** — полная сортировка. Если `Sort Method: external merge` — данных больше, чем `work_mem`, сортировка идёт **на диск** (медленно). Решение: увеличить `work_mem`.
- **`Top-N Heapsort`** — частичная сортировка для `ORDER BY ... LIMIT N`. Не сортирует все данные, держит только топ-N. Гораздо быстрее полного `Sort`.

**`Buffers: shared hit` vs `shared read` (самая важная метрика для сеньора):**

```text
Buffers: shared hit=1234 read=56
```

- **`shared hit`** — страница найдена в `shared_buffers` (оперативная память). **Быстро.**
- **`shared read`** — страницу пришлось **читать с диска** (I/O). **Медленно** (в 100–1000 раз медленнее, чем из RAM).

Если в плане много `read` — проблема:
- Не хватает `shared_buffers` (увеличить).
- Индекс не используется (seq scan читает всё с диска).
- Таблица/индекс «раздуты» (нужен `VACUUM`).

**Расхождение `rows` (оценка) и `actual rows` (реальность) > 10×** → устаревшая статистика, нужен `ANALYZE`.

### 21. Как оптимизировать медленные запросы

Оптимизация медленных запросов — итеративный процесс. Основные шаги:

1.  **Идентифицировать медленные запросы**: включить логирование медленных запросов (`log_min_duration_statement` в PostgreSQL) или использовать `pg_stat_statements` для поиска самых ресурсоёмких запросов.
2.  **Проанализировать план выполнения** через `EXPLAIN ANALYZE`: найти узлы с наибольшим фактическим временем и наибольшим расхождением между оценкой и реальностью. Обратить внимание на `Seq Scan` по большим таблицам, неэффективные `Nested Loop` с большим числом итераций, сортировки на диске.
3.  **Добавить или скорректировать индексы**: создать индексы по столбцам в `WHERE`, `JOIN`, `ORDER BY`. Рассмотреть составные индексы для часто используемых комбинаций. Проверить, что существующие индексы действительно используются.
4.  **Обновить статистику**: выполнить `ANALYZE` для таблиц, участвующих в запросе, если статистика устарела.
5.  **Переписать запрос**: заменить коррелированные подзапросы на `JOIN` или оконные функции; избегать `SELECT *` (выбирать только нужные столбцы); использовать `EXISTS` вместо `IN` с подзапросом, возвращающим много строк; разбить сложный запрос на CTE, если это улучшает план.
6.  **Рассмотреть денормализацию или материализованные представления** для часто выполняемых тяжёлых агрегатов.
7.  **Настроить параметры СУБД**: `work_mem` (для сортировок и хеш-соединений), `shared_buffers` (кэш) и другие, если проблема связана с нехваткой памяти.
8.  **Проверить блокировки**: если запрос ждёт блокировку, а не выполняется, это может быть причиной «медленности».

Важно: оптимизация должна быть **измеримой**. Всегда сравнивайте `EXPLAIN ANALYZE` до и после изменений.

Практический пример (запрос из `run.sql`):

```sql
-- ❌ До: условие на orders в JOIN, индекс по created_at может не помочь
--    (планировщик соединяет сначала oi × orders по order_id, фильтр по дате — позже)
EXPLAIN ANALYZE
SELECT p.category, SUM(oi.price_at_moment * oi.quantity) AS revenue
FROM order_items oi
JOIN products p ON oi.product_id = p.id
JOIN orders   o ON oi.order_id = o.id AND o.created_at > NOW() - INTERVAL '1 month'
GROUP BY p.category;

-- ✅ После: сначала отфильтровать нужные заказы (CTE), затем соединение —
--    индекс idx_orders_created_at срабатывает на малом наборе строк
EXPLAIN ANALYZE
WITH recent_orders AS MATERIALIZED (
    SELECT id FROM orders WHERE created_at > NOW() - INTERVAL '1 month'
)
SELECT p.category, SUM(oi.price_at_moment * oi.quantity) AS revenue
FROM order_items oi
JOIN recent_orders ro ON oi.order_id = ro.id
JOIN products       p ON oi.product_id = p.id
GROUP BY p.category;
```

Плюс: убедиться, что по `order_items (order_id)` есть индекс (`idx4`), чтобы соединение с `recent_orders` шло через `Index/Hash` без полного скана 1.5M строк.

### 22. Какие ещё типы индексов есть в PostgreSQL (кроме B-tree)

B-tree — самый универсальный и часто используемый тип индекса (вопрос 2), но в PostgreSQL есть и специализированные структуры, которые выбирают под конкретную задачу. Выбор типа индекса — это trade-off между скоростью поиска, скоростью записи и занимаемым местом.

**Типы индексов:**

| Тип | Для чего | Поддерживаемые операции | Где применяется |
| :--- | :--- | :--- | :--- |
| **B-tree** (дефолт) | Равенство, диапазоны, сортировка | `=`, `<`, `>`, `<=`, `>=`, `BETWEEN`, `ORDER BY`, `IS NULL` | Универсальный — по умолчанию |
| **Hash** | Только точное равенство | `=` | Практически бесполезен (B-tree так же быстр на `=`) |
| **GIN** (Generalized Inverted Index) | Составные значения в одной ячейке | `@>` (содержит), `?` (есть ключ), `&&` (пересечение) | JSONB, массивы (`int[]`, `text[]`), полнотекстовый поиск (`tsvector`) |
| **GiST** (Generalized Search Tree) | Не-строго упорядоченные данные | диапазоны, геоданные | PostGIS (гео), range-типы (`int4range`), полнотекстовый поиск с ранжированием |
| **BRIN** (Block Range Index) | Большие таблицы с коррелированными данными | `=`, `<`, `>`, `BETWEEN` (как B-tree) | Временные ряды, логи, мониторинг — данные вставляются хронологически |
| **SP-GiST** | Не-сбалансированные деревья | `=`, `<`, `>` | IP-адреса, телефонные номера, trie-структуры |

**GIN** — «инвертированный индекс» (как алфавитный указатель в книге, но в обратную сторону): хранит отображение «значение → список строк, где оно встречается». Идеален для поиска внутри составных значений (JSONB, массивы).

```sql
-- GIN для JSONB (поиск по полям JSON)
CREATE INDEX idx_users_metadata ON users USING GIN (metadata);
SELECT * FROM users WHERE metadata @> '{"role": "admin"}';

-- GIN для массива тегов
CREATE INDEX idx_users_tags ON users USING GIN (tags);
SELECT * FROM users WHERE tags @> ARRAY['java'];
```

**BRIN** — «Block Range Index»: не хранит каждое значение, а только минимальные/максимальные значения для групп блоков (страниц) таблицы. Занимает в **1000 раз меньше** места, чем B-tree, но работает корректно **только если данные физически упорядочены** (например, вставляются по времени). Для перемешанных данных BRIN будет возвращать лишние блоки — эффективность падает.

```sql
-- BRIN для временного ряда (огромная таблица логов, вставка по времени)
CREATE INDEX idx_logs_created_brin ON logs USING BRIN (created_at);
SELECT * FROM logs WHERE created_at > NOW() - INTERVAL '1 hour';
```

**GiST** — «Generalized Search Tree»: как B-tree, но с настраиваемой логикой сравнения (не строгий линейный порядок). Используется для геоданных (PostGIS) и range-типов.

```sql
-- GiST для геоданных (PostGIS)
CREATE INDEX idx_locations_geom ON locations USING GIST (geom);
SELECT * FROM locations WHERE ST_DWithin(geom, POINT(10, 20), 5);
```

**Trade-offs:**
- **B-tree**: универсальный, поддерживает `=` / диапазоны / `ORDER BY`, но занимает больше места для больших таблиц и не оптимален для составных значений.
- **Hash**: только `=`, медленнее на восстановление после краша (до PG 10 не логировался в WAL), на практике почти никогда не лучше B-tree.
- **GIN**: быстрый поиск по составным значениям, но медленный `INSERT`/`UPDATE` (индекс разрастается) и занимает много места.
- **BRIN**: минимальный размер, быстрая вставка, но работает только при упорядоченных данных (иначе много лишних блоков).
- **GiST**: гибкость (любая логика сравнения), но более сложная структура и не поддерживает `ORDER BY` в общем случае.

**Follow-up (что спросит интервьюер):**
- «Когда GIN лучше B-tree?» → для JSONB, массивов, полнотекстового поиска — B-tree не умеет искать внутри составного значения.
- «Почему BRIN для логов, а не B-tree?» → таблица в миллионах/миллиардах строк, данные вставляются по времени → BRIN в 1000 раз меньше, а селективность по времени высока.
- «Какой индекс для `WHERE email LIKE 'john%'`?» → B-tree (префиксный поиск), но не `WHERE email LIKE '%john%'` (нужен GIN + `pg_trgm`).
- «Какой индекс для `WHERE id BETWEEN 100 AND 200`?» → B-tree (диапазон) — BRIN тоже подошёл бы, если данные упорядочены по `id`.

### 23. Какие блокировки (Locks) есть в PostgreSQL и как они работают

MVCC (вопрос 17) решает конфликты «чтение–запись», но **не** решает «запись–запись». Когда две транзакции хотят изменить одну и ту же строку, PostgreSQL использует **блокировки (locks)**, чтобы обеспечить корректность. Понимание типов блокировок критично для диагностики дедлоков и производительности.

**Row-level locks (на уровне строки):**

| Ключевое слово | Что блокирует | Кто может читать | Кто может блокировать для UPDATE |
| :--- | :--- | :--- | :--- |
| `FOR UPDATE` | Эксклюзивная блокировка строки | Да | **Никто** (блокирует до COMMIT) |
| `FOR NO KEY UPDATE` | Как `FOR UPDATE`, но допускает `UPDATE` FK-значений | Да | Только `UPDATE` первичных ключей блокируется |
| `FOR SHARE` | Разделяемая блокировка (для чтения) | Да | `UPDATE` / `DELETE` блокируются, но несколько `FOR SHARE` могут существовать одновременно |
| `FOR KEY SHARE` | Слабейшая блокировка (для FK-проверок) | Да | `UPDATE` PK блокируется, `UPDATE` остальных — нет |

**Примеры:**

```sql
-- Пессимистичная блокировка строки (UPDATE заблокирован до COMMIT)
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;

-- "Слабая" блокировка — другие могут читать, но не блокировать для UPDATE
SELECT * FROM accounts WHERE id = 1 FOR SHARE;

-- Блокировка только для проверки FK (самая слабая)
SELECT * FROM accounts WHERE id = 1 FOR KEY SHARE;
```

**Table-level locks (на уровне таблицы):**
- `ACCESS SHARE` — устанавливается любым `SELECT`.
- `ROW EXCLUSIVE` — устанавливается `INSERT`/`UPDATE`/`DELETE` (несколько могут быть одновременно).
- `SHARE` — устанавливается `VACUUM`/`CLUSTER` (блокирует DML).
- `EXCLUSIVE` — устанавливается `CREATE INDEX` (без CONCURRENTLY).
- `ACCESS EXCLUSIVE` — устанавливается `DROP TABLE`, `ALTER TABLE` (блокирует всё).

Совместимость: `ACCESS SHARE` совместима со всеми, `ACCESS EXCLUSIVE` несовместима со всеми (кроме себя).

**Advisory locks (прикладные блокировки):**
Advisory locks — это блокировки **на уровне приложения**, которые PostgreSQL не проверяет на содержимое. Их используют для распределённой синхронизации **без создания таблиц**:

```sql
-- Установить advisory lock (если уже держится кем-то — блокируется до освобождения)
SELECT pg_advisory_lock(12345);

-- Критическая секция (например, обработка батча)
-- ... бизнес-логика ...

-- Освободить
SELECT pg_advisory_unlock(12345);

-- Non-blocking вариант (не ждёт, возвращает false, если занят)
SELECT pg_try_advisory_lock(12345);
```

Advisory lock может быть **session-level** (удерживается до `COMMIT`/`ROLLBACK`/отключения сессии) или **transaction-level** (`pg_advisory_xact_lock` — освобождается автоматически при завершении транзакции).

**Deadlocks (взаимная блокировка):**
Deadlock возникает, когда две транзакции ждут друг друга:
- T1 держит блокировку на строке A и хочет заблокировать B.
- T2 держит блокировку на строке B и хочет заблокировать A.
Обе ждут бесконечно → deadlock.

PostgreSQL **детектирует** deadlocks: параметр `deadlock_timeout` (по умолчанию 1 секунда) определяет, как часто проверяется граф блокировок. Если deadlock найден — одна из транзакций откатывается с ошибкой:

```
ERROR:  deadlock detected
DETAIL:  Process 12345 waits for ShareLock on transaction 67890; blocked by process 12346.
         Process 12346 waits for ShareLock on transaction 67890; blocked by process 12345.
HINT:  See server log for query details.
```

Мониторинг активных блокировок:

```sql
-- Кто кого блокирует
SELECT
    blocked.pid AS blocked_pid,
    blocking.pid AS blocking_pid,
    blocked.query AS blocked_query
FROM pg_stat_activity blocked
JOIN pg_locks bl ON bl.pid = blocked.pid AND NOT bl.granted
JOIN pg_locks kl ON kl.locktype = bl.locktype
    AND kl.database IS NOT DISTINCT FROM bl.database
    AND kl.relation IS NOT DISTINCT FROM bl.relation
    AND kl.page IS NOT DISTINCT FROM bl.page
    AND kl.tuple IS NOT DISTINCT FROM bl.tuple
    AND kl.virtualxid IS NOT DISTINCT FROM bl.virtualxid
    AND kl.transactionid IS NOT DISTINCT FROM bl.transactionid
    AND kl.classid IS NOT DISTINCT FROM bl.classid
    AND kl.objid IS NOT DISTINCT FROM bl.objid
    AND kl.objsubid IS NOT DISTINCT FROM bl.objsubid
    AND kl.granted
JOIN pg_stat_activity blocking ON blocking.pid = kl.pid;
```

**Trade-offs:**
- **`FOR UPDATE`**: гарантируется эксклюзивность, но блокирует другие `UPDATE`/`DELETE` на той же строке → риск дедлоков при неправильном порядке операций.
- **`FOR SHARE`**: позволяет параллельное чтение, но всё равно блокирует `UPDATE`/`DELETE` → подходит для «прочитать, проверить, записать с повторной проверкой».
- **Advisory locks**: гибкость (любая логика), но PostgreSQL не знает, что именно блокируется — полная ответственность на приложении (риск забыть `unlock`).

**Follow-up (что спросит интервьюер):**
- «Как избежать дедлока при переводе денег между счетами?» → всегда блокировать строки в **одном и том же порядке** (например, по `id` ASC).
- «Чем `FOR UPDATE` отличается от `FOR SHARE`?» → `FOR UPDATE` эксклюзивная (блокирует и чтение, и запись для других `FOR UPDATE`), `FOR SHARE` разделяемая (несколько `FOR SHARE` могут быть одновременно, но `FOR UPDATE` заблокирован).
- «Зачем advisory lock, если есть `FOR UPDATE`?» → advisory lock блокирует **не строку**, а произвольный «ресурс» (например, «обработка батча N») — `FOR UPDATE` не умеет это.
- «Что делать, если `pg_stat_activity` показывает много `waiting`?» → проверить `pg_locks`, убить блокирующую транзакцию (`pg_terminate_backend`) или уменьшить размер транзакций.

### 24. Как работает партиционирование таблиц в PostgreSQL

Партиционирование — это разбиение большой таблицы на несколько физических частей (партиций), которые логируют как одна таблица. Это **критичная** тема для high-load систем с большими объёмами данных (логи, заказы, события).

**Типы партиционирования:**

| Тип | Как делит | Пример |
| :--- | :--- | :--- |
| **Range** | Диапазоны значений | По датам (месяцы, кварталы), по ID (1–1M, 1M–2M) |
| **List** | Перечисление значений | По статусам (`PAID`, `CANCELED`), по регионам |
| **Hash** | Хеш-функция от значения | Равномерное распределение (без явного правила) |

**Range партиционирование** (классика для логов/заказов):

```sql
-- Основная таблица (не хранит данные — только метаданные)
CREATE TABLE orders (
    id BIGINT,
    created_at TIMESTAMP NOT NULL,
    total_amount NUMERIC
) PARTITION BY RANGE (created_at);

-- Партиции по кварталам
CREATE TABLE orders_2026_q1 PARTITION OF orders
    FOR VALUES FROM ('2026-01-01') TO ('2026-04-01');

CREATE TABLE orders_2026_q2 PARTITION OF orders
    FOR VALUES FROM ('2026-04-01') TO ('2026-07-01');

CREATE TABLE orders_2026_q3 PARTITION OF orders
    FOR VALUES FROM ('2026-07-01') TO ('2026-10-01');

CREATE TABLE orders_2026_q4 PARTITION OF orders
    FOR VALUES FROM ('2026-10-01') TO ('2027-01-01');

-- "Перехватчик" для данных вне диапазона
CREATE TABLE orders_default PARTITION OF orders DEFAULT;
```

**Partition pruning** — ключевое преимущество: планировщик **пропускает** партиции, которые не могут содержать нужные данные. Запрос `WHERE created_at > '2026-07-01'` не будет сканировать `orders_2026_q1` и `orders_2026_q2`.

```sql
-- EXPLAIN покажет, что используются только q3 и q4
EXPLAIN
SELECT COUNT(*) FROM orders WHERE created_at > '2026-07-01';
-- Seq Scan on orders_2026_q3
-- Seq Scan on orders_2026_q4
-- (q1 и q2 пропущены — partition pruning)
```

**Зачем партиционирование:**
- **Partition pruning** — запросы читают только нужные партиции.
- **Быстрое удаление старых данных**: `DROP TABLE orders_2026_q1;` — мгновенно, без `DELETE` по миллионам строк.
- **Параллельный VACUUM**: каждая партиция вакуумируется независимо (можно параллельно).
- **Локальные индексы**: индексы создаются **внутри** партиции (меньше по размеру, быстрее).
- **Maintenance**: `REINDEX`, `CLUSTER`, `VACUUM FULL` — по одной партиции (меньше блокировка).

**Ограничения:**
- Первичный ключ **должен включать** столбец партиционирования (иначе нарушение уникальности между партициями).
- Внешние ключи **на** партиционированную таблицу — поддерживаются с PG 12 (раньше — нет).
- `ALTER TABLE` на основной таблице применяется ко **всем** партициям (может быть долго).

**Trade-offs:**
- ✅ Ускоряет запросы с фильтрами по столбцу партиционирования (pruning).
- ✅ Упрощает управление большими объёмами (удаление, вакуум).
- ❌ Сложность схемы (больше объектов, миграции на каждую партицию).
- ❌ Если запрос **не** фильтрует по столбцу партиционирования — партиционирование бесполезно (сканируются все партиции, как одна большая таблица).
- ❌ PK должен включать столбец партиционирования → сложнее для применения.

**Follow-up (что спросит интервьюер):**
- «Как удалить данные старше 1 года?» → `DROP TABLE orders_2025_q1; DROP TABLE orders_2025_q2; ...` (или `DETACH PARTITION` + `DROP`).
- «Почему не `DELETE WHERE created_at < ...`?» → `DELETE` по миллионам строк создаёт мусор (MVCC), блокирует, долго. `DROP TABLE partition` — мгновенно.
- «Какой столбец выбрать для партиционирования?» → тот, по которому чаще всего фильтруют запросы (обычно время/дата для логов, статус для заказов).
- «Что если данные приходят не по порядку?» → Range партиционирование всё равно работает, но pruning менее эффективен (данные в партиции могут быть «перемешаны»).

### 25. Чем JSONB отличается от JSON в PostgreSQL и как его индексировать

Postgres поддерживает два типа для хранения JSON: **`JSON`** и **`JSONB`**. Они выглядят похоже, но устроены принципиально по-разному.

**JSON** (text-based):
- Хранит JSON **как есть** (текстовая строка).
- Сохраняет **порядок ключей** и **дубликаты** ключей.
- **Без индексов** (нельзя индексировать).
- Медленный на запросах (парсинг при каждом обращении).

**JSONB** (binary):
- Хранит JSON в **бинарном** формате.
- **Не сохраняет** порядок ключей и **удаляет** дубликаты.
- **Поддерживает индексы** (GIN, GiST).
- Быстрый на запросах (данные уже распарсены).

**Почему JSONB почти всегда лучше**: для большинства задач (поиск по полям, фильтрация) JSONB существенно быстрее. Порядок ключей в JSON для большинства приложений не важен.

**Операторы JSONB:**

| Оператор | Что делает | Пример |
| :--- | :--- | :--- |
| `->` | Извлечь значение как JSON | `profile -> 'address'` → `{"city": "Moscow"}` (JSON) |
| `->>` | Извлечь значение как текст | `profile ->> 'city'` → `'Moscow'` (text) |
| `#>` | Извлечь по массиву путей | `profile #> '{address,city}'` → `"Moscow"` |
| `#>>` | Как `#>`, но как текст | `profile #>> '{address,city}'` → `Moscow` |
| `@>` | Содержит (суперобъект) | `profile @> '{"role": "admin"}'` → true, если `role = admin` |
| `<@` | Содержится в (субобъект) | `'{"a":1,"b":2}' <@ profile` → true, если profile содержит a и b |
| `?` | Есть ли ключ | `profile ? 'email'` → true, если есть ключ `email` |
| `?&` | Есть ли все ключи (из массива) | `profile ?& ARRAY['a','b']` |
| `?\|` | Есть ли хотя бы один ключ | `profile ?\| ARRAY['a','b']` |

**Индексирование JSONB (GIN):**

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    profile JSONB
);

-- GIN-индекс по всему JSONB
CREATE INDEX idx_users_profile ON users USING GIN (profile);

-- Поиск пользователей с определённым интересом
SELECT * FROM users WHERE profile @> '{"interests": ["java"]}';

-- Извлечение поля (как текст)
SELECT profile ->> 'email' AS email FROM users;

-- Поиск по вложенному полю
SELECT * FROM users WHERE profile #> '{address,city}' = '"Moscow"';
```

**Expression index** (индекс на выражение) — для конкретного поля JSONB:

```sql
-- Индекс только на поле email (быстрее, чем GIN на весь JSONB)
CREATE INDEX idx_users_profile_email ON users ((profile ->> 'email'));

SELECT * FROM users WHERE profile ->> 'email' = 'john@example.com';
```

**Trade-offs:**
- **JSON**: сохраняет порядок/дубликаты, но **нельзя индексировать** → медленные запросы.
- **JSONB**: быстрый, индексируемый, но **не сохраняет порядок** ключей и дубликаты (для большинства задач не важно).
- **GIN на весь JSONB**: гибкий (любые запросы `@>`, `?`), но медленный `INSERT`/`UPDATE` и занимает много места.
- **Expression index на конкретное поле**: быстрый `INSERT`, но работает только для **одного** поля (нужен отдельный индекс на каждое поле).

**Follow-up (что спросит интервьюер):**
- «Когда JSONB лучше, чем отдельная таблица?» → когда структура данных **изменяется часто** (добавляют поля) и не все записи имеют все поля. Если структура фиксированная и все записи имеют все поля — отдельная таблица с колонками будет быстрее.
- «Как искать в массиве значений JSONB?» → `profile @> '{"tags": ["java"]}'` (содержит) или `profile ? 'java'` (если массив на верхнем уровне).
- «Какой индекс для JSONB: GIN или expression?» → GIN если нужны запросы по **разным** полям, expression если только по **одному** конкретному полю (быстрее INSERT).
- «JSONB поддерживает `LIKE`?» → Нет, `LIKE` работает только на `text`. Нужно `profile ->> 'name' LIKE '%john%'` (но без индекса — seq scan) или GIN + `pg_trgm`.

### 26. Что такое нормализация баз данных (1NF, 2NF, 3NF, BCNF)

Нормализация — это процесс **упорядочивания** структуры БД для минимизации избыточности данных и аномалий вставки/обновления/удаления. Нормальные формы — это последовательные условия, которые должна удовлетворять схема.

**1NF (Первая нормальная форма):**
- Все значения **атомарны** (не составные, не массивы, не списки).
- Нет повторяющихся групп (групп) столбцов.
- Каждый столбец содержит **одну** единицу данных.

```sql
-- ❌ НЕ 1NF: "phones" — составное значение (массив)
CREATE TABLE users (
    id INT PRIMARY KEY,
    name TEXT,
    phones TEXT[]  -- массив = не атомарно
);

-- ✅ 1NF: отдельная таблица для телефонов
CREATE TABLE users (
    id INT PRIMARY KEY,
    name TEXT
);
CREATE TABLE user_phones (
    user_id INT REFERENCES users(id),
    phone TEXT,
    PRIMARY KEY (user_id, phone)
);
```

**2NF (Вторая нормальная форма):**
- 1NF + **все** неключевые атрибуты зависят от **всего** первичного ключа (а не от его части).
- Актуально только для **составных** первичных ключей.

```sql
-- ❌ НЕ 2NF: composite PK (order_id, product_id), но "product_name" зависит только от product_id
CREATE TABLE order_items (
    order_id INT,
    product_id INT,
    product_name TEXT,  -- зависит от product_id, а не от всего PK
    quantity INT,
    PRIMARY KEY (order_id, product_id)
);

-- ✅ 2NF: информация о продукте вынесена в отдельную таблицу
CREATE TABLE order_items (
    order_id INT,
    product_id INT,
    quantity INT,
    PRIMARY KEY (order_id, product_id)
);
CREATE TABLE products (
    id INT PRIMARY KEY,
    name TEXT
);
```

**3NF (Третья нормальная форма):**
- 2NF + **нет транзитивных зависимостей** (неключевой атрибут не зависит от другого неключевого атрибута).

```sql
-- ❌ НЕ 3NF: "department_name" зависит от "department_id" (неключевой атрибут зависит от неключевого)
CREATE TABLE employees (
    id INT PRIMARY KEY,
    name TEXT,
    department_id INT,
    department_name TEXT  -- транзитивная зависимость: id → department_id → department_name
);

-- ✅ 3NF: department_name вынесена
CREATE TABLE employees (
    id INT PRIMARY KEY,
    name TEXT,
    department_id INT REFERENCES departments(id)
);
CREATE TABLE departments (
    id INT PRIMARY KEY,
    name TEXT
);
```

**BCNF (Boyce-Codd Normal Form):**
- Усиление 3NF: **каждый** детерминант (то, что определяет другие атрибуты) должен быть **кандидатным ключом**.
- В большинстве практических случаев 3NF и BCNF совпадают; BCNF требует строгой проверки всех детерминантов.

**Денормализация** — намеренное нарушение нормальных форм для **улучшения производительности чтения**:
- Когда **read-heavy** (чтения значительно чаще записей).
- Для **отчётности** (дашборды, аналитика).
- Когда JOINs становятся узким местом.

Пример: в таблице `orders` добавить `customer_name` (хотя это в `customers`) — чтобы не делать JOIN на каждом чтении.

**Trade-offs:**
- **Нормализация (3NF/BCNF)**: минимум избыточности, простые обновления, но много JOINs → медленные чтения.
- **Денормализация**: быстрые чтения (меньше JOINs), но избыточность → риск рассинхронизации при обновлениях.

**Follow-up (что спросит интервьюер):**
- «Зачем нормализация?» → избежать аномалий (вставка/обновление/удаление), уменьшить избыточность, упростить обновления.
- «Когда денормализация оправдана?» → read-heavy, отчётность, JOINs — узкое место. Пример: `orders.customer_name` для ускорения чтения.
- «Чем 3NF отличается от 2NF?» → 3NF добавляет запрет транзитивных зависимостей (неключевой атрибут не зависит от другого неключевого).
- «Что такое BCNF?» → усиление 3NF: каждый детерминант должен быть кандидатным ключом.

### 27. Что такое CTE (Common Table Expressions) и рекурсивные запросы

**CTE (Common Table Expression)** — это «виртуальная таблица», объявленная через `WITH` в начале запроса. CTE улучшает читаемость запросов, позволяет разбить сложный запрос на логические части и (в PostgreSQL 12+) оптимизируется планировщиком.

**Обычный CTE:**

```sql
WITH recent_orders AS (
    SELECT id, total_amount
    FROM orders
    WHERE created_at > NOW() - INTERVAL '1 month'
)
SELECT p.category, SUM(roi.total_amount) AS revenue
FROM order_items oi
JOIN recent_orders roi ON oi.order_id = roi.id
JOIN products p ON oi.product_id = p.id
GROUP BY p.category;
```

**CTE vs подзапрос:**
- **CTE** — лучше для **читаемости** (именование промежуточного результата).
- **Подзапрос** — в PostgreSQL 12+ часто **оптимизируется** (inline) в основной запрос, если это выгоднее.
- До PostgreSQL 12 CTE **всегда** материализовались (были optimization fence), начиная с 12 — планировщик может inline'ить.

**Управление материализацией CTE (PG 12+):**

```sql
-- Принудительная материализация (как до PG 12)
WITH recent_orders AS MATERIALIZED (
    SELECT id FROM orders WHERE created_at > NOW() - INTERVAL '1 month'
)
SELECT ...;

-- Принудительный inline (не материализовать)
WITH recent_orders AS NOT MATERIALIZED (
    SELECT id FROM orders WHERE created_at > NOW() - INTERVAL '1 month'
)
SELECT ...;

-- Без указания — планировщик решает сам
WITH recent_orders AS (
    SELECT id FROM orders WHERE created_at > NOW() - INTERVAL '1 month'
)
SELECT ...;
```

**Рекурсивный CTE (`WITH RECURSIVE`):**
Рекурсивный CTE — мощнейший инструмент для работы с **иерархическими** данными (дерево категорий, оргструктура, граф). Он состоит из **базового случая** (anchor) и **рекурсивного шага** (рекурсия).

```sql
-- Иерархия категорий (дерево)
WITH RECURSIVE category_tree AS (
    -- Базовый случай: корневые категории (parent_id IS NULL)
    SELECT id, name, parent_id, 0 AS depth, ARRAY[id] AS path
    FROM categories
    WHERE parent_id IS NULL

    UNION ALL

    -- Рекурсивный шаг: дети (присоединяем к уже найденным)
    SELECT c.id, c.name, c.parent_id, ct.depth + 1, ct.path || c.id
    FROM categories c
    JOIN category_tree ct ON c.parent_id = ct.id
)
SELECT * FROM category_tree ORDER BY path;
```

**Как работает:**
1. **Базовый случай**: находит все корневые категории (depth=0, path=[id]).
2. **Рекурсивный шаг**: для каждой уже найденной категории находит её детей (depth+1, path дополняется id ребёнка).
3. Процесс продолжается, пока не будут найдены все уровни дерева.

**`path` как массив** — позволяет:
- Вычислять **глубину** вложенности (`depth`).
- Строить **путь** от корня до узла (`path = [1, 5, 12]`).
- Обнаружать **циклы** (если id уже в path — цикл).

**Применения рекурсивных CTE:**
- Иерархии (категории товаров, оргструктура, дерево папок).
- Графы (маршруты, зависимости).
- Генерация последовательностей (например, все даты за месяц).

```sql
-- Генерация последовательности дат за 30 дней
WITH RECURSIVE date_range AS (
    SELECT NOW() - INTERVAL '1 day' AS date
    UNION ALL
    SELECT date + INTERVAL '1 day'
    FROM date_range
    WHERE date < NOW()
)
SELECT date FROM date_range ORDER BY date;
```

**Trade-offs:**
- **CTE**: читаемость, разбивка запроса на части. В PG 12+ оптимизируется (inline или материализация).
- **Рекурсивный CTE**: мощный для иерархий, но **может быть медленным** на глубоких деревьях (без ограничений по глубине — риск бесконечной рекурсии при циклах).
- **Подзапрос**: в PG 12+ часто оптимизируется лучше CTE (inline), но менее читаем для сложных запросов.

**Follow-up (что спросит интервьюер):**
- «Чем CTE отличается от подзапроса?» → CTE — именованная временная таблица (читаемость), подзапрос — inline. В PG 12+ CTE может быть inline'д (оптимизирован).
- «Как избежать бесконечной рекурсии в рекурсивном CTE?» → добавлять условие остановки (например, `WHERE depth < 10`) или проверку на цикл (`WHERE id NOT IN path`).
- «Когда рекурсивный CTE лучше, чем self-JOIN?» → при **неизвестной глубине** иерархии (self-JOIN требует фиксированного числа уровней).
- «Что такое `MATERIALIZED` / `NOT MATERIALIZED` в CTE?» → принудительная материализация / inline (PG 12+). Без указания — планировщик решает сам.

### 28. Что такое материализованные представления (Materialized Views)

**Материализованное представление** — это **физически сохранённый** результат запроса (в отличие от обычного `VIEW`, который вычисляется при каждом обращении). Оно позволяет кэшировать **тяжёлые** агрегаты и вычисления, которые не нужно пересчитывать каждый раз.

**Создание:**

```sql
CREATE MATERIALIZED VIEW daily_revenue AS
SELECT
    date_trunc('day', created_at) AS day,
    SUM(total_amount) AS revenue,
    COUNT(*) AS order_count
FROM orders
WHERE status = 'PAID'
GROUP BY date_trunc('day', created_at);

-- Обычный запрос — мгновенно (данные уже посчитаны)
SELECT * FROM daily_revenue WHERE day > NOW() - INTERVAL '7 days';
```

**Обновление (REFRESH):**

```sql
-- Полное обновление (пересчёт всего)
REFRESH MATERIALIZED VIEW daily_revenue;

-- Конкурентное обновление (без блокировки чтения)
-- Требует UNIQUE INDEX на материализованном представлении
CREATE UNIQUE INDEX idx_daily_revenue_day ON daily_revenue (day);
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_revenue;
```

**`CONCURRENTLY`** — обновляет только **изменённые** строки (дифф), не блокирует чтение. Без `CONCURRENTLY` — полное пересоздание (блокирует чтение на время обновления).

**Автоматическое обновление:**
PostgreSQL **не** поддерживает триггеры на материализованные представления (как на обычные VIEW). Обновление нужно планировать **вручную**:
- **Cron** (pg_cron или внешний cron): `REFRESH MATERIALIZED VIEW daily_revenue;` каждые N минут.
- **Приложение** (Spring `@Scheduled`): вызвать `REFRESH` через JDBC.
- **Событие** (после загрузки данных): обновить после `COPY` / массового `INSERT`.

**Trade-offs:**
- ✅ **Мгновенное чтение** тяжёлых агрегатов (данные уже посчитаны).
- ✅ **Разгрузка** основной таблицы (запросы идут в материализованное представление).
- ❌ **Данные устаревают** между обновлениями (не real-time).
- ❌ **Дополнительное место** на диске (дублирование данных).
- ❌ **Нужно планировать refresh** (cron, события) — иначе данные устареют.

**Обычный VIEW vs материализованное представление:**

| Критерий | VIEW | MATERIALIZED VIEW |
| :--- | :--- | :--- |
| Вычисление | При каждом обращении | Один раз (при создании/refresh) |
| Скорость чтения | Зависит от запроса | Мгновенно (кэш) |
| Актуальность | Всегда актуально | Устаревает между refresh |
| Место на диске | Не занимает | Занимает (дублирование) |
| Обновление | Автоматически | Вручную (REFRESH) |

**Follow-up (что спросит интервьюер):**
- «Когда материализованное представление лучше, чем обычный VIEW?» → когда запрос **тяжёлый** (агрегаты, JOINs по большим таблицам) и **не требует real-time** (можно обновлять раз в 5–15 минут).
- «Как обновлять материализованное представление без блокировки чтения?» → `REFRESH MATERIALIZED VIEW CONCURRENTLY` + UNIQUE INDEX.
- «Можно ли обновлять автоматически (триггер)?» → Нет, PostgreSQL не поддерживает триггеры на материализованные представления. Нужно cron / приложение / событие.
- «Материализованное представление vs отдельная таблица?» → Мат. представление — **производное** (вычисляется из других таблиц), отдельная таблица — **источник** (данные загружаются). Мат. представление удобнее, если логика вычисления меняется (нужно пересоздать VIEW, а не менять загрузку).

### 29. Почему для PostgreSQL критически важен Connection Pool (HikariCP, PgBouncer)

В отличие от MySQL (архитектура **thread-per-connection**), PostgreSQL использует архитектуру **process-per-connection**. Каждое новое клиентское соединение создаёт **отдельный процесс** ОС, который:
- Потребляет ~2–10 МБ **оперативной памяти**.
- Тратит ресурсы CPU на **инициализацию** (fork, setup).
- Удерживает файловые дескрипторы, буферы.

**Последствия для high-load:**
- Прямое создание сотен/тысяч соединений на каждый HTTP-запрос быстро **исчерпает память** и лимит `max_connections` (по умолчанию 100), приводя к падению БД.
- **Создание соединения** занимает ~20–50 мс (TCP handshake, authentication) — это **узкое место** при высокой нагрузке.

**Решение на стороне приложения (HikariCP):**
**HikariCP** — пул соединений **в приложении** (JDBC-уровень). Держит **горячую** пул из 10–50 соединений и **переиспользует** их между запросами.

```yaml
# Spring Boot + HikariCP
spring:
  datasource:
    hikari:
      maximum-pool-size: 20
      minimum-idle: 5
      connection-timeout: 30000
      idle-timeout: 600000
      max-lifetime: 1800000
```

**Решение на стороне сервера (PgBouncer):**
**PgBouncer** — пул соединений **на сетевом уровне** (между приложением и PostgreSQL). Мультиплексирует **тысячи** клиентских соединений на **малое число** реальных соединений с Postgres.

**Режимы PgBouncer:**

| Режим | Как работает | Когда использовать |
| :--- | :--- | :--- |
| **Session** | Клиентское соединение привязано к реальному на всё время сессии | Когда нужны `SET`/prepared statements на уровне сессии |
| **Transaction** (самый частый) | Клиентское соединение привязано к реальному **только на время транзакции** | Высокая нагрузка, короткие транзакции |
| **Statement** | Клиентское соединение привязано к реальному **на время одного запроса** | Максимальная плотность, но проблемы с prepared statements |

**Проблема prepared statements в Transaction-режиме:**
В режиме **Transaction** prepared statements **не работают** (или работают с ограничениями), потому что prepared statement привязан к **реальному** соединению, а в Transaction-режиме клиентское соединение может быть привязано к **разным** реальным соединениям в разных транзакциях.

**Решения:**
- Использовать **unnamed statements** (не prepared) — работают в любом режиме.
- Настроить `pgbouncer_force_prepared_statements=0` (выключить prepared statements).
- Использовать **Session-режим** (но это снижает плотность пула).

**Архитектура с HikariCP + PgBouncer:**

```
Приложение (Spring Boot)
    ↓ (HikariCP: 20 соединений)
PgBouncer (мультиплексор)
    ↓ (10 реальных соединений)
PostgreSQL
```

**Trade-offs:**
- **HikariCP** (в приложении): простой, быстрый (JDBC-уровень), но каждый инстанс приложения держит **свой** пул (N инстансов × 20 соединений = 20N соединений к Postgres).
- **PgBouncer** (на сервере): централизованный, масштабируется (тысячи клиентов → 10 реальных), но добавляет **сетевой хоп** и сложность (настройка, мониторинг).
- **Совместное использование** (HikariCP + PgBouncer): лучшее из обоих миров — HikariCP уменьшает число соединений от приложения, PgBouncer мультиплексирует их на Postgres.

**Follow-up (что спросит интервьюер):**
- «Почему нельзя открывать соединение на каждый запрос?» → Создание соединения ~20–50 мс, процесс-per-connection в Postgres → исчерпание памяти/`max_connections`.
- «HikariCP vs PgBouncer — когда что?» → HikariCP — всегда (в приложении), PgBouncer — при **очень** высокой нагрузке (сотни/тысячи клиентов).
- «Что делать с prepared statements в PgBouncer Transaction-режиме?» → Использовать unnamed statements или выключить prepared statements (`pgbouncer_force_prepared_statements=0`).
- «Какой размер пула выбрать?» → HikariCP: 10–50 (зависит от нагрузки и числа инстансов). PgBouncer: `max_client_conn` (тысячи), `pool_size` (10–50 реальных).

### Common PostgreSQL Pitfalls

Типичные ошибки, которые приводят к проблемам с производительностью или целостностью данных.

**1. N+1 на уровне БД**
Выполнение запросов **в цикле приложения** вместо одного `JOIN`. Например, вместо одного запроса «заказы + товары» делать 1 запрос на заказы + N запросов на товары (по каждому заказу).
- **Решение**: `JOIN` или `IN (...)` с батчем. В Hibernate/JPA — `fetch join` или `@BatchSize`.

**2. Забытый `VACUUM`**
Без регулярного `VACUUM` таблица **раздувается** мёртвыми версиями строк (MVCC). Производительность падает (больше I/O, индексы разрастаются). В крайнем случае — **wraparound XID** (база останавливается).
- **Решение**: убедиться, что `autovacuum` включён и настроен (на больших таблицах может не успевать — уменьшить `autovacuum_vacuum_scale_factor`).

**3. Медленный `COUNT(*)`**
В PostgreSQL `COUNT(*)` **медленный**, потому что из-за MVCC нет метаданных о количестве строк (в отличие от InnoDB в MySQL, который хранит это в статистике). `COUNT(*)` делает **полное сканирование** таблицы.
- **Решение**: для приблизительного подсчёта — `pg_stat_user_tables.n_live_tup` (быстро, но неточно). Для точного — `COUNT(*)` (медленно, но точно). Для инкрементального подсчёта — отдельная таблица-счётчик.

**4. `SELECT *` в production**
`SELECT *` выбирает **все** столбцы, включая те, которые не нужны. Это:
- Лишний I/O (чтение всех колонок).
- Проблемы с **TOAST** (большие значения >2 КБ хранятся отдельно, `SELECT *` может прочитать их).
- Хрупкость кода (при добавлении столбца в таблицу — приложение может сломаться).
- **Решение**: выбирать только нужные столбцы.

**5. Prepared statements в PgBouncer Transaction-режиме**
В режиме **Transaction** prepared statements **не работают** (или работают с ограничениями), потому что prepared statement привязан к реальному соединению, а клиентское соединение может быть привязано к разным реальным в разных транзакциях.
- **Решение**: использовать unnamed statements, выключить prepared statements (`pgbouncer_force_prepared_statements=0`) или перейти на Session-режим.

**6. Неактуальная статистика (нет `ANALYZE`)**
Планировщик использует **устаревшую** статистику → выбирает неоптимальный план (например, `Seq Scan` вместо индекса).
- **Решение**: `ANALYZE` после массовых изменений данных, убедиться что `autovacuum` + `analyze` работают.

**7. `SELECT ... FOR UPDATE` без `ORDER BY`**
Блокировка строк в **неопределённом** порядке → риск **дедлоков** (две транзакции блокируют строки в разном порядке).
- **Решение**: всегда `ORDER BY` по первичному ключу (детерминированный порядок блокировки).

**8. Неиндексируемые условия (functions on indexed column)**
`WHERE LOWER(email) = 'john@example.com'` — функция `LOWER()` **обнуляет** индекс по `email` (планировщик не может использовать индекс, если столбец обёрнут в функцию).
- **Решение**: **expression index** — `CREATE INDEX ON users (LOWER(email))` — индекс на выражение.
