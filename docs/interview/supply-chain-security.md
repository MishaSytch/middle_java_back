# Supply Chain Security

### 1. SBOM (Software Bill of Materials): CycloneDX, SPDX
**SBOM** — структурированный список всех компонентов в software artifact (dependencies, versions, hashes, licenses).

**Форматы:**
- **CycloneDX** (cборка: `cyclonedx-maven-plugin`)
  ```xml
  <plugin>
      <groupId>org.cyclonedx</groupId>
      <artifactId>cyclonedx-maven-plugin</artifactId>
      <version>2.8.0</version>
      <executions>
          <execution>
              <goals><goal>makeBom</goal></goals>
          </execution>
      </executions>
  </plugin>
  ```
  - JSON/XML
  - Component hierarchy (direct + transitive)
  - Hashes (SHA-256), licenses, CVE references

- **SPDX** (Software Package Data Exchange)
  - Лицензионный focus (licenses, copyright)
  - Tag-value / RDF / JSON
  - Когда: license compliance, legal review

**Применение:**
- Vulnerability management: SBOM → scan → CVE alerts
- License compliance: SBOM → check licenses
- Security audit: SBOM → verify provenance
- Regulatory: EU Cyber Resilience Act (2026) — SBOM required для hardware/software

**Tools:**
- `syft` (Aqua) — generate SBOM from container images, source code
- `grype` (Anchore) — scan SBOM для CVE
- `trivy` — SBOM + vulnerability scan
- `OWASP Dependency-Check` — Maven/Gradle plugin, NVD DB

**CI integration:**
```yaml
# GitHub Actions
- name: Generate SBOM
  run: mvn cyclonedx:makeBom
- name: Upload SBOM
  uses: actions/upload-artifact@v4
  with:
    name: sbom
    path: bom.json
```

### 2. Sigstore/cosign: signing container images
**Проблема:** как гарантировать, что image в registry — тот, что вы собрали (не подменён)?

**Sigstore:**
- Open source framework для signing и verifying artifacts
- Components: `cosign` (CLI), `fulcio` (CA), `rekor` (transparency log)
- Short-lived certificates (no long-lived keys)
- Keyless signing (via OIDC: GitHub Actions, GCP, AWS)

**Cosign:**
```bash
# Sign image (keyless, GitHub Actions)
cosign sign --yes ghcr.io/owner/repo:tag

# Verify signature
cosign verify --yes ghcr.io/owner/repo:tag

# Verify against specific identity
cosign verify --yes \
  --issuer=https://token.actions.githubusercontent.com \
  --identity-regexp=".*github.com/owner/repo.*" \
  ghcr.io/owner/repo:tag
```

**GitHub Actions integration:**
```yaml
- name: Sign image
  uses: sigstore/cosign-action@v3
  with:
    image: ${{ env.IMAGE }}
    tags: ${{ env.TAG }}
    upload: true
```

**Kubernetes admission:**
- `sigstore/policy-controller` — verify signatures on deploy
- `ValidatingWebhook`: reject images without valid signature

**Практика 2026:**
- Sign все production images
- Verify in CI (build → sign → push)
- Verify in cluster (admission controller)
- Keyless signing (OIDC) — preferred over long-lived keys

### 3. Reproducible builds: проверка идентичности сборок
**Цель:** один и тот же source code → один и тот же binary (hash match).

**Почему важно:**
- Supply chain attack detection (modified source → different binary)
- Audit: third-party может воспроизвести сборку и проверить
- Transparency: no hidden modifications

**Tools:**
- `reproducible-builds.org` — standard, tools
- Java: Maven/Gradle — не reproducible из коробки (timestamps, random ordering)
  - Workaround: fix timestamps (`SOURCE_DATE_EPOCH`), sort resources
  - `mvn package -Dbuild.timestamp=...`
- Docker: `docker build` с `--build-arg SOURCE_DATE_EPOCH=...`
- `debsnap`, `reprotest` — для Linux packages

**CI/CD:**
```yaml
# Build twice, compare hashes
- name: Build 1
  run: mvn package && sha256sum target/app.jar > hash1
- name: Build 2
  run: mvn package && sha256sum target/app.jar > hash2
- name: Compare
  run: diff hash1 hash2 || echo "Not reproducible!"
```

**Практика:**
- Не критично для Java (JVM, не binary)
- Критично для native (GraalVM, C, Go, Rust)
- Docker images: layer hashes должны match

### 4. Dependency verification: Gradle verification metadata, Maven locked modes
**Gradle Verification Metadata (`gradle/verification-metadata.xml`):**
```xml
<verification-metadata xmlns="http://schemas.gradle.org/gradle-verification-metadata/1.0">
    <components>
        <component group="com.example" name="lib" version="1.0.0">
            <artifact>
                <sha256 value="abc123..." origin="Generated by Gradle"/>
            </artifact>
        </component>
    </components>
</verification-metadata>
```
- `gradle --write-verification-metadata sha256` — generate
- Build: verify hashes, fail on mismatch
- Когда: locked dependencies, security audit

**Maven locked modes:**
- `mvn dependency:resolve -Dlockfile` — generate lock file
- `mvn -Dlockfile` — verify against lock file
- Maven 3.9+: `maven-lockfile` plugin
- Alternative: `maven-enforcer-plugin` (ban versions, require versions)

**Практика:**
- Production: locked dependencies (no surprise updates)
- CI: verify hashes, fail on mismatch
- Update process: explicit dependency bump → regenerate lock file

### 5. Vulnerability scanning: Snyk, Dependabot, OWASP Dependency-Check
**Tools:**
- **Snyk** (commercial): SCA + container + IaC, cloud platform
- **Dependabot** (GitHub): auto-update PRs, vulnerability alerts
- **OWASP Dependency-Check** (OSS): Maven/Gradle plugin, NVD DB
- **Trivy** (Aqua): container + filesystem + SCA
- **Grype** (Anchore): SCA, SBOM-based

**OWASP Dependency-Check (Maven):**
```xml
<plugin>
    <groupId>org.owasp</groupId>
    <artifactId>dependency-check-maven</artifactId>
    <version>9.0.0</version>
    <configuration>
        <failBuildOnCVSS>7</failBuildOnCVSS>
        <suppressionFile>suppressions.xml</suppressionFile>
    </configuration>
</plugin>
```

**Dependabot (GitHub):**
```yaml
# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: "maven"
    directory: "/"
    schedule:
      interval: "weekly"
    groups:
      spring:
        patterns: ["org.springframework*"]
```

**CI/CD:**
```yaml
# GitHub Actions
- name: Snyk scan
  uses: snyk/actions/maven@master
  env:
    SNYK_TOKEN: ${{ secrets.SNYK_TOKEN }}
  with:
    args: --fail-on=all

- name: Trivy scan
  uses: aquasecurity/trivy-action@master
  with:
    scan-type: 'fs'
    format: 'sarif'
    output: 'trivy-results.sarif'
```

**Процесс:**
1. Scan (CI: every PR, every build)
2. Report (dashboard: Snyk, GitHub Security)
3. Triage (CVSS score, exploitability, business impact)
4. Patch (Dependabot PR, manual update)
5. Verify (re-scan, confirm fix)

### 6. CVE management: prioritization, patching strategy
**CVE (Common Vulnerabilities and Exposures):** уникальный идентификатор для vulnerability.

**Prioritization:**
- **CVSS score** (0-10): exploitability, impact
  - Critical: 9.0-10.0
  - High: 7.0-8.9
  - Medium: 4.0-6.9
  - Low: 0.1-3.9
- **EPSS** (Exploit Prediction Scoring System): вероятность exploit в 30 дней
- **Business context**: is this dependency used in critical path?

**Patching strategy:**
1. **Critical (CVSS 9+, EPSS > 0.5)**: patch within 24-48h
2. **High (CVSS 7-8.9)**: patch within 1 week
3. **Medium (CVSS 4-6.9)**: patch within 1 month
4. **Low (CVSS 0.1-3.9)**: patch quarterly

**Process:**
- Alert (Snyk, Dependabot, GitHub Security)
- Triage (security team: is it real? impact?)
- Assess (which services affected? critical path?)
- Patch (update dependency, test, deploy)
- Verify (re-scan, monitor)
- Document (post-mortem, lessons learned)

**Suppressions:**
- False positive (CVE не applicable к нашему использованию)
- Accepted risk (patch не available, risk acceptable)
- `suppressions.xml` (OWASP), Snyk ignore, Dependabot ignore

### 7. Build provenance и SLSA framework
**SLSA (Supply-chain Levels for Software Artifacts):**
- Framework для evaluation supply chain security
- Levels: L1 (basic) → L4 (highest)
- Focus: provenance, build integrity, identity

**SLSA Levels:**
- **L1**: Build provenance (who, what, when, where)
- **L2**: L1 + build isolation (hermetic build, no external access)
- **L3**: L2 + reproducible builds + verified provenance
- **L4**: L3 + formal verification

**Provenance:**
- `in-toto` / `SLSA Provenance` — signed attestation:
  ```json
  {
    "_type": "https://slsa.dev/provenance/v0.2",
    "buildType": "https://github.com/actions/runner",
    "builder": { "id": "https://github.com/owner/repo" },
    "buildInvocation": { "configSource": { "revision": "abc123" } },
    "materials": [ { "uri": "sha256:...", "digest": "..." } ],
    "product": [ { "uri": "sha256:...", "digest": "..." } ]
  }
  ```
- Signed (Sigstore, in-toto)
- Verified (consumer: verify signature, check builder identity)

**Tools:**
- `in-toto` — framework for provenance
- `slsa-github-generator` — generate provenance in GitHub Actions
- `cosign` — verify provenance

**GitHub Actions (SLSA L3+):**
```yaml
# .github/workflows/build.yml
- name: Build with provenance
  uses: slsa-framework/slsa-github-generator@v1
  with:
    compile_cmd: "mvn package"
```

**Практика 2026:**
- SLSA L2+ для production builds
- Provenance for all container images
- Verify provenance in cluster (admission)
- GitHub Actions: built-in SLSA support
